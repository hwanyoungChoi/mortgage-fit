# interior-tbd-amount — be 검토

2026-10-27 · 대상: `.cony/specs/interior-tbd-amount.md`(미커밋) · 검토 모드(코드 수정 없음) · 관점: 데이터 모델·공용 검증·서버·`/import`·D1 데이터·AC-0

## 판정

**D1: 조건부 찬성 (C).** A는 반대, B는 사용자 목표를 못 채워 반대. C의 구조(검증을 넓혀 먼저 배포, 비우기 화면은 나중)는 맞다. 다만 "24시간 대기"는 이 프로젝트에서 보호 효과의 근거가 약하다. 시간 대신 **사람이 확인하는 게이트**로 바꾸고 아래 조건을 스펙에 넣을 것을 요구한다.

## 확인한 사실 (코드로 읽음)

1. **저장 표현·검증 변경 범위.** 견적 금액을 막는 곳은 `src/lib/utils/validateInteriorPlan.ts:148` `parseQuote`의 `isInteriorAmount(value.amount)` 한 곳이다. 서버 `server/interiorPlans/parseInteriorPlanRequests.ts`는 `validateInteriorItemFields`·`parseInteriorItem`·`parseInteriorPlan`만 부르고 amount를 따로 보지 않는다(`isInteriorAmount`는 PATCH `budget`에만 쓴다). 로컬 `createInteriorPlanStore`(`addItem`·`updateItem`·`createPlan`)와 `parseInteriorPlans`도 같은 함수를 쓴다. 스펙의 "서버 코드 diff 0, 마이그레이션 0"은 맞다. 항목은 `interior_plan_items.data` JSON이라 스키마 변경이 없다(`migrations/0007_interior_plans.sql`).
2. **`parseOptional`의 의미가 스펙 규칙과 같다.** `hasValue`는 키 없음·`undefined`를 "없음"으로 보고, `null`·`0`·`""`·문자열·소수·상한 초과는 `isInteriorAmount`에서 걸려 null(=거부)이 된다. 스펙 45~49행의 "키 없음과 `undefined`만 미정" 규칙이 `parseOptional(value, "amount", isInteriorAmount)`로 그대로 나온다. 결과 객체에 `...(amount !== undefined && { amount })`로 쓰면 `amount: undefined` 키가 남지 않는다(`budget` 등 기존 선택 필드와 같은 패턴).
3. **서버 읽기는 검증하지 않는다.** `handleInteriorPlans.ts:58,65`는 `JSON.parse(row.data) as ...`로 그대로 돌려준다. 그래서 D1에 금액 없는 견적이 들어가도 서버 GET이 깨지지 않고, 옛 서버로 롤백해도 서버가 500을 내지 않는다. 깨지는 곳은 클라이언트 파서(`useInteriorPlanList.ts`의 `parseInteriorPlanWithItems`)다.
4. **옛 번들 탭 손실 경로(A3)는 맞다.** 순서를 따라가 확인했다.
   - `useInteriorPlanListSource.ts:72-79`의 `storage` 이벤트 → `store.notify()` → `useSyncExternalStore`가 `getSnapshot`을 다시 부름.
   - `interiorPlanStorage.ts`의 `getSnapshot`은 원문이 바뀌었으니 `parseInteriorPlans`를 다시 돌린다 → 옛 `parseQuote`가 amount 없는 견적에서 null → `parseInteriorPlanWithItems` null → `{ status: "corrupt" }`(계획 하나만이 아니라 전체).
   - `MortgageHome.tsx:363`이 `CorruptPlansNotice`를 그리고, [계획 초기화] → `window.confirm` → `source.reset`(`useInteriorPlanSource.ts:201`) → `store.reset`이 `removeItem`. 이 `removeItem`이 다른 탭에 `storage` 이벤트를 보내 새 탭도 빈 목록이 된다.
   - 손상 상태에서는 `readWritablePlans`가 실패를 돌려주므로 옛 탭이 **덮어쓰기로** 데이터를 잃게 하는 경로는 없다. 손실은 [초기화] 확인 창을 사용자가 누를 때만 생긴다. 확인 창 문구는 "원문을 먼저 복사하세요"이고 원문 textarea와 [원문 복사]가 있다.
   - 로그인 상태의 옛 탭은 `selectList()`가 `serverList.isError`로 `loadFailed`가 되어 "불러오지 못함"만 보인다. 파괴 동작 없음. 서버 데이터는 안전하다. 스펙 A3의 결론("유일한 손실 경로 = 로그아웃 + 같은 브라우저 + 옛 탭 + [초기화] 확인")에 동의한다.
5. **손실 경로의 실제 크기는 스펙이 말한 것보다 더 좁다.** 이 경로는 **로컬에만 있는 계획**을 지운다. `useInteriorPlanImport.ts`의 이전은 로컬 원문을 읽기만 하고 지우지 않으므로, 이미 로그인해서 이전된 계획은 로컬 사본을 잃어도 서버에 남는다. 진짜 손실은 "로그인한 적 없는/이전 전의 로컬 계획"에 한한다. (추론: 운영 D1·두 사용자의 실제 로컬 상태는 읽지 못했다. 사용자가 확인할 수 있는 항목이다.)
6. **타입 오류만으로는 fe가 고칠 곳 목록이 완성되지 않는다.** 스펙 190행 "타입 오류가 fe가 고칠 곳 목록이 된다"는 틀렸다. `interiorLineDraft.ts:40`의 `String(quote.amount)`는 `amount?: number`가 되어도 컴파일되고 런타임에 시트에 문자열 `"undefined"`가 들어간다. `interiorPlanRows.ts:79`의 `row.quote?.amount ?? 0`도 조용히 통과한다(이쪽은 의도대로 0). `LineRow.tsx:79`·`buildInteriorPlanTable.ts:40-41`은 `formatManwon`·`toWon`에서 타입 오류가 난다. `tsconfig`에 `exactOptionalPropertyTypes`가 없어 `amount: undefined`도 타입으로는 막히지 않는다(그래서 AC-0(g) 버그 2번 테스트가 유일한 방어다).
7. **`validateInteriorPlan.test.ts`의 반전 줄.** 373행 `quote({ amount: undefined })` → null이 맞다. 같은 `it`("견적·지급 금액은 필수")의 374행은 지급이라 그대로 두어야 하므로, 테스트 이름도 "지급 금액은 필수"로 바뀌어야 한다. 스펙 AC-0(a)의 "제거된 `expect(` 0개"와 충돌하지 않는지 qa가 감사에서 같이 봐야 한다(이름 변경은 단언 제거가 아님).

## D1 근거

1. **A 반대.** 배포 순간 열려 있던 모든 옛 탭이 곧바로 위험 구간에 들어가고, 그 시점에는 사용자가 미정을 저장하려고 새 번들을 쓰는 중이라 위험이 가장 높다. 버전 확인 장치를 같이 넣어도 이미 열린 탭에는 코드가 없다.
2. **B 반대.** 업체를 저장할 곳이 `quote.vendor` 하나뿐이라 시나리오 1·2를 못 채운다(스펙 224행의 분석에 동의). 자리 표시 금액·별도 키 우회도 조용한 왜곡/손실이라 버린 판단이 맞다. 이번 요청에 한해 "업체·견적 빈 줄 만들기만 허용"은 사용자 목표가 아니다.
3. **C 찬성.** 1단계에서 읽는 쪽을 먼저 넓히면 "새 클라이언트 + 옛 서버"는 없고(A2: 한 Workers 배포에 서버와 정적 번들이 같이 바뀐다) 위험은 "2단계 시점에 열려 있는 1단계 이전 탭"으로 줄어든다. 1단계는 사용자가 미정을 만들 수 없으므로 1단계 배포 자체는 해가 없다. 1단계만으로 P⁺ 읽기 경로를 전부 테스트할 수 있다는 점도 가치가 있다. 서버 diff가 없어 비용은 배포 한 번과 대기뿐이다.

## "24시간 대기·롤백 하한"에 대한 판단

- **24시간은 무엇을 보호하는가.** 옛 번들 탭은 시간이 지난다고 새 번들이 되지 않는다. 이 앱은 서비스 워커·버전 확인이 없다(`grep` 결과 없음, `public/`은 favicon뿐). 탭을 새로고침하거나 브라우저가 탭을 버렸다가 다시 열 때만 새 번들이 된다. 따라서 24시간은 "사용자가 그 사이 새로고침했을 확률"의 대리 지표일 뿐 보장이 아니다. 사용자 2명이면 그 확률을 사람이 직접 확인하는 편이 더 싸고 확실하다.
- **더 단순한 완화책.** 시간 게이트를 "두 사용자 확인 게이트"로 바꾼다. 1단계 배포 후 사용자 두 사람이 자기 기기(PC·휴대폰)의 우리 집 탭을 닫거나 새로고침했다고 답하면 2단계를 머지한다. 대기 시간은 위 확인에 부수로 둔다(사용자가 바로 확인하면 24시간을 기다릴 이유가 없다). 한 줄이면 되고 구현 비용 0이다.
- **손실 자체를 없애는 확인.** 손실은 로컬 전용 계획에만 생긴다. 2단계 전에 사용자가 "로그인 없이 만든 계획이 있는가, 로그인했을 때 이전됐는가"를 확인하게 한다. 이전돼 있으면 최악의 경우에도 서버에 사본이 있다.
- **롤백 하한은 맞지만 문장을 구체화해야 한다.** "태스크 1 이전 번들로 롤백 금지"만으로는 Workers Builds가 main 머지마다 배포하는 이 프로젝트에서 어떻게 롤백하는지가 모호하다. 정확한 규칙은 "2단계에 문제가 생기면 **revert PR로 1단계 상태**로 되돌린다(1단계 이전으로 가지 않는다)"이다. 1단계 상태는 금액 없는 데이터를 정상으로 읽으므로 2단계 revert 뒤 이미 저장된 미정 줄도 안전하다. 1단계 이전으로 가면 로컬은 전부 손상 화면(이 탭에서도), 로그인 사용자는 미정 줄이 있는 계획이 하나만 있어도 목록 조회 전체가 실패한다(파서가 하나라도 어긋나면 전체 실패). 대시보드 롤백 버튼으로 이전 버전을 고르는 실수를 막으려면 1단계 배포의 커밋·시각을 `.cony/log.md`에 적는 것(이미 AC-0(e)에 있음)에 더해 ADR에 같은 값을 적는다.
- **결론.** 대기 시간 자체는 해롭지 않지만 근거로 삼기에 약하다. 24시간을 "필수 게이트"가 아니라 "사용자 확인이 늦으면 기다리는 기본값"으로 낮추고, 확인을 게이트로 한다.

## 리스크

- **R1 (중) 수동 확인 방법 오류.** 스펙 182행의 "1단계 빌드 탭과 2단계 브랜치 빌드 탭을 함께 띄워"는 두 서버가 다른 포트면 origin이 달라 localStorage가 공유되지 않고 `storage` 이벤트도 가지 않는다. 같은 origin에서 1단계 빌드로 탭을 연 채 서버를 2단계 빌드로 바꿔 같은 포트로 띄우고, 새 탭에서 저장하는 순서여야 재현된다.
- **R2 (중) 미리보기 배포와 운영 D1.** `wrangler.jsonc`의 `d1_databases`는 하나뿐이고 `previews: {}`에 별도 DB가 없다. 추론: PR 미리보기 Worker가 운영 D1에 연결돼 있을 수 있다(대시보드 설정은 못 봤다). 그렇다면 2단계 브랜치 미리보기에서 로그인해 미정 줄을 저장하면 1단계가 운영에 나가기 전에 운영 데이터에 금액 없는 견적이 들어가 옛 번들 사용자의 목록 조회가 실패한다. 순서상 2단계는 1단계 뒤라 막히지만, 로컬 하네스로만 검증하고 실계정으로 미리보기에 쓰기를 하지 않는다는 규칙을 둔다.
- **R3 (저) 수식·표시 누락.** 위 사실 6의 `String(quote.amount)`가 "undefined"를 칸에 넣는다. 1단계 `ItemSheet`가 미정 줄을 열 때 빈칸이어야 한다는 AC가 1-2에 있지만 단언 대상으로 명시돼야 한다.
- **R4 (저) 같은 필수→선택 완화의 반복.** 이번이 처음이라 규칙을 ADR-033과 `interior-planner.md`에 적는 계획은 좋다. 다만 "필수 → 선택 완화"에서 **한 번 들어간 데이터는 되돌릴 수 없다**(옛 파서가 받지 못함)는 점을 한 줄 더 적으면 된다.
- **R5 (저) 합계의 `?? 0`.** `interiorPlanRows.ts:79`는 이미 `row.quote?.amount ?? 0`이라 미정이 조용히 0으로 합쳐진다. 의도된 동작이지만 "미정 n건"이 같이 나오지 않으면 0원으로 오해된다는 A5를 AC-1·AC-3이 다룬다. 이 계산과 건수는 `interiorPlanRows` 한 함수에서 같은 판단("확정이고 금액이 있는가")으로 만들어야 한다(요약·표·허브가 따로 세지 않게).

## 스펙에 넣을 조건

1. AC-0(e)의 게이트를 바꾼다: "태스크 2는 태스크 1 배포 기록(커밋·시각)이 `.cony/log.md`에 있고, **사용자 두 사람이 자기 기기의 열린 우리 집 탭을 닫거나 새로고침했다고 확인한 뒤**에 머지한다. 확인이 늦으면 24시간을 기본 대기로 한다." 24시간 단독 게이트 문구는 지운다.
2. 롤백 하한 문구를 구체화한다: "2단계 문제는 revert PR로 1단계 상태에 맞추고, 1단계 이전 커밋/버전으로 되돌리지 않는다." 1단계 배포 커밋·시각을 ADR-033에 적는다.
3. 2단계 전에 사용자에게 묻는다: 로그인 없이 만들어 이전되지 않은 로컬 계획이 있는가(있으면 로그인해서 이전된 것을 확인하거나, 손상 화면에 닿으면 [초기화] 전에 원문을 복사하도록 안내).
4. 1-2의 `interiorLineDraft.ts:40`을 명시한다: `amount?`가 되면 `String(quote.amount)`가 컴파일되지만 "undefined"를 넣는다 → `quote?.amount` 분기로 고치고, 미정 줄을 열면 견적 칸이 `""`이라는 단언을 1-3에 둔다. "타입 오류가 목록이 된다" 문장은 "타입 오류 + `grep amount`로 `String(`·템플릿 사용처 확인"으로 고친다.
5. 1-3 수동 확인을 같은 origin으로 고친다(옛 빌드 탭을 연 채 같은 포트에서 새 빌드로 교체).
6. 1-1 테스트: `validateInteriorPlan.test.ts` 373행만 반전하고, 같은 `it`의 이름을 지급 전용으로 바꾼다(374행 지급 undefined → null은 유지). 새 단언에 `amount: undefined` 키가 결과에 없음(`Object.hasOwn`)을 넣는다(`exactOptionalPropertyTypes` 없음).
7. 1-1 서버 하네스(새 파일): `/import`, 항목 POST·PUT·계획 POST에서 금액 없는 견적 200, `null`/`0`/`"100"`/`1.5`/`1e9` → 400, GET이 `toStrictEqual`로 입력과 같음. 기존 `server/**` 테스트 파일 수정 0을 유지한다.
8. 미리보기 규칙: 2단계 검증에 실계정으로 미리보기 URL에 쓰기를 하지 않는다. 로컬 하네스·`pnpm dev`로 한다(미리보기가 운영 D1을 쓰는지 확인되기 전까지).
9. 미정 건수·지출 예정·남은 예산은 `interiorPlanRows` 한 곳에서 계산하고 요약·표·CSV·허브가 그 결과를 쓴다(같은 판단을 여러 곳에 두지 않는다).
10. ADR-033에 "필수 → 선택 완화는 2단계 배포, 저장된 선택 필드는 이후 옛 번들이 읽지 못하므로 되돌릴 수 없다"를 적는다(스펙의 계획대로 + 마지막 문장).
