# [우리 집] 금액 원 단위 입력·표시 — be 제안

- 날짜: 2026-10-27
- 브랜치: `cony/interior-tbd-amount`(1단계 커밋 065a94b, 배포 전)
- 모드: 제안(코드 수정 없음)

## 결론

추천은 **A안**이다. 원 단위 값을 새 키에 정수로 저장하고, 견적 금액(`quote.amountWon`)과 총 예산(`plan.budgetWon`)만 옮긴다. 옛 키(`amount`·`budget`, 만원)는 다시 쓰지 않고, 읽을 때 한 함수에서 ×10,000으로 바꾼다.

이번 원 단위 변경은 ADR-033과 같은 게이트를 탈 수 있다. 조건이 하나 있다: **새 키 읽기와 보존을 1단계 배포 전에 1단계에 넣어야 한다.** 1단계가 지금 상태로 먼저 배포되면, 그 번들은 새 키를 모르고 쓸 때 지운다. 그러면 원 단위 변경에 2단계 배포를 한 번 더 해야 한다.

## 판단 근거로 확인한 코드 사실

1. **알려진 키만 복사하는 곳이 세 군데다.**
   - `parseQuote`·`validateInteriorPlanFields`는 알려진 키만 담은 새 객체를 만든다(`validateInteriorPlan.ts:148-162, 199-212`).
   - 로컬 저장소는 쓸 때마다 파싱한 스냅샷 **전체**를 다시 직렬화한다(`interiorPlanStorage.ts` `commit`, `writePlan`).
   - 서버 GET 응답도 클라이언트가 같은 파서로 걸러 캐시에 둔다(`useInteriorPlanList.ts:14-23`). 항목 PUT은 그 캐시에서 만든 항목 전체를 보낸다(`interiorLineWrites.ts` `inputOf`).
   - 결과: 새 키를 모르는 번들은 로그인 여부와 상관없이 **어떤 쓰기를 하든** 새 키를 조용히 지운다. 로컬에서는 다른 계획의 키까지 지운다.
2. **서버와 클라이언트는 한 번에 배포된다**(ADR-011 개정: Workers + Static Assets). 그래서 "옛 서버 + 새 번들" 조합은 없고, 위험은 열려 있는 옛 번들 탭뿐이다.
3. **플랜 PATCH는 병합된 결과를 다시 검증하지 않는다.** `UPDATE … SET data = json_patch(data, ?3)`로 바로 쓴다(`handleInteriorPlans.ts:296-305`). 그래서 같은 뜻의 두 키(`budget`·`budgetWon`)가 함께 남지 않게 하는 규칙을 PATCH 파싱에 둬야 한다.
4. **표·CSV·인쇄는 이미 원 단위다.**
   - `buildInteriorPlanTable.ts:35-45`의 `toWon`, `interiorPlanExportText.ts:30`의 `formatWon`(같은 변환이 두 군데 있다).
   - 목록·요약·허브는 `formatManwon`을 쓴다(`LineRow.tsx:40`, `PlanSummary.tsx:23`, `MortgageHub.tsx:114`).
   - 계산은 `interiorPlanRows.ts` 한 곳(`buildInteriorPlanRows`·`summarizeInteriorPlan`)이고, 허브도 그 결과를 쓴다(`summarizeHub.ts`).
5. **화면에서 입력하는 금액은 견적과 총 예산뿐이다.**
   - 견적: `interiorLineDraft.ts`. 총 예산: `CreatePlanSheet`·`PlanSettingsSheet`.
   - 항목 예산은 매물 추가 비용 가져오기가 만원으로 쓰고(`extraCostsToInteriorItems.ts`), 빈 줄 비고 "예산 n"에 표시만 된다.
   - 지급은 화면에 없고, 쓰기 때 그대로 돌려보낸다.
6. **`PlanSettingsSheet`는 이름만 바꿔도 `budget`을 보낸다.** 빈칸이면 `null`을 보낸다(`:60, :96-100`). 아래 A안 조건 4가 이 동작 때문에 필요하다.

## 선택지

### A. 값마다 새 키(원 정수): `quote.amountWon?`, `plan.budgetWon?` — 추천

**어떤 금액을 원으로 옮기나**

- 견적과 총 예산만 옮긴다. 화면에 남은 입력이 이 둘뿐이기 때문이다.
- 항목 예산(`item.budget`)과 지급(`payment.amount`)은 저장 형식을 그대로 두고, 표시할 때만 ×10,000한다. 이 둘은 입력하는 화면이 없어서 새 키를 만들 이유가 없다.
- 매물 추가 비용 가져오기는 항목 예산을 지금처럼 만원으로 쓴다(코드 변경 없음). 만들기 시트의 총 예산 미리 채움만 ×10,000으로 바꾸고, 저장은 `budgetWon`으로 한다.

**읽기 규칙(한 곳에서만)**

- `quoteWonOf(q)`는 다음 순서로 값을 정한다.
  - `amountWon`이 있으면 그 값
  - 없고 `amount`가 있으면 `amount × 10,000`
  - 둘 다 없으면 미정
- `planBudgetWonOf(p)`도 같은 규칙이다.
- 두 함수와 `WON_PER_MANWON`을 공용 파일 한 곳에 두고, `buildInteriorPlanRows`(지출 예정·미정 건수)와 `summarizeInteriorPlan`(총 예산·남은 예산)만 이 함수를 부른다. 이때 `plannedTotal`·`budget`·`remaining`은 원 단위가 된다.
- 요약·표·CSV·허브는 그 결과를 포맷만 한다. `buildInteriorPlanTable`의 `toWon`과 export의 `formatWon` 중복은 하나로 합친다.
- **파서는 저장 형태를 바꾸지 않는다.** `amount`를 `amountWon`으로 정규화하면 로컬 쓰기 한 번에 모든 계획이 다시 쓰여, 옛 탭에서 손상으로 읽힌다. ADR-033 조건 3의 GET `toStrictEqual` 왕복 테스트도 깨진다.

**검증(`validateInteriorPlan.ts`, 공용)**

| 대상                                         | 규칙                                                              |
| -------------------------------------------- | ----------------------------------------------------------------- |
| `amountWon`                                  | `Number.isSafeInteger`, 0~`MAX_WON`. 0은 ADR-033 개정의 셀프 시공 |
| `budgetWon`                                  | 1~`MAX_WON`                                                       |
| 한 견적에 `amount`와 `amountWon`이 함께 있음 | 거부(null)                                                        |
| 한 플랜에 `budget`과 `budgetWon`이 함께 있음 | 거부(null)                                                        |
| `amount`                                     | 지금 규칙 1~999,999,999 그대로                                    |

- `amount`에 0을 허용하는 ADR-033 개정은 필요 없어진다. 2단계부터는 `amount`를 쓰지 않기 때문이다. 1단계 diff가 그만큼 줄어든다.
- 두 키가 함께 있으면 거부하는 이유: 어느 쪽이 맞는지 고를 수 없다. 이 상태는 쓰기 버그로만 생기고, 아래 쓰기 규칙이 막는다.

**상한**

- 추천: `MAX_WON = 9_999_999_999_999`(13자리).
  - 옛 최대값 999,999,999만원 × 10,000 = 9,999,999,990,000도 이 안에 든다. 그래서 금액 칸을 건드리지 않은 옛 줄을 저장해도 상한 오류가 나지 않는다.
  - 최악의 합계: 지출 예정은 항목 100개 × 확정 1개 × 1e13 = 1e15, 남은 예산은 −1e15 이상이다. `Number.MAX_SAFE_INTEGER`(9.007e15)보다 작으므로 정수 연산이 정확하다.
- 입력 검증 `validateWonAmount`: 13자리 초과는 "최대 13자리" 오류. 견적은 0을 허용하고 총 예산은 하한 1이다. `parseAmount`의 숫자열 규칙은 그대로 쓴다.

**쓰기 규칙(같은 뜻의 두 키가 동시에 남지 않게)**

1. 견적 쓰기 `editedQuote`(공용 함수 하나)
   - 1단계: `amount`를 쓰면서 `amountWon`을 구조 분해로 뺀다.
   - 2단계: `amountWon`을 쓰면서 `amount`를 뺀다. 미정이면 둘 다 뺀다.
   - 고친 견적만 바뀌고 형제 견적은 원래 키 그대로 둔다(옛 데이터를 다시 쓰지 않음).
2. 총 예산 PATCH는 공용 순수 함수 `budgetMergePatch` 하나로 처리하고, 서버 `parsePlanPatchRequest`와 로컬 `applyPlanPatch`가 같이 쓴다.
   - 요청에 `budget`이나 `budgetWon` 중 하나라도 있으면 두 키를 함께 정한다(준 키는 그 값, 다른 키는 `null`).
   - 두 키를 모두 숫자로 주면 400이다.
   - 이렇게 하면 1단계 탭이 2단계 데이터 위에 `{budget: n}`을 보내도 `budgetWon`이 지워지고 n이 이긴다(사용자 편집이 조용히 무시되지 않는다).
3. 1단계 `PlanSettingsSheet`는 **바뀐 칸만 보낸다**(근거 6). 그렇지 않으면 1단계 탭에서 이름만 바꿔도 `budget: null`이 나가 위 규칙에 따라 `budgetWon`이 지워진다.

**옛 번들·"알려진 키만 복사"**

| 번들                                       | 2단계 데이터(`amountWon`만 있는 견적)                    | 결과                                             |
| ------------------------------------------ | -------------------------------------------------------- | ------------------------------------------------ |
| 1단계 이전                                 | 로컬은 `amount` 없음 → corrupt. 서버는 조회 실패         | ADR-033과 같은 위험이고 같은 게이트로 막는다     |
| 1단계(이 제안대로 새 키를 아는 번들)       | 읽고 보존한다                                            | 손실 없음                                        |
| 1단계(새 키를 모르는 번들, 지금의 065a94b) | 미정으로 읽는다. **쓰기 한 번에 `amountWon`이 지워진다** | 조용한 손실. 그래서 1단계에 반드시 포함해야 한다 |

- 1단계 시트에서 원 단위 견적을 열 때
  - `amountWon % 10000 === 0`이면 만원으로 채운다.
  - 아니면 `""`로 열고, 지금 필수 오류로 다시 입력하게 한다. 미정 줄과 같은 처리라 조용한 손실은 없다.
  - 0원은 1단계 입력 규칙에 걸려 다시 입력하게 된다.
- 1단계 설정 시트도 같은 규칙으로 채운다. 바뀐 칸만 보내므로 건드리지 않으면 값이 보존된다.

**만원·원이 섞인 계획의 합계**

- 모두 `quoteWonOf`로 원 정수로 바꾼 뒤 더하므로 정확하다.
- 예: 확정 `{amount: 800}`과 `{amountWon: 1234500}` → 9,234,500원.
- 총 예산 `{budget: 1000}`, 지출 예정 9,234,500원 → 남은 예산 765,500원.

**홈 허브**

- `HubPlanLine.plannedTotal`이 원 단위가 되고, 표시는 원 포맷으로 바뀐다.
- 같은 허브의 계산기 카드(매매가, 만원)는 그대로라 카드 사이 단위가 다르다. 제품 확인이 필요하다(아래 "결정 필요" 2).

**서버·마이그레이션**

- D1 마이그레이션 없음. JSON `data` 컬럼이라 키 추가는 저장 형식 변경이 아니다.
- 서버 코드 diff는 0이 아니다:
  - `parseInteriorPlanRequests.ts`의 PATCH 키 목록, `budgetMergePatch` 적용, 오류 메시지
  - 타입(`InteriorPlanPatch`)
- 그래서 ADR-033 조건 3의 "서버 diff 0"은 이번 1단계에 맞지 않는다. 개정해야 한다.
- 견적만 옮기면(A-1, 아래) 서버 diff는 0으로 유지된다.

**API 계약 변경**

- 견적에 `amountWon?`, 플랜에 `budgetWon?`가 생긴다.
- PATCH가 `budgetWon`(숫자 또는 null)을 받고, 두 키를 함께 정하는 규칙이 생긴다.
- 두 키가 함께 오면 400이다(POST·PUT·import·PATCH 모두).
- 스펙 `interior-planner.md` "API 계약"과 `interior-tbd-amount.md` "데이터 모델" 갱신이 필요하다.

**게이트에 합치는 방법**

- 태스크 1(1단계, 배포 전)에 넣을 것
  - 검증
  - 타입
  - `quoteWonOf`·`planBudgetWonOf`
  - 원 표시(목록·요약·허브)
  - `editedQuote`의 `amountWon` 빼기
  - `budgetMergePatch`(서버·로컬)
  - 설정 시트 "바뀐 칸만 보내기"
  - 1단계 시트의 원→만원 채우기 규칙
- 태스크 2(2단계, 게이트 뒤)에 넣을 것
  - 원 입력 시트(줄·만들기·설정)
  - `amountWon`·`budgetWon` 쓰기
  - 미정 비우기·0원
- 게이트 조건은 ADR-033 조건 1을 그대로 쓴다.
- 롤백 하한은 1단계다. 1단계는 두 키를 다 읽으므로 2단계를 revert해도 안전하다.

**테스트 가능성(전부 순수 함수 + 기존 D1 하네스)**

- 검증 표
  - 통과: `amount`만 / `amountWon`만 / 둘 다 없음(미정) / `amountWon` 0 / 9,999,999,999,999
  - 거부: 둘 다 있음 / 10,000,000,000,000 / 1.5 / "1" / null
  - 결과에 `Object.hasOwn` 단언
- `quoteWonOf`·혼합 계획 합계(위 예시 값)
- `budgetMergePatch` 4가지 입력 × 시작 상태 2가지
- `editedQuote`: 1단계는 `amountWon`을 빼고, 2단계는 `amount`를 뺀다. 형제 견적은 원래 키 그대로다.
- **1단계 보존 테스트**: 계획 X에 `amountWon`이 있을 때 계획 Y를 쓰면, 원문에서 X의 `amountWon`이 같은 값으로 남는다. 서버 쪽은 같은 항목의 형제 견적 PUT으로 확인한다.
- D1 하네스
  - 새 키로 POST·PUT·import 후 GET `toStrictEqual`
  - `budgetWon`이 있는 플랜에 PATCH `{budget}`을 보내면 `budget`만 남는다. 반대 방향도 확인한다.
  - 두 키가 함께 오면 400
- 옛 파서 기록은 ADR-033 조건 8과 같고, P⁺에 `amountWon` 견적을 추가한다.

**비용**

- 읽기 분기 두 개(`quoteWonOf`·`planBudgetWonOf`)는 영구히 남는다. AC-0 때문에 옛 데이터를 다시 쓰지 않으므로 이 분기가 이번 변경에서 유일한 호환 경로다. 두 함수 안에만 있다.

### A-1. A와 같지만 견적만 원으로(총 예산은 만원 그대로)

- 장점: 서버 diff 0과 ADR-033 조건 3을 그대로 지킨다. PATCH 규칙과 설정 시트 변경이 필요 없다.
- 단점
  - 총 예산 입력만 만원으로 남아 "입력·표시 모두 원"이라는 요청을 다 채우지 못한다.
  - 남은 예산 계산은 이미 원으로 맞추므로 표시는 원으로 통일할 수 있다. 다만 입력 단위가 칸마다 다르다.
- 사용자가 "견적만"이면 된다고 하면 이 안이 가장 단순하다.

### B. 플랜 단위 표시 `amountUnit: "won"`(같은 키의 뜻을 바꿈) — 비추천

- 항목은 플랜과 다른 행이다(ADR-029 D1 C). 그래서 항목 금액의 뜻이 다른 행의 키에 따라 달라진다.
  - 항목 PUT 검증은 플랜 단위를 모른다.
  - 기존 계획을 바꾸려면 플랜 PATCH와 항목 n개 PUT이 필요한데, 원자적이지 않다. 중간 상태에서는 금액이 10,000배로 잘못 읽힌다.
  - 바꾸지 않으면 사용자의 기존 계획은 계속 만원으로 입력해야 한다.
- 단위 키를 모르는 번들은 원 값을 **만원으로 읽어 10,000배로 보인다.** 손상 표시조차 없는 오독이다. 또 쓸 때 `amountUnit`을 지워 그 뒤로 계속 오독한다.
- 서버 diff, 테스트, 위험 모두 A보다 크다.

### C. 같은 키 `amount`(만원)에 소수 4자리 허용(예: 123.45) — 비추천

- 장점: 새 키가 없어 두 키 규칙과 PATCH 규칙이 필요 없다.
- 단점
  - 돈을 부동소수로 저장하게 된다. ADR-002가 정수를 택한 이유(정확한 계산)를 뒤집는다.
  - 관례(원화는 소수 없는 통화이고 최소 단위 정수로 저장)와도 어긋난다.
  - "소수 4자리 이하" 검사와 소비처마다 반올림(`Math.round(x*1e4)`)이 퍼진다. `isInteriorAmount`를 지급·항목 예산과 같이 쓰므로 그쪽 범위도 같이 넓어지거나 갈라진다.
  - 1단계 이전 번들은 소수를 손상으로 읽는다. 결국 게이트 비용은 A와 같다.

### 고려했지만 선택지에서 뺀 것

- **기존 `amount`를 원으로 일괄 재작성(D1 UPDATE·로컬 변환)**: "마이그레이션은 추가만"(AC-0)을 어긴다. 옛 탭은 원 값을 만원으로 10,000배 오독한다.

## 리스크

- **R1. 1단계 배포 순서.** 065a94b만 먼저 배포하면 그 번들이 운영에 퍼진다. 이후 원 단위 쓰기는 그 번들에서 조용히 지워진다. 원 단위를 이번 게이트에 태울지 1단계 배포 **전에** 확정해야 한다.
- **R2. 플랜 PATCH는 병합 뒤 검증이 없다.** 두 키 규칙을 빠뜨리면 두 키가 함께 남는다. 검증이 "둘 다 있음"을 거부하므로 그 순간 GET이 그 가구의 모든 계획을 조회 실패로 만든다. `budgetMergePatch` 테스트와 D1 하네스 테스트가 필수다.
- **R3. 1단계 탭의 다시 입력 요구.** 2단계 기기가 쓴 1,234,500원 견적을 1단계 탭에서 고치면 금액을 만원으로 다시 넣어야 한다. 사용자가 직접 넣는 값이라 조용한 손실은 아니지만 정밀도가 줄 수 있다. 게이트 기간에만 생긴다.
- **R4. 0원 개정의 범위가 바뀐다.** ADR-033 개정의 "견적 금액 0 허용"이 `amountWon`으로 옮겨 간다. ADR 문구를 고쳐야 한다(추론: 아직 0 허용 코드는 없다. `isInteriorAmount`는 `>= 1`이다).

## 조건(추천 A 채택 시)

1. 원 단위 결정과 1단계 보강을 **1단계 배포 전에** 머지한다. 1단계 PR에서 `amountWon` 보존 테스트가 통과해야 한다.
2. 원 변환과 옛 키 읽기는 `quoteWonOf`·`planBudgetWonOf` 두 곳뿐이다. 다른 곳에서 `amount`·`budget`을 직접 읽지 않는지 grep으로 확인한다. 예외는 항목 예산·지급 표시다(×10,000, 같은 `WON_PER_MANWON` 사용).
3. 두 키 규칙은 견적은 `editedQuote` 한 곳, 총 예산은 `budgetMergePatch` 한 곳에서 처리한다. 서버와 로컬은 `budgetMergePatch`를 같이 쓴다.
4. 1단계 설정 시트는 바뀐 칸만 보낸다.
5. 새 ADR-034(단위)를 쓴다. 내용은 다음과 같다.
   - ADR-002를 [우리 집] 견적·총 예산에 한해 뒤집는다(계산기·매물은 만원 그대로).
   - ADR-033의 게이트와 롤백 하한을 재사용한다.
   - ADR-033 조건 3(서버 diff 0)과 0원 개정을 함께 개정한다.
6. 스펙 API 계약(`interior-planner.md`)과 데이터 모델(`interior-tbd-amount.md`)을 갱신한다.

## 결정 필요

1. 범위: A(견적·총 예산, 추천) / A-1(견적만).
2. 표시 형식(pm·사용자)
   - 목록·요약·허브를 표처럼 "1,234,500원"으로 할지, 큰 금액은 "1억 2,345만 6,000원"처럼 할지.
   - 홈 허브의 계산기 카드(만원 "12억 5,000만원")와 우리 집 줄(원)이 다른 형식으로 나란히 보여도 되는지.
3. `MAX_WON` 13자리(추천, 옛 최대값을 포함) / 12자리(입력 현실치, 이 경우 옛 최대값 근처의 줄을 고칠 때 상한 오류).

## 확인한 사실과 추론

- **확인**(위 파일·줄)
  - 알려진 키만 복사하는 경로 세 곳
  - PATCH가 `json_patch` 후 검증하지 않음
  - 설정 시트가 이름만 바꿔도 `budget`을 보냄
  - 표·CSV가 이미 원 단위
  - 허브가 `summarizeInteriorPlan`을 재사용함
  - 서버와 클라이언트가 한 번에 배포됨
  - `isInteriorAmount` 하한이 1임
- **추론**(실행하지 않음)
  - 13자리 상한에서 합계가 안전 정수 안에 든다는 계산
  - 1단계 시트에서 원→만원으로 채우는 동작의 UX
  - D1 `json_patch`가 `null`로 키를 지운다는 점. RFC 7396과 SQLite 문서 기준이고, 기존 `budget: null` 경로가 이미 이 동작에 기대고 있다.
