# 태스크 5 표 내보내기 스펙 — qa 검토

날짜: 2026-10-27
대상: `.cony/specs/interior-planner.md` "표 내보내기" 절, 예시 플랜 Q, AC-11·AC-12, U13~U20, D6, A11~A17, 태스크 5-1~5-3
관점: 테스트 가능성(예시 값 직접 계산, 경계, jsdom 단언 방법, AC-0 유지)

## 판정: 조건부 찬성

예시 Q·P의 숫자와 CSV 문자열은 손으로 다시 계산해서 모두 맞다. 그래도 아래 조건이 남아 있다. 조건 중 3개는 스펙에 한 줄씩 넣어야 하고, 나머지는 5-2 테스트 계획에 반영하면 된다.

- 합계가 0일 때와 빈 표에서 "계"를 무엇으로 쓰는지가 정해져 있지 않다.
- 대표 견적이 "확정 우선, 없으면 최저, 동률이면 먼저 적은 것"인지를 가르는 예시가 Q에는 없고 P에만 일부 있다.
- CSV의 BOM을 `Blob.text()`로 읽으면 BOM이 사라져 테스트가 항상 실패하거나 BOM 검증이 무의미해진다. 바이트로 읽어야 한다.

### Q CSV

- 셀을 하나씩 세어 확인했다. 쉼표 5개가 모든 줄에서 맞고 `계,,,9800000,7500000,`, `에어컨,,[거실],,,"추후 구매 · 예산 1,500,000원"`, 마지막 `필름,…,2000000,2000000,`의 빈 비고 모두 맞다.
- 따옴표가 필요한 곳은 세부내용 "철거, 방수, 도기 교체"(쉼표), 비고 "…700,000원"(쉼표), "…1,500,000원"(쉼표)이고 스펙 문자열과 일치한다. `미확정 · 견적 2개 중 최저`는 `·`만 있어 감싸지 않는 것도 맞다.
- 세부내용이 모두 `[`로 시작하므로 수식 주입 대상이 없다. 헤더의 `(원)`은 감싸지 않아도 된다.
- 단점: Q CSV는 `"` 이스케이프, `'` 접두, LF 포함 셀을 하나도 쓰지 않는다. 이 부분은 AC-12(b)의 별도 입력으로만 검증된다(아래 3번 참고).

### 최대 금액

- 한 줄: 999,999,999 × 10,000 = 9,999,999,990,000 (13자리).
- 100개 합계: 99,999,999,900 × 10,000 = 999,999,999,000,000 (15자리). 맞다.
- 이 값은 모두 `Number.MAX_SAFE_INTEGER`(9.007e15)보다 작아 곱셈·덧셈이 정확하다. 따라서 `Number.isSafeInteger`가 참이라는 단언은 회귀 방지용일 뿐 변이를 잡지 못한다. 정확한 값(`999999999000000`, `"999,999,999,000,000"`)을 같이 단언해야 의미가 있다.

## 3. 경계 누락과 보탤 AC

### 3-1. 순수 함수 `buildInteriorPlanTable`

- 견적 0개 · 동률 최저 · 공간 없음 · 최대 금액은 AC-11 한 줄에 다 있지만 입력과 기대 문자열이 없다. 위 표의 값으로 단위 테스트를 만든다.
- 공간 없음: `spaceName === null`이면 세부내용이 `[공간 없음]`. 메모가 있으면 `[공간 없음] 메모`.
- 확정 견적 id가 견적에 없는 경우(`confirmedAmountOf`가 null): 미확정으로 취급된다. 손상된 로컬 데이터는 검증을 거치므로 우선순위는 낮다.
- 메모 앞뒤 공백은 `parseOptionalText`가 `trim`해서 저장하므로 "세부내용 끝에 공백이 남는" 경우는 검증 통과 데이터에서는 없다. 빈 메모는 키가 없다.
- 헤더 문자열(제목, 기준일 줄)은 컴포넌트가 아니라 순수 함수로 뺄 것을 조건으로 건다(아래 5번). 그래야 "총 예산 없음", "예상 총액 0" 경계를 jsdom 없이 단언한다.

### 3-2. `toCsv`

경계 입력을 모두 단위 테스트로 둔다. 기대는 모두 스펙 정의에서 나온다.

| 입력                                                             | 기대                                                                         |
| ---------------------------------------------------------------- | ---------------------------------------------------------------------------- |
| `하루"바스`                                                      | `"하루""바스"`                                                               |
| `줄1\n줄2`, `줄1\r\n줄2`                                         | 큰따옴표 안에 그대로                                                         |
| `a,b`                                                            | `"a,b"`                                                                      |
| `=1,2`                                                           | `"'=1,2"` (접두를 먼저, 이스케이프를 나중에. 순서가 바뀌면 `'"=1,2"`가 된다) |
| `=SUM(A1)`                                                       | `'=SUM(A1)` (쉼표 없으니 감싸지 않음)                                        |
| `-`, `+1`, `@x`, `\t탭`, `\r`, `\n`, `＝`, `＋`, `－`, `＠` 시작 | 앞에 `'`                                                                     |
| `'=1` (이미 `'`로 시작)                                          | 접두 없음                                                                    |
| 중간에 `=`가 있는 `a=1`                                          | 접두 없음                                                                    |
| 빈 문자열, `null`·`undefined`                                    | 빈 필드                                                                      |
| 숫자 `1800000`                                                   | 접두 없음, 감싸지 않음                                                       |
| 마지막 줄                                                        | CRLF로 끝                                                                    |
| 맨 앞                                                            | U+FEFF 하나(두 번 붙지 않음). BOM이 있어도 첫 필드 `구분`에 접두가 붙지 않음 |

### 3-3. 변이로 확인할 것 (5-2에 있는 것에 더해)

- 접두 삭제, BOM 삭제, 대표 견적을 "첫 견적"으로 → 5-2에 이미 있다.
- 추가 권장: 접두와 이스케이프 순서 뒤집기, `<`를 `<=`로, 대표 견적을 "최저"만 보도록(확정 무시), CRLF를 LF로, 마지막 줄 CRLF 삭제, 숫자 열에 접두 적용.

### 3-4. 숫자의 안전성과 합계 일치

- `계.확정 === summary.confirmedTotal * 10000`, `계.견적 === Σ대표 견적`을 Q·P·항목 100개 확정 999,999,999 모두에서 단언한다.
- 100개 입력의 fixture는 `plan.items`에 id·spaceId를 단순 반복해 만든다. 검증(`isInteriorPlan`)을 통과시킬 필요는 없다.

### 3-5. 파일 이름 `interiorPlanExportFileName(planName, today)`

스펙의 "하나씩 `_`로 바꾸고 앞뒤 공백·마침표를 뗀다"는 변환 순서에 따라 결과가 달라진다. 변환(`_` 치환)을 먼저, 앞뒤 정리를 나중에 하는 것으로 해석하고 다음 값을 AC에 못 박기를 권한다.

| 이름                       | 기대 파일 이름                    | 확인하는 것                                                                      |
| -------------------------- | --------------------------------- | -------------------------------------------------------------------------------- |
| `우리 집`                  | `우리 집-인테리어-2026-10-27.csv` | 공백은 유지                                                                      |
| `a/b:c?`                   | `a_b_c_-인테리어-2026-10-27.csv`  | 스펙 예시. 끝의 `_`는 떼지 않음                                                  |
| `.` , `...`, `.`           | `인테리어-2026-10-27.csv`         | 정리 후 비면 대체 이름                                                           |
| `///`                      | `___-인테리어-2026-10-27.csv`     | `/`는 `_`로 치환되므로 남는 것이 있다. 대체 이름이 아니다(이 값으로 해석을 고정) |
| `.숨김.`                   | `숨김-인테리어-2026-10-27.csv`    | 앞뒤 마침표 제거                                                                 |
| `a\tb`, `a\nb`, `a\u0000b` | `a_b-인테리어-…`                  | 제어 문자                                                                        |
| `a"b<c>d\|e*f\\g`          | `a_b_c_d_e_f_g-인테리어-…`        | 금지 문자 9개 전부                                                               |
| 40자 한글                  | 길이 그대로                       | 자르지 않음                                                                      |

- 제어 문자의 범위(U+0000~U+001F, U+007F 외에 U+0080~U+009F, U+2028/2029, 양방향 제어 U+202A~202E 등)는 스펙이 "제어 문자"라고만 쓴다. 확장자가 항상 `.csv`로 끝나 위험은 낮지만 범위를 고정해 두면 테스트가 모호하지 않다.
- 접미사 `-인테리어-…`가 항상 붙어 Windows 예약 이름(CON, NUL 등)은 문제가 되지 않는다.

## 4. jsdom에서 단언하는 방법

### 4-1. 인쇄

- `window.print`는 jsdom에 "Not implemented" 스텁으로 존재한다. `vi.spyOn(window, "print").mockImplementation(() => {})`로 호출만 센다.
- 단언: [인쇄·PDF] 클릭 1회 → `toHaveBeenCalledTimes(1)`. 마운트·표 보기 전환 후에는 0회(effect에서 부르는 사고를 막는다). 가리기·항목 0개에서는 클릭해도 0회.
- `@media print`는 jsdom에서 볼 수 없다. 스펙의 "리드 확인" 처리가 맞다(아래 7번에 확인표).

### 4-2. 내려받기: 세 층으로 나눈다

1. **`toCsv`와 행 만들기는 문자열을 직접 단언**한다. BOM은 `csv.charCodeAt(0) === 0xfeff`, CRLF는 `csv.endsWith("\r\n")`.
2. **`downloadTextFile` 단위 테스트**: jsdom에는 `URL.createObjectURL`·`revokeObjectURL`이 없으므로 `vi.fn`을 `URL`에 붙여 준다(`afterEach`에서 되돌림). 클릭은 `HTMLAnchorElement.prototype.click`을 `mockImplementation(function () { … this.download, this.href … })`로 가로챈다. 그렇지 않으면 jsdom이 `blob:` 이동에서 "Not implemented: navigation" 오류를 찍는다.
   - **Blob 내용을 읽을 때 `blob.text()`를 쓰지 않는다.** jsdom 30의 `Blob.text()`는 UTF-8 decode 규칙으로 맨 앞 BOM을 버린다(`node_modules/jsdom/lib/jsdom/living/helpers/encoding.js`의 `utf8Decode` 주석, Node의 `Blob`도 같음을 확인했다). `await blob.arrayBuffer()`로 바이트를 읽고 앞 3바이트가 `EF BB BF`인지, 전체가 `TextEncoder().encode("﻿" + expected)`와 같은지 비교한다. 다른 realm의 typed array는 `toEqual`이 불안정하므로 `Array.from(...)`으로 바꿔 비교한다.
   - `createObjectURL`에 넘어간 Blob의 `type`이 `text/csv;charset=utf-8`인지, `a.download`가 기대 파일 이름인지, `revokeObjectURL`이 같은 URL로 불리는지, 임시 `<a>`가 DOM에 남지 않는지 단언한다.
   - `revokeObjectURL`을 클릭 직후 동기로 부를지 지연할지는 스펙에 없다. 일부 브라우저(특히 Safari)는 바로 revoke하면 다운로드가 취소될 수 있다고 알려져 있어서 5-3의 실기 확인에 넣을 항목이다. 테스트는 `vi.useFakeTimers` 뒤 `vi.runAllTimers()`를 한 번 거치고 단언하게 써서 동기든 지연이든 통과하게 한다.
3. **화면 테스트는 `downloadTextFile`을 `vi.mock`해서 인자만** 본다: `(파일 이름, 전체 CSV 문자열)`. Q의 기대 CSV와 `===`로 비교한다. 이렇게 하면 화면 테스트에서 Blob·URL 스텁이 필요 없고, 가리기 때 0회 호출을 단언하기 쉽다. 파일 이름이 fe 마음대로 바뀔 수 있으므로(5-1 메모) 경로는 구현 뒤 맞춘다.

### 4-3. 기기 날짜

- 기존 화면 테스트의 패턴을 그대로 쓴다: `vi.useFakeTimers({ toFake: ["Date"] })` + `vi.setSystemTime(new Date(2026, 9, 27, 12, 0, 0))`(로컬 생성자라 시간대와 무관). `MortgageHome.test.tsx`에 같은 형태가 이미 있다. 표 머리의 기준일과 파일 이름 날짜 둘 다 이 한 값으로 확인한다.
- "누른 순간의 값"(표 읽기 전용 절): 파일 이름의 날짜는 클릭 시점의 `Date`, 표 머리의 날짜는 렌더 시점이어서 자정을 넘기면 둘이 다를 수 있다. 어느 쪽이 맞는지 스펙에 한 줄로 정하고(권장: 둘 다 같은 `now`를 쓴다) 23:59:59.999 → 00:00:00.000 경계 테스트 하나를 둔다.
- 값이 바뀐 뒤에 눌러도 새 값이 나가는지: 렌더 뒤 스토어를 바꿔(폴링 모방) 클릭하고 CSV가 새 값인지 확인한다. 핸들러가 낡은 클로저를 쥐는 결함을 잡는다.

### 4-4. 화면 구조

- 병합: 욕실 두 줄 중 첫 줄의 구분 셀이 `rowSpan === 2`, 둘째 줄에는 구분 셀이 없다(첫 줄 6셀, 둘째 줄 5셀). 한 줄짜리 묶음은 `rowSpan`이 1(DOM 기본값)이다. `td.rowSpan`으로 단언하면 속성 유무와 상관없다.
- 구분 셀을 `<th scope="rowgroup">`로 만들면 `cell` 역할이 아니라 `rowheader`가 된다. 테스트가 역할에 의존하므로 스펙이나 fe에서 한쪽으로 정하는 것이 좋다. 역할에 의존하지 않으려면 `within(row).getAllByRole(/cell|rowheader/)`처럼 쓸 수 있다.
- 표 전체를 Q 표와 비교할 때는 `tr`별 셀 텍스트를 2차원 배열로 뽑아 스펙의 열 값과 비교한다(병합 셀은 첫 줄에만 있으므로 그 배열 모양 자체가 병합 검증이다).
- 표에 접근 가능한 이름(`<caption>` 또는 `aria-label`)을 주면 `getByRole("table", { name })`로 찾을 수 있다. 이름이 없으면 화면에 표가 둘 이상 생길 때 질의가 모호해진다. 스펙에 "표의 접근 가능한 이름 = 표 머리 제목"을 한 줄 넣기를 권한다.
- 보기 전환: `getByRole("radio", { name: "표" })`. 이름이 "표"로 정확히 일치하는 라디오는 하나여야 한다. 표 보기에서 [항목 추가] 버튼이 없고(스펙의 "자리를 대체"), 줄을 눌러도 항목 시트(dialog)가 열리지 않는 것을 단언한다.
- 금액 열 오른쪽 정렬·고정폭, 360px 가로 스크롤, 페이지 가로 밀림은 jsdom에서 볼 수 없다(7번).

## 5. 구조 요구(테스트하기 어려운 구조를 만들지 않도록)

1. 표 머리 문자열(제목 `"{이름} 인테리어 계획"`, `"{날짜} 기준 · 총 예산 n원 · 예상 총액 n원"`)을 컴포넌트 안에서 조립하지 않고 순수 함수로 둔다(예: `buildInteriorPlanTable`의 결과에 포함하거나 형제 함수). 입력은 `plan.name`, `summary.budget`, `summary.expectedTotal`, `today`다. 그래야 "총 예산 없음", "예상 총액 0" 경계를 jsdom 없이 확인한다.
2. 원 단위 변환과 쉼표 서식은 순수 함수에서만 한다. 컴포넌트가 `* 10000`을 다시 하면 화면·CSV·인쇄가 어긋날 수 있다(스펙도 "같은 결과를 쓴다"고 쓴다). 화면 표는 `formatThousands(원 값)`만 호출하고 CSV는 정수를 그대로 쓴다는 구분을 코드 리뷰에서 확인한다.
3. 화면 표 컴포넌트가 `now`·`window`·`localStorage`를 직접 읽지 않고 props로 받는다. 날짜 주입은 `summarizeInteriorPlan(plan, now)`과 같은 방식이다.
4. 가리기 판단은 한 곳(`isPrivacyMode` prop 하나)에서만 한다. 버튼 비활성, 안내 문구, 내려받기 호출 차단 세 곳이 각자 판단하면 하나만 빠져도 값이 파일로 나간다. 핸들러 안에서도 `isPrivacyMode`를 한 번 더 확인하는 이중 방어를 권한다(비활성 버튼이 강제로 눌려도 0회가 되게).
5. 인쇄 숨김은 "숨길 것을 나열"하는 방식보다 "인쇄 영역만 보이게 하는" 방식이 안전하다(나중에 플랜 화면에 요소가 추가되어도 새지 않음). 예: `@media print`에서 문서 전체를 `visibility: hidden`으로 두고 인쇄 영역에만 `visibility: visible`을 준 뒤 위치를 맨 위로 옮기는 방식. 스펙은 숨김 목록을 쓰고 있는데 앱 전역의 다른 요소(글자 크기 조절, 알림 등)가 목록에서 빠질 수 있다. fe가 `AppRoutes`·`App`의 바깥 요소(`src/App.tsx`)를 확인하고 결정한다.

## 9. 리스크

- 가장 큰 위험은 CSV BOM 검증이 무의미해지는 것이다. `text()`로 읽으면 BOM이 항상 사라져, 구현이 BOM을 안 붙여도 "BOM 없음"과 구분 못 하는 쪽으로 테스트가 쓰이거나(기대를 맞추려고) BOM 단언이 영원히 실패한다. 반드시 바이트로 읽는다.
- 대표 견적 규칙(확정 우선 → 최저 → 먼저 적은 것)은 Q만으로는 세 변이 중 하나(첫 견적)만 잡힌다. P 샷시와 동률 값이 있어야 나머지를 잡는다.
- 인쇄 숨김이 목록 방식이면 jsdom이 못 잡는 누수가 생긴다. 리드의 실기 확인에만 의존하게 된다.
- 낡은 클로저: 폴링으로 값이 바뀐 뒤 내보낸 파일이 이전 값이면 사용자는 모른 채 틀린 파일을 받는다(4-3의 테스트가 필요).
- 안전하지 않은 값이 아니라 `'` 접두 자체의 부작용(엑셀에서 접두가 보임)은 A16에서 받아들였다. 자동 테스트가 아니라 5-3 확인으로 남는다.
