## 근거

### 1. 화면이 만원 값을 직접 읽는 곳이 적어서 A가 닿는 범위가 작다 (확인)

- 계산은 `interiorPlanRows.ts`의 `buildInteriorPlanRows`·`summarizeInteriorPlan` 한 곳이다. 허브는 `summarizeHub.ts`로 같은 결과를 쓴다.
- `formatManwon`을 부르는 우리 집 화면은 `LineRow.tsx:40, 58`, `PlanSummary.tsx:23`, `MortgageHub.tsx:114`뿐이다.
- 입력 화면은 `ItemSheet`(견적), `CreatePlanSheet`·`PlanSettingsSheet`(총 예산) 세 곳이고 모두 `AmountInput`을 쓴다.
- 표·CSV·인쇄는 이미 원이고 변환이 두 군데(`buildInteriorPlanTable.ts` `toWon`/`formatWon`, `interiorPlanExportText.ts` `formatWon`)에 중복돼 있다. A는 이 중복을 지울 기회다.

### 2. `AmountInput`은 만원 전용이라 단위 인자가 필요하다 (확인)

- 단위 글자 "만원", 힌트 `HINT_PLACEHOLDER = "만원 단위로 입력"`, 힌트 값 `formatManwon`, 검증 `validateAmount`(상한 9자리, 0 거부, 오류 문구에 "만원 단위"·"999,999,999만원")가 컴포넌트 안에 굳어 있다.
- 같은 컴포넌트를 계산기·매물 화면이 쓴다. 우리 집만 원으로 바꾸려면 `unit` 하나를 받아야 한다.
- 추천: `Record<AmountUnit, { suffix, placeholder, validate, formatHint }>` 레지스트리. 단위가 늘 때 분기를 늘리지 않는다. 지금 쓰는 값은 두 개(`manwon`, `won`)뿐이다.
- 검증은 하한이 호출처마다 다르다(견적 0 허용 / 총 예산 1). `validateWonAmount(raw, { min })`처럼 하한을 인자로 받는다.
- 오류 문구도 원용으로 새로 둔다("정수(원 단위)로 입력하세요", "최대 13자리(9,999,999,999,999원)까지"). 글자 수를 문구에 넣는다.

### 3. 설정 시트의 "바뀐 칸만 보내기"는 작고 안전하다 (확인 + 추론)

- `PlanSettingsSheet.tsx`는 `isChanged`를 이미 이름과 예산 각각 비교로 계산한다(`:75`). 같은 비교로 패치를 만들면 된다(`name`이 바뀌면 `name`, 예산이 바뀌면 예산 키).
- `InteriorPlanPatch`는 이미 모든 키가 선택이라(`interiorPlan.ts:92-97`) 타입 변경이 없다.
- 효과는 두 가지다. 1단계 시트에서 이름만 고쳐도 예산이 지워지지 않고, 2단계에서 옛 `budget`을 건드리지 않은 계획은 `budget` 그대로 둔다(AC-0).
- 추론: 이 경우 예산 칸을 비운 채 저장하면 지운다는 지금 동작(`null`)은 "칸이 바뀌었고 비었을 때만" 나간다. 테스트 한 줄이 필요하다.

## 화면별 검토

### 입력 시트

- `interiorLineDraft.amount`는 쉼표 뺀 문자열이다. 2단계에서는 원 문자열이 되고, `toInteriorLineDraft`는 `quoteWonOf`로 채운다. `isSameLineDraft`의 문자열 비교는 그대로 동작한다.
- 옛 `amount: 800`(만원) 줄을 열면 칸에 `8,000,000`이 보이고, 건드리지 않고 업체명만 고쳐도 `editedQuote`가 `amountWon`으로 다시 쓴다. 이 줄은 그때 새 키로 옮겨 간다. AC-0(옛 데이터를 다시 쓰지 않음)은 "열지 않은 줄"에 대한 말이라 충돌하지 않는다. 문서에 한 줄로 못 박아 두면 좋다.
- 원 입력은 "800"을 800원으로 받아 버린다. 만원 입력에 익숙한 사용자가 800만원을 넣으려다 800원을 저장할 수 있다(추론, 사용성 위험). 입력 힌트에 `800원`이 바로 보이게 하고(조건 3), 값이 10,000원 미만이면 힌트 줄에 "만원 단위가 아닙니다. 원 단위입니다"처럼 알린다. 저장을 막지는 않는다(0원·소액 합법).
- 13자리 입력은 자릿수를 세기 어렵다. 입력칸의 쉼표(`toAmountInputText`)에 더해 힌트 줄을 억·만 형식("1억 2,345만 6,000원")으로 보여 주는 것이 가장 값어치가 크다.

### 1단계 시트에서 원 단위 견적을 만원으로 채우기 (be 규칙)

- 만원으로 나누어떨어지면 채우고, 아니면 빈칸으로 연다. 조용한 손실은 없다.
- UX 문제: 금액이 있는 줄에서 "견적 금액을 입력하세요"가 뜬다. 업체명만 고치려던 사용자는 이유를 모른다. 게이트 기간에만 생기지만, 1단계 시트에 한 줄 안내가 필요하다(예: 빈칸이고 견적이 원 단위일 때 "원 단위 금액은 만원 단위로 다시 입력하세요"). 조건 5.
- 이 안내는 2단계에서 지우는 코드다. 폴백이 아니라 1단계 전용 임시 코드이므로 2단계 태스크에 삭제를 명시한다.

### 설정 시트·만들기 시트

- `CreatePlanSheet`의 미리 채움은 `sumExtraCosts`(만원)에 ×10,000을 곱해 `budgetWon`으로 저장한다. `WON_PER_MANWON`을 쓴다. 매물 가져오기가 만든 항목 예산(`item.budget`, 만원)은 그대로이고 표시만 ×10,000이다.
- 설정 시트 초기값은 `planBudgetWonOf(plan)`. 옛 `budget: 1000`은 `10,000,000`으로 보인다.

### 표시 형식

- 목록·요약·허브: "1,234,500원"(천 단위 쉼표 + 원) 추천. 이유는 세 가지다.
  - 표·CSV·인쇄·내보내기 본문이 이미 이 형식이라 화면과 인쇄물이 같은 글자로 읽힌다.
  - 목록은 금액을 위아래로 훑어 비교하는 화면이다. "800만원", "1,234,500원", "1억 2,345만 6,000원"이 섞이면 자릿수 비교가 안 된다. 억·만 형식은 금액이 둥글수록 짧고 아닐수록 길어 열이 흔들린다.
  - 길이는 최대 `9,999,999,999,999원`(17자)이다. 현실 값(수천만~수억)은 `125,000,000원`(12자)이라 모바일 줄에서 업체명과 같이 들어간다(추론, 실제 폭은 브라우저에서 확인해야 한다).
- 억·만 형식은 입력 힌트 줄에만 쓴다. 이때 `formatManwon` 재사용이 안 되므로(만원 단위 입력) 원 → 억·만 변환 함수 하나(`formatWonKorean`)를 둔다. 표시용 `formatWon`과 합쳐 `amount.ts` 옆 한 파일에 둔다.
- 허브: 계산기 카드는 "12억 5,000만원", 우리 집 줄은 "지출 예정 125,000,000원"이 나란히 보인다. 카드마다 보여 주는 것이 다르고(매물 수·한도 vs 지출 예정) 단위 표기("원"/"만원")가 글자에 붙어 있어 오독 위험은 낮다. 막지 않되 pm이 형식을 정한 뒤 확인한다. 가리기(`MaskedValue`) 동작은 그대로다.

### 계산 계층

- 조건 2 보강: `buildInteriorPlanRows`의 `budgetNote`도 원으로 내보내는 편이 낫다. 지금 `rowNoteOf(row, formatBudget)`는 만원을 받아 목록(`formatManwon`)과 표(`formatWon`)가 서로 다른 함수를 넘긴다. 원으로 내보내면 두 호출이 같은 `formatWon`이 되어 `rowNoteOf`의 인자가 필요 없다. 그러면 소비처(목록·표·CSV·허브·요약) 중 만원을 읽는 곳이 없다. be의 "예외는 항목 예산·지급 표시"가 사라진다.
- `InteriorPlanRows.plannedTotal`·`InteriorPlanSummary.budget/remaining`의 JSDoc "만원"을 "원"으로 고치고, 이름은 그대로 둔다(타입 검사가 `Won` 접미사를 강제하지 않으므로 필드 주석이 유일한 안전장치다). 필요하면 `plannedTotalWon`으로 바꿔 컴파일러가 놓친 소비처를 잡게 한다. 나는 이름 변경을 권한다. 단위가 바뀌는 순간 `plannedTotal`을 만원으로 읽는 코드가 조용히 틀린 값을 보여 주기 때문이다.

### 테스트 변경량

- 만원 표기를 단언하는 테스트가 많다(확인, `grep -c "만원"`): `MortgageHome.lines.test.tsx` 37, `MortgageHub.summary.test.tsx` 33, `createSimple` 14, `tbd` 14, `lineSheet` 10 등 약 130곳. 2단계에서 입력 값도 바뀐다("800" → "8000000"). 변경이 크고 기계적이다.
- 따라서 표시 전환(만원 → 원)은 입력 전환과 별도 커밋으로 나누는 편이 리뷰하기 쉽다.

## 리스크

- **R1 (be R1 동의)**: 1단계가 새 키를 모르는 상태로 먼저 배포되면 조용한 손실이다. 결정이 나기 전에 065a94b 계열을 배포하지 않는다.
- **R2**: 원 입력으로 "800"을 800원으로 저장하는 오입력(위 입력 시트). 힌트로 줄이지만 막지는 못한다.
- **R3**: 1단계 시트가 금액이 있는 줄을 빈칸으로 연다. 안내 없이는 "금액이 사라졌다"로 보인다.

- **R5**: 허브 카드 단위 혼재(위 표시 형식).

## 조건 (A 채택 시)

1. 모든 우리 집 소비처가 원만 본다. 만원 읽기는 `quoteWonOf`·`planBudgetWonOf`·항목 예산 변환(`budgetNote`)·지급 표시 한 곳(rows 계층)으로 모은다. 소비처에서 `amount`·`budget`·`WON_PER_MANWON`을 직접 쓰지 않는지 grep한다.
2. `plannedTotal`·`budget`·`remaining`의 이름에 `Won`을 붙인다(타입이 놓친 소비처를 잡는다).
3. `AmountInput`은 `unit` 레지스트리를 받는다. 우리 집은 `won`, 나머지는 기본 `manwon`. 힌트는 원 → 억·만(`formatWonKorean`). 하한은 호출처가 정한다(견적 0, 총 예산 1). 오류 문구는 원용을 따로 둔다.
4. `PlanSettingsSheet`는 바뀐 칸만 보낸다. 이름만 고친 저장이 예산 키를 보내지 않는 테스트를 둔다.
5. 1단계 시트가 원 단위 견적(만원으로 나누어떨어지지 않는 것, 0)을 빈칸으로 열 때 안내 문구를 보인다. 이 코드는 2단계 태스크에서 삭제한다.
6. 표시 전환과 입력 전환을 별도 커밋으로 나누고, 다른 fe의 `LineRow`·`ItemSheet`·테스트 변경이 머지된 뒤에 시작한다.

## 결정 필요 (fe 의견)

1. 범위: A. A-1은 "입력 단위가 시트마다 다르다"가 사용자 요청("입력·표시 원")을 못 채운다.
2. 표시 형식: 목록·요약·허브·표 모두 "1,234,500원", 입력 힌트만 "1억 2,345만 6,000원". 허브의 계산기 카드와의 혼재는 pm이 확인한다.
3. `MAX_WON`: 13자리 추천에 동의한다(옛 최대값 포함). 입력 힌트가 있으면 13자리도 읽을 수 있다.

## 확인한 사실과 추론

- 확인(코드): `AmountInput`이 만원 전용(`AmountInput.tsx` 안의 단위·힌트·검증), `PlanSettingsSheet`의 이름·예산 각각 비교와 항상 `budget`을 보내는 것(`:75, :96-100`), `InteriorPlanPatch`의 선택 키, 표·내보내기의 `toWon`/`formatWon` 중복, `formatManwon` 소비처 위치, 테스트의 만원 문구 분포.
- 확인(기록): 8e30cdd가 `parseQuote`에서 견적 0을 허용했다(서버 쪽 `isInteriorQuoteAmount`). 제안 R4는 "0 허용 코드가 아직 없다"고 썼는데 그 사이 들어갔다. 클라이언트 `validateAmount`는 여전히 0을 거부한다(`AMOUNT_ERROR_MESSAGES.notPositive`). A로 가면 `amount`의 0 허용은 안 쓰이게 되지만 이미 머지된 코드와 ADR 개정 문구는 정리해야 한다(`amountWon` 0으로 옮김).
- 추론(실행하지 않음): 모바일 폭에서 12자리 원 금액의 줄 표시, 힌트의 소액 안내가 오입력을 얼마나 줄이는지, 플로팅 버튼 파일 위치, 다른 fe의 실제 변경 범위.
