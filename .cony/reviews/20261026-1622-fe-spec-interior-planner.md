날짜: 2026-10-26 · 검토만 함(코드·스펙 변경 없음). 읽은 것: 스펙 전체, `TabNav.tsx`, `AppRoutes.tsx`, `parseRoute.ts`, `useHashRoute.ts`, `useAccountImport.ts`, `useBudgetSource.ts`, `useListingOrderSource.ts`, `useListingSource.ts`, `useLeaveHousehold.ts`, `markDeviceImportsDone.ts`, `ListingCard.tsx/.module.css`, `MaskedValue.tsx`, `useListingsScrollRestoration.ts`, qa catchup 검토. 화면은 실행해 보지 않았다(코드 읽기 기준).

## 판정: 조건부 찬성

방향(탭 + 항목 단위 저장 + 태스크 0 선행)은 맞다. 아래 "고쳐야 할 것" 6개를 스펙에 반영하면 구현에 들어갈 수 있다. 나머지는 구현 중 판단할 권고다.

## 근거 (확인한 사실)

1. 매물 카드 버튼 줄에 [인테리어 계획]을 더하면 360px에서 안 들어간다. `ListingCard.module.css`의 `.actions`는 `flex: 1 1 0` + `white-space: nowrap` 버튼 5개(수정·복사·메모·공유·삭제)가 한 줄이다. 카드 안쪽 폭 약 328px에서 6개면 버튼당 약 48px인데 "인테리어 계획"(7자)은 한 칸에 안 맞는다.
2. 이전 기록 키 `interior-plan-imports`가 userId 배열이라 "한 번 옮기면 끝"이다. 매물은 `account-imports`가 **id를 기록**해서 로그아웃 중 새로 만든 것도 다음 로그인에 올라간다. 플랜은 userId만 기록하면 (a) 로그인 뒤 로그아웃 상태에서 만든 새 플랜은 영영 안 올라가고, (b) 시나리오 7·AC-10의 "나간 뒤 B 계정으로 옮겨진다"가 `markDeviceImportsDone`이 userId를 미리 기록하는 순간 깨진다(수락 때 플랜 기록을 완료로 표시하라고 쓴 부분).
3. 태스크 0의 이전 상태는 `userId`가 같으면 다시 안 돈다. `useAccountImport`의 effect(`state?.userId === userId`이면 return), `useBudgetSource`·`useListingOrderSource`의 `importState?.userId === userId` 가드가 같은 모양이다. "건너뜀"을 기존 `done`으로 두면 나간 뒤 한 번 실행이 일어나지 않는다.

## 고쳐야 할 것 (조건)

1. **태스크 0: "건너뜀"을 별도 상태로.** 세 훅 모두 `skipped`(가구 중) 상태를 두고, effect가 `skipped && household === null`이면 다시 `run`하게 한다. `isAccountImportSettled`는 skipped도 참. `AccountImportResult`에 `skipped` 사유 `"household"`를 더하면 타입이 이미 있는 `skipped` 분기(corrupt·unavailable)를 재사용한다. 유닛 테스트에 "같은 userId에서 household가 non-null → null로 바뀌면 `send` 1회"를 꼭 넣는다(이게 빠지면 변이 확인에서 안 잡힌다).
   - 예산·순서는 서버가 COALESCE라 올려도 덮이지 않는다. 그래도 스펙대로 건너뛰되, `skipped`일 때 `accountBudget`/`accountOrder` 조회는 켠다(`isImportDone`에 skipped 포함). 안 그러면 가구 중에 예산 줄이 loading에 멈춘다.
   - 예산·순서 이전 상태는 Listings 화면 컴포넌트 안에 있고, 매물 이전은 AppRoutes 위에 있다. "나가면 한 번 실행"의 시점이 화면마다 다르다(Listings가 마운트돼 있을 때만 예산·순서가 돈다). 나가기는 Listings의 가구 시트에서만 하므로 문제는 없지만 AC-10 테스트는 이 차이를 알고 써야 한다.
   - 나간 뒤 `account-imports`에 다른 계정 기록이 있으면 기존 로직상 "내 계정으로 옮길까요?" `window.confirm`이 곧바로 뜬다. 스펙 "다른 계정 확인창도 띄우지 않는다"는 가구 중에만 해당하고, 나간 직후에는 뜰 수 있음을 AC-10 기대값에 적는다.
2. **플랜 이전 기록은 id 단위로.** `interior-plan-imports`를 `account-imports`와 같은 `Record<userId, planId[]>`(`userIdRecordStorage` 재사용)로 바꾼다. 수락 때 기록 완료 표시도 그 시점의 기기 플랜 id만 넣는다(매물과 같은 동작). 그래야 가구 중 로그아웃 상태에서 만든 플랜이 나간 뒤 올라간다.
3. **useLeaveHousehold·useAcceptHouseholdInvite의 무효화 목록에 `interiorPlanListQueryKey()` 추가.** 지금은 listing·budget·order만 무효화한다. 플랜 쿼리를 캐시에 가진 채 수락·나가기를 하면 한동안 옛 범위의 플랜이 보인다. 스펙 파일 소유 목록에 두 훅이 없다.
4. **카드 진입은 버튼 줄에 넣지 않는다.** 선택지: (a) 펼친 카드의 버튼 줄 아래 별도 한 줄 링크(전체 폭 "인테리어 계획 →"), (b) 줄 안에서 "인테리어"(4자)로 줄이고 `flex` 비율 조정. 추천 (a). 둘 다 360px·최대 글자 크기에서 확인한다. 상태가 후보·보류·비후보뿐이라 "계약한 매물만" 조건은 걸 수 없고 모든 카드에 보인다(D2/D3 참고).
5. **카드가 플랜 목록을 가져오지 않게.** "연결 플랜이 있으면 `#/home/{planId}`, 없으면 `#/home?listing=`"을 카드에서 판단하려면 저장 목록 화면이 플랜 GET(최악 2MB)을 항상 불러야 한다. 인테리어를 안 쓰는 사용자도 해당된다. 카드는 항상 `#/home?listing={id}`로 보내고, Home이 연결된 플랜을 찾으면 `#/home/{planId}`로 `replace`하게 한다. 이러면 카드 쪽 변경은 링크 하나다.
6. **같은 항목을 둘이 고칠 때의 조용한 덮어쓰기 완화.** 장면: 남편과 아내가 같은 항목(예: 도배)에 각자 통화한 업체 견적을 넣는다. 가장 흔한 동시 편집이 바로 견적 줄 추가인데 D1-C는 이걸 항목 안에서 덮는다(스펙이 인정한 한계). 최소 완화: 시트가 열려 있는 동안 폴링으로 같은 항목의 `updatedAt`이 시트를 연 시점 값과 달라지면 시트 위에 "다른 사람이 이 항목을 고쳤습니다 [최신 값으로 다시 열기]"를 보이고, 저장 직전에도 같은 비교를 한다(서버 변경 없음, 클라이언트 비교). 서버에서 `updatedAt` 불일치를 409로 막는 방식이 더 확실하지만 API 계약 변경이라 be·pm 판단이다.

## 화면 흐름·사용성 (권고)

- **항목 시트(360px)**: 공간·공종·예산·견적 5줄×4칸·지급 5줄×4칸·상태·날짜 2·메모를 한 시트에 두면 키보드 위로 40칸 가까이 스크롤한다. 구성 제안: 위에서부터 공간·공종·예산 → 견적(줄은 업체·금액 한 줄, 연락처·메모는 줄 탭 시 펼침) → 지급 → 상태·날짜·메모는 접기. 견적/지급이 비어 있으면 줄 0개로 시작하고 [견적 추가]로 늘린다. 저장 비활성(고친 것 없음), 닫기·뒤로 가기 때 고친 게 있으면 `window.confirm`(시트가 뒤로 가기로 닫히므로 `useOpenSheet` 닫기 경로에서 확인해야 한다), 저장 중 중복 탭 방지, 첫 오류 칸 포커스는 체크리스트대로.
- **반복 작업 두 가지는 시트 없이**: (1) 지급 예정 줄의 [지급함] 버튼(할 일 목록 행에서 바로 그 지급 줄만 토글해 항목 PUT) — 매일 쓰는 동작이 "항목 탭 → 스크롤 → 체크 → 저장"이면 안 쓴다. (2) 첫 입력 때 항목을 수십 개 만든다: 그룹(공간) 머리의 [+ 이 공간에 추가]가 공간을 미리 채우고, 저장 후 시트를 닫지 않고 같은 공간으로 다음 항목을 받는 [저장하고 하나 더]. 이 둘이 없으면 AC 수치는 맞아도 쓰기 불편하다. (3)과 (4)는 스펙의 "범위 안" 작업량이라 새 기능이 아니다.
- **[항목 추가] 위치**: 목록 맨 아래에 두면 항목 수에 따라 흔들린다(체크리스트). 그룹 머리 [+]와 상단 줄(요약 아래)로 옮기고, 100개 비활성 안내는 버튼 옆 문구로 둔다.
- **확정**: 라디오는 확정 취소가 안 된다 → [확정 취소] 필요. 확정한 견적 줄을 삭제하면 `confirmedQuoteId`를 같이 지워야 검증(`confirmedQuoteId`가 견적에 없음 → 400)에 안 걸린다. 확정 시 상태 자동 상승(A3)은 "계획·견적 중일 때만"이므로 확정 해제 시 상태를 되돌릴지도 정해야 한다(되돌리지 않는 쪽이 단순). 견적을 처음 추가하면 상태 계획 → 견적 중으로 올리는 것도 같은 규칙에 얹을 수 있다.
- **요약 6칸**: "남은 예산"을 가장 크게, "앞으로 낼 돈"을 두 번째로, 나머지(총 예산·예상 총액·확정·지급함)는 한 줄 보조 행으로. 6칸 동일 크기는 360px 첫 화면에서 목록을 화면 밖으로 민다. 최대 글자 크기에서 줄바꿈되는지 확인한다. 할 일은 3줄까지 + [더 보기].
- **"앞으로 낼 돈 = 확정 − 지급함"의 정의 구멍**: A4가 확정 안 된 항목의 지급 줄을 허용한다. 그러면 지급함이 확정 합계 밖의 돈을 포함해 앞으로 낼 돈이 줄거나 음수가 된다. 항목별로 `max(확정 − 그 항목 지급함, 0)`을 합하거나, 정의를 "확정 항목의 지급함만 뺀다"로 못 박고 `summarizeInteriorPlan` 테스트에 넣는다(P에는 이 케이스가 없다).
- **예산 초과 표시**: 미확정 항목에 견적이 예산보다 비싸도(P의 ② 타일 650 > 600) 예상 총액엔 예산이 쓰여 낮게 잡힌다. 의도(U6)라면 항목 줄에 "견적 650 > 예산 600" 정도의 작은 표시가 있어야 요약만 보고 안심하지 않는다.
- **[공간별|공종별] 선택은 URL 쿼리에**: 스펙 "주소와 메모리로 유지"라고 쓰고도 주소 형태는 `#/home/{planId}`뿐이다. 체크리스트상 보기 상태는 쿼리(`?view=trade`)여야 하고, `parseRoute`가 허용 쿼리 밖을 지우므로 라우트 타입에 `view`를 포함하고 잘못된 값은 공간별로 맞춘다.
- **상태 처리 빈틈**: 플랜은 있고 항목이 0개인 상태의 빈 화면(공종 칩으로 시작하는 안내)이 스펙에 없다. "연결된 매물이 삭제되었습니다"는 매물 출처가 loading·error일 때 보이면 거짓이므로 매물이 확정 로드된 뒤에만 판단한다. 저장 실패(네트워크)와 404(함께 쓰는 사람이 삭제)는 입력 유지 + 시트 안 오류.
- **가리기**: 금액·연락처·메모만이 아니라 업체명·플랜 이름도 같은 수준으로 가릴지 정한다(카드는 이름을 가리지 않으므로 이름은 보임이 일관). 가리기 중 항목 시트를 열면 입력칸에 값이 드러나는 것이 문제 — 메모 편집이 가리기 중 어떻게 동작하는지(`MemoEditor`/`ListingCard`)를 따른다. `MaskedValue`가 `containers/Mortgage/Listings/components/`에 있어 Home이 import하면 container 간 직접 import(금지)다. 이번에 `src/components/`로 승격해야 한다(사용처 2곳이 실제로 생기는 시점이라 승격 근거가 있음). 파일 소유 목록에 없다.
- **라우팅·뒤로 가기**: `#/home?listing=` → 시트를 열고 주소에서 지우는 것은 `replace`로 해야 뒤로 가기가 카드로 돌아간다. 카드 → Home → 뒤로 가기에서 목록 스크롤 복원(`savedScrollY`)이 기존엔 "카드 → 계산"에서만 되는 구조(`useListingsScrollRestoration`은 언마운트 때 저장하므로 Home으로 가도 저장은 됨)이니 실제로 복원되는지 확인할 항목에 넣는다. 탭 이동은 기존대로 `replace`. `parseRoute`의 `planId`·`listing` 값은 정규식(`^[A-Za-z0-9_-]{1,64}$`) 밖이면 `#/home`으로 맞춘다.
- **탭 3개**: `TabNav.module.css`는 `.item { flex: 1 }`이라 3탭이면 폭 약 105px. "저장 목록"은 들어간다. 최대 글자 크기에서 확인. `TABS`는 `Record<TabName, …>`라 `TabName`에 `home`을 더하면 등록 누락이 타입에서 걸리지만 `TAB_ORDER` 배열은 걸리지 않으니 순서 배열 길이를 테스트하거나 순서를 `TABS`에서 파생한다.

## 로컬 스토어·출처 훅

- 로컬 스토어는 메모리 스냅샷이 아니라 쓰기 직전에 저장소를 다시 읽어 항목만 바꾸고 쓴다(탭 둘이 로그아웃 상태로 열려 있을 때 한쪽이 다른 쪽 플랜을 통째로 덮는 것을 막는다). 키 하나에 플랜 전체를 저장하므로 쓰기 실패(용량)는 스펙대로 기존 키를 건드리지 않고 알린다.
- 출처 훅: `useListingSource`의 `selectSourceStatus`는 매물 이전이 settled여야 `loggedIn`이다. 플랜 출처도 같은 `accountImport` 상태와 **플랜 이전 상태**가 모두 settled일 때 loggedIn이어야 빈 서버 목록 깜빡임이 없다. 가구 중에는 플랜 이전이 skipped로 settled.
- 항목 PUT·POST 응답(항목 하나)은 `setQueryData`로 캐시의 해당 항목만 바꾼다. 매 저장마다 최대 2MB GET을 다시 받지 않는다. 쿼리 키는 함수형(`interiorPlanListQueryKey`)으로, 가구가 아니면 `refetchInterval: false`(AC-7).
- 이전 대상 플랜의 `listingId`가 가리키는 매물을 사용자가 "옮기지 않기"(다른 계정 확인창)로 제외하면 계정에 매물이 없어 연결이 끊긴 것처럼 보인다(A8과 같은 문구가 거짓이 됨). 드문 경우지만 알아 둔다.
- 플랜 3개 상한에 걸려 import가 400이면 실패 안내만 있고 사용자가 할 수 있는 일이 없다(로컬 플랜을 못 올림). 실패 문구에 "계정에 이미 3개 있음"을 명시하고 [다시 시도]는 숨긴다.

## 태스크 0 구현 위험 요약

1. 재실행 트리거 없음(근거 3) — 가장 큰 위험. 변이 확인에서 "조건 삭제"만 보지 말고 "null로 바뀐 뒤 재실행 코드 삭제"도 확인한다.
2. `me.data`가 undefined인 동안 시작하지 않는 건 이미 `userId === null`로 보장됨. 가구 여부는 같은 `me`에서 읽어야 한다(`householdOf(me.data)`). 훅에서 `useMe()`를 한 번 더 부르면 쿼리는 같지만 `userId`와 `household`가 같은 렌더에서 일관되게 읽힌다.
3. 이전이 `running`인 도중 가구로 바뀌는 경우(수락 직후)는 `markDeviceImportsDone`이 먼저 기록하므로 현재 흐름과 같다. 새로 생기는 경합은 아니다.
4. 이 수정은 서버 변경이 없고 사용자 데이터 노출 결함을 막으므로 스펙대로 단독 PR 선배포에 찬성한다.

## 기존 화면 회귀 (AC-0)

- `Route`·`TabName`·`parseRoute`·`toRoutePath`·`PATHS`를 한 번에 건드린다. 이전엔 `#/home…`이 계산으로 맞춰졌고, 이후엔 home이 된다. `AppRoutes.test.tsx`와 `parseRoute.test.ts`의 탭 개수·접근성 이름 단언이 깨질 수 있으니 같은 PR에서 갱신하고, "알 수 없는 해시는 계산", `#/listings?login=` 처리, `share`/`invite` 토큰 대소문자는 그대로임을 테스트로 고정한다.
- 스토어 생성(`createStores`)에 키 2개를 더하는 것은 안전하다. 읽기 경로에서 기존 13개 키 `setItem`/`removeItem` 0회는 스파이 Storage 단언이 좋다.
- 로그인 복귀(`#/listings?login=`)는 계속 저장 목록이라, Home에서 시작한 사용자는 로그인 뒤 목록 화면으로 간다. Home에 로그인 진입점이 필요 없다는 전제이므로 Home 로그아웃 상태 빈 화면에 "계정에 저장하려면 저장 목록에서 로그인" 안내 한 줄이 있으면 좋다(없어도 막히지는 않음).
