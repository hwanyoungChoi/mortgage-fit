## 근거

1. **예시 값은 모두 맞고, 잘못된 구현을 가른다.** 아래 검산표 참고. 특히 R7(미확정 미정)이 "미정을 전부 센 구현"(2건)과 "확정한 미정만 센 구현"(1건)을 가르고, "R1 비우면 미정 2건"은 "비우면 확정도 풀리는 구현"(1건)과 가른다.
2. **AC 대부분이 `toStrictEqual`·CSV 9행처럼 판정 가능한 문장이다.** AC-0(c)의 "키 삭제, `amount: undefined` 남기면 실패"가 핵심이고 interior-simple의 c1·c2 틀을 그대로 쓴다.
3. **빠진 곳은 있지만 전부 AC 한 줄씩 더하면 되는 크기다.** 가장 큰 구멍은 (i) 표의 "빈 줄(견적 없음)"과 "미정"을 구분하는 단언이 없고, (ii) 1단계에서 미정 줄 시트를 열었을 때의 동작(AC가 아니라 태스크 문장에만 있음)이며, (iii) 옛 번들 위험을 재는 방법이 "수동 확인" 한 줄뿐이라는 점이다.

- **지출 0 + 미정만**: 확정이 R6 하나뿐인 계획 → "지출 예정 0만원 · 금액 미정 1건 제외", 허브 "지출 예정 0만원 · 미정 1건". 미정을 "지출 예정 없음"으로 숨기는 구현을 가른다.
- **옛 다견적 항목 안의 미정 견적**(요청하신 경계). makeFullItem 변형 F⁺: q1 하루바스 370✓, q2 욕실나라 금액 없음. 기대:
  - 줄 2개, q2 줄에 "미정". 지출 예정 370, 미정 0건(q2는 미확정).
  - q2를 확정하면 확정이 q2로 옮겨 가서(D2 a) 지출 예정 0, 미정 1건, "다른 견적 확정이 풀린다" 안내가 여전히 뜬다.
  - 확정된 q2(미정)를 n≥2 항목에서 삭제 → `confirmedQuoteId` 키 빠짐, q1·지급·연락처 그대로, 미정 0건.
  - q1 금액 수정 시 q2는 `amount` 키 없는 채 `toStrictEqual`(스펙에 있음).
- **빈 줄 vs 미정**: L의 Y(견적 0개, "예산 2,000,000원" 비고)와 P⁺의 R7(견적 1개, 금액 없음)을 같은 계획에 두면 표에서 Y의 견적 칸은 **빈칸**, R7은 **"미정"**이어야 한다. 지금 `buildInteriorPlanTable.ts`는 `quoteWon: number | undefined`("견적 없는 줄은 undefined")라서, 미정을 그냥 `undefined`로 두면 둘이 같아진다(표 모델에 구분을 더해야 하는 지점). 스펙 AC에 이 쌍이 없다.
- **0 오표시 방지**: 미정 줄 어디에도 "0만원"·"0원"·`0`이 나오면 안 된다. `quote.amount ?? 0` 같은 폴백이 화면까지 새는 것을 막는 단언(목록 R6/R7 줄, 표 R6/R7 셀, CSV 두 셀).
- **빈 문자열 변환 버그**: 1단계에서 미정 줄 시트를 열면 견적 칸 값이 `""`이어야 한다(`String(undefined)`는 "undefined", `Number("")`는 0이다). AC에 없다.

## 조건 (스펙에 넣을 것)

### C1. AC-1~3에 빠진 경계를 더한다

위 "고칠 값"을 AC-1에 넣는다. 최소: 총 예산 700 + 미정, 확정 미정만 있는 계획(지출 0), F⁺ 3종, "미정 줄에 0·'0원' 없음", R7 체크 시 지출 800 유지, R6 채움 시 남은 80, R1 비움 시 남은 380.

### C2. 1단계 시트 동작을 AC로 만든다 (현재는 태스크 1-2의 한 문장)

AC-2를 "1단계"와 "2단계"로 나눈다.

- 1단계(AC-2-S1): P⁺에서 R6 시트를 열면 견적 칸 `value === ""`(0·"undefined"·"NaN" 아님). 금액 없이 저장하면 필수 오류, 쓰기 0회. 120을 넣어 저장하면 `amount: 120` 추가, 나머지 키 그대로, 지출 920.
- 열었다 닫기만 하면 `interior-plans` 원문 `===`, 쓰기 0회 (AC-0(b)에 이미 있음, 시트 열기 대상에 R6를 명시).
- 2단계(AC-2): 현재 문장 그대로.

### C3. "문구는 한 번만 보인다"의 범위를 정한다

`PlanSummary`는 목록 보기와 표 보기 둘 다에서 화면 위에 있다(`PlanScreen.tsx:101`). 표 보기에는 표 머리와 "계" 비고에도 같은 문구가 나오므로 한 화면에 3번이다. 판정 가능한 문장으로: "요약 영역(`aria-label="요약"`) 안에 '금액 미정 n건 제외'가 정확히 한 번". 표 보기는 영역별로 각각 한 번(요약 1, 표 머리 1, 계 1). 테스트는 `within(요약)`과 정확한 문자열을 쓰고 정규식 부분 일치는 쓰지 않는다("미정"은 "미확정"에 안 들어 있지만 "금액 미정 n건 제외"와 "미정"이 겹치므로).

### C4. 가리기 AC를 모든 노출 지점으로 넓힌다

- 현재 AC-4는 `innerHTML`에 "미정"·"800만원"·"거실 매입등"이 없다는 한 줄이다. 목록 보기와 표 보기 둘 다에서 확인한다(표 보기에서는 CSV·인쇄가 비활성).
- 가리기 중에도 체크박스 접근 가능한 이름은 구분·업체·(가리면 세부내용 제외)다. 미정이라는 단어가 `aria-label`로 새지 않아야 한다.
- "미정 1건"을 요약·표 머리·계 비고·허브 네 곳에서 따로 센다(MaskedValue 밖에 렌더하는 버그가 한 곳씩 따로 생긴다).
- 가리기를 껐다 켜도 `interior-plans` 원문 `===`.

### C5. AC-0 보강

- (d) 가구 모드(`server/household/householdInteriorPlans.d1.test.ts` 틀)에서도 P⁺ POST·PUT·GET이 `toStrictEqual`이어야 한다. 현재 (d)는 로컬 저장소와 D1 하네스만 쓴다.
- (a) 서버 400 단언을 AC로 올린다: 본문 규칙 한 줄 변경이므로 `POST items`·`PUT items/{id}`·`POST plans`·`/import`에서 `amount`가 `null`·0·`"100"`·1.5·1,000,000,000이면 400이고 오류 모양이 변경 전과 같다. 999,999,999와 1은 통과(경계 안쪽).
- (a) 클라이언트 응답 파서: 서버가 미정 견적이 든 GET·POST·PUT 응답을 돌려줄 때 `useInteriorPlanList`·`useCreateInteriorItem`·`useUpdateInteriorItem` 등이 `loadFailed`로 떨어지지 않는다(AppRoutes 로그인 테스트 한 개, fetch 모킹). A3 마지막 줄의 조회 실패 경로가 새 번들에서는 없다는 증명이다.
- (b) 로그아웃·로그인 혼자·가구 세 모드 외에 **탭 간 `storage` 이벤트**를 하나 더한다: P⁺ 원문을 다른 탭이 쓴 것처럼 `storage` 이벤트로 흘려 보내면 새 번들은 목록을 정상으로 갱신하고 `corrupt`가 되지 않는다.
- (g) 일부러 넣을 버그를 3개에서 6개로: 기존 3개에 더해 (4) 미정 건수에 미확정 줄까지 센다(R7), (5) "미정"을 `MaskedValue` 밖에 렌더한다, (6) 표에서 빈 줄과 미정을 구분하지 않는다(`undefined` 하나로 합친다). 각각 실패하는 테스트 이름을 기록한다.

### C6. 순수 함수로 뺀다 (테스트하기 쉬운 구조)

컴포넌트에 판단을 묻지 않는다. 다음 계산은 `src/lib/utils/`의 순수 함수에서 한 번만 하고, 목록·요약·표·CSV·허브가 그 결과를 쓴다(스펙의 "홈이 따로 계산하지 않는다" 규칙의 연장).

- `buildInteriorPlanRows`가 `plannedTotal`과 함께 `tbdCount`(확정이고 금액 없는 줄 수)를 돌려준다. `summarizeInteriorPlan`·`summarizeHub`의 `HubPlanLine`에 `tbdCount`가 전달된다.
- 표 모델에 "견적 없음 / 미정 / 금액"을 구분하는 값(예: 문자열 합집합이 아니라 판별 유니온)을 둔다. `number | undefined` 하나에 두 뜻을 싣지 않는다.
- 계 비고·표 머리의 문구는 `tbdCount`를 받는 작은 함수 하나에서 만든다(n=0이면 빈 문자열). 경계 표: n=0·1·2·10.

### C7. 타입이 안전망이다

`InteriorQuote.amount?`로 바꾸면 `LineRow`·`buildInteriorPlanTable`·`interiorPlanRows`·`interiorLineDraft`·`ItemSheet`의 `quote.amount` 사용처가 `tsc` 오류가 된다(스펙 의존 관계에 있음). 이 오류를 `?? 0`이나 `!`로 덮지 않는다는 규칙을 스펙에 쓴다. 테스트는 C1의 "0 오표시 없음"으로 지킨다. 1-2의 완료 기준에 `pnpm build`(worker 타입 검사 포함)를 넣는다.

### C8. 문구·기본값 의존

U4·U5·U6이 사용자 확인 전이다. 테스트 리터럴은 스펙 AC의 문자열을 그대로 쓰고 상수에서 가져오지 않는다(바꾸면 테스트도 같이 바뀌어야 한다). 사용자가 U4(CSV 빈칸)로 바꾸면 AC-3의 CSV 3줄(R6, R7, 계)만 바뀌므로, 스펙에 그 영향 범위를 한 줄로 적는다.

## 옛 번들 탭 위험: 재현·고정 방법

**실제로 재현된다.** 이 검토에서 현재 파서(= 1단계 이전 코드)를 별도로 번들해 같은 계획에 견적만 바꿔 읽혔다(스크래치 스크립트, 저장소 밖: `/private/tmp/claude-501/-Users-hwanyoungchoi-cony-sandbox-loan-calculator/c43f2613-2353-4c04-a3f5-099935e7042e/scratchpad/probe/run.ts`).

| 견적                            | `parseInteriorPlans` 결과 |
| ------------------------------- | ------------------------- |
| `{id, vendor}` (amount 키 없음) | **corrupt**               |
| `amount: 120`                   | ok                        |
| `amount: null`                  | corrupt                   |
| `amount: 0`                     | corrupt                   |

즉 A3의 첫 단계(옛 번들이 키 없는 견적을 만나면 전체 corrupt)는 코드 그대로다. 스펙의 나머지 단계(`storage` 이벤트 재읽기, [계획 초기화]의 확인 창)는 문서와 코드 위치 인용을 보고 판단했고, 이번에 화면에서 돌려 보지는 않았다.

고정 방법 (영구 테스트가 아니라 배포 전 절차 + 가벼운 영구 가드 둘):

1. **영구 테스트로 옛 코드를 복사해 두지 않는다.** 옛 파서 사본은 시간이 지나면 현재 코드와 어긋나고, CLAUDE.md가 금지하는 호환 레이어와 닮는다.
2. **배포 전 절차(1단계 완료 때 한 번, 결과를 기록)**: `git worktree add ../old <1단계 직전 커밋>`에서 위 스크립트처럼 `parseInteriorPlans`를 번들하고, 1단계 브랜치가 만든 P⁺ JSON(`JSON.stringify(plans)`)을 먹여 `corrupt`임을 확인한다. 이 기록이 "옛 탭은 정말 손상 판정을 받는다"는 근거이고, 2단계에서 같은 스크립트를 **1단계 커밋의 파서**로 돌려 `ok`임을 확인한다(1단계 탭이 2단계 데이터를 읽는지의 자동 근사).
3. **영구 가드(자동)**: 태스크 2의 diff에서 `src/lib/utils/validateInteriorPlan.ts`·`src/lib/types/interiorPlan.ts`·`server/**`의 변경이 0줄이어야 한다. 2단계가 읽기 규칙을 건드리지 않으므로, 1단계 탭이 2단계 데이터를 읽는다는 보장이 이 한 줄로 성립한다. PR 체크리스트에 `git diff --stat 1단계커밋..HEAD -- <3경로>` 결과를 붙인다.
4. **수동 확인(1-3의 "두 탭" 항목)**은 그대로 두되 기대 결과를 쓴다: 1단계 빌드 탭이 열려 있는 상태에서 2단계 브랜치 탭이 미정을 저장하면 1단계 탭은 `storage` 이벤트 뒤 정상 목록(해당 줄은 "미정")을 보인다.
5. **영구 테스트로 고정할 수 있는 것**: 새 `parseInteriorPlans`의 tolerant-reader 계약(키 없음 ok, `null`/0/문자열/소수/상한 초과 corrupt). 이것이 AC-0(a)의 새 단언이다. 옛 번들 거동 자체는 영구 테스트 대상이 아니다.

AC-0(e)(24시간 대기)은 **자동 테스트로 판정할 수 없는 절차 게이트**다. `.cony/log.md`의 두 시각 차이를 눈으로 확인하는 항목이라고 AC에 명시하고, 태스크 2의 qa 기록에 두 시각과 diff 가드 결과를 적는다. main에 필수 체크가 없으므로(메모리) 머지를 기계가 막아 주지 못한다는 점도 적는다.

## D1 의견 (테스트 가능성)

- **A**: 테스트는 가장 쉽다(배포 1번, 매트릭스 없음). 그러나 옛 탭 위험은 테스트로 아무것도 못 막는다. 반대하지 않지만, 손실 경로가 데이터 파괴(초기화)라 찬성도 안 한다.
- **B**: 테스트는 사실상 변경 없음이지만 시나리오 1·2를 못 충족한다. 사용자 목표와 어긋나므로 반대.
- **C(추천): 찬성.** 근거는 두 가지다.
  1. 1단계만으로 "모든 읽기·표시·보존 경로"를 P⁺ fixture로 테스트할 수 있고, 2단계는 시트 한 곳(draft·editedQuote)으로 범위가 좁아 AC-2가 작아진다. 각 단계의 AC 경계가 깨끗하다.
  2. 2단계가 읽기 규칙을 건드리지 않는다는 diff 가드(위 3)로 "1단계 탭이 2단계 데이터를 읽는다"를 기계적으로 보일 수 있다. A에는 이런 근사 장치가 없다.
- C의 약점(리스크로 기록): (i) 24시간 대기 안에 1단계 이전 탭이 남아 있을 확률은 접속 통계가 없어 증명 못 한다(A4). (ii) 1단계에서는 미정을 만드는 화면이 없으므로 **1단계의 실제 사용자 검증이 없다**. 미정 줄을 볼 방법은 이미 쓴 시드·import뿐이라 1단계 qa는 fixture 기반이다. 2단계 qa가 화면 흐름을 처음 검증한다. (iii) 1단계 시트가 미정 줄을 열면 견적 칸이 빈칸인데 저장하려면 금액이 필요하다. 1단계 동안 이 상태가 사용자에게 보일 수 있으므로 오류 문구가 "견적을 입력하세요"로 읽히는지 확인하고, 이 임시 동작은 2단계에서 없어진다.

## 리스크

1. 옛 번들 탭 손상 판정(위): 데이터 손실 경로가 [계획 초기화]의 확인 창 하나에 의존한다. `CorruptPlansNotice`가 "원문을 복사해 보관한 뒤 초기화"를 이미 안내하므로(코드 확인) 완화돼 있지만 자동 테스트로 막을 수 없다.
2. 표의 빈 줄/미정 혼동(C6)과 `?? 0` 폴백으로 미정이 0원처럼 새는 것: 합계가 맞아 보여서 합계 테스트만으로는 못 잡는다. 셀·문구 단언이 필요하다.
3. "문구 한 번" 같은 화면 단언은 보기별 중복(C3) 때문에 getByText가 다중 일치 오류를 내거나, 반대로 일치가 많아 보이는 단언이 의미 없어질 수 있다.
4. 표 머리의 "{오늘} 기준"은 날짜 의존이다. AC-3 테스트는 시계를 고정(fake timers)해야 한다.

## 자동 테스트로 못 하는 항목 (화면에서 직접 확인)

- "미정"의 흐린 글자색이 금액과 구분되고 대비가 충분한지(WCAG 4.5:1), 인쇄 미리보기에서 "미정"·"계" 비고가 잘리지 않는지.
- 저장 뒤 스크롤 위치 유지(jsdom은 스크롤을 못 잰다). 포커스가 첫 칸에 가는지는 `document.activeElement`로 자동 확인 가능.
- 옛 번들 탭과 새 번들 탭을 함께 띄운 두 탭 시나리오, 배우자 휴대폰의 열려 있는 옛 탭.
- 24시간 대기 게이트(절차).
