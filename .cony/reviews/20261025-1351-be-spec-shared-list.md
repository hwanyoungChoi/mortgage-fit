# 함께 쓰는 목록 스펙 — be 검토

2026-10-25 · 대상 `.cony/specs/shared-list.md` · 관점: 데이터 무결성 · 보안 · 성능 · API 계약

## 판정: 조건부 통과

D1 방향(추가만 하는 `households` + `users.household_id`)은 맞다. 다만 아래 필수 조건 6개를 스펙에 명시하고 구현해야 한다. 조건 1~3은 빠지면 데이터가 어긋난다.

## 확인한 사실 (직접 실행)

스크래치 DB에 `0002~0004`를 적용하고 `PRAGMA foreign_keys=ON` 상태로 확인했다(sqlite 3.51, D1과 같은 엔진 계열이지만 D1 원격에서 돌린 것은 아니다).

- `ALTER TABLE users ADD COLUMN household_id TEXT REFERENCES households (id)`는 FK를 켠 채로 통과한다. 기존 행은 모두 NULL이고 다른 컬럼은 그대로다. 스펙의 "REFERENCES를 빼는 대안"은 쓸 일이 없을 가능성이 높다. `--local`로 한 번 더 확인하면 된다.
- 쿼리 플랜: 지금 `WHERE user_id = ?`는 `sqlite_autoindex_listings_1 (user_id=?)`를 쓴다. 스펙의 범위 조각을 넣은 혼자 쓰는 경우도 같은 PK 인덱스를 쓴다(구성원 집합은 `users` PK와 `users_household_id` 인덱스로 구한다). PUT/PATCH/DELETE는 `(user_id=? AND id=?)` 인덱스 탐색이 유지된다. 혼자 쓰는 사용자의 반환 행과 순서(id 순)도 같다.
- 단일 `INSERT … SELECT … FROM json_each(…) WHERE NOT EXISTS(가구 범위에 같은 id) AND (가구 합계 + n ≤ 500) ON CONFLICT DO NOTHING`은 기대대로 동작한다. 상한 조건이 문장 시작 시점의 개수로 한 번만 계산돼 전부 넣거나 전부 안 넣는다. 다른 구성원이 가진 id는 건너뛴다.
- `UPDATE listings SET id = lower(hex(randomblob(16))) WHERE user_id = ?`는 행마다 다른 값을 만든다(32자).
- 클라이언트 `useAccountImport.ts`는 로컬 목록을 읽기만 하고 지우지 않는다. 기록은 계정별(`importedIds`)이라, 한 기기를 두 계정이 쓰면 같은 id가 두 계정에 들어가는 일이 실제로 생긴다. 스펙의 id 충돌 가정은 현실적이다.

추론: D1 batch는 한 트랜잭션이고 Durable Object 단일 스레드에서 도는 것으로 알고 있다(문서 확인은 못 했다). 그렇다면 batch 안의 조건 문장은 다른 요청과 끼어들지 않는다. 이 설계(배치 안 가드)는 그 전제 위에 있다.

## 필수 조건

1. **수락 batch의 "성공했을 때만" 가드를 `used_at = now`로 걸지 않는다.** D1 batch는 앞 문장이 0행을 바꿔도 뒤 문장을 계속 실행한다. 가드를 `used_at = ?now`(초 단위)로 걸면, 같은 초에 들어온 두 번째 수락도 첫 번째의 표시를 보고 가드를 통과한다. 인원 상한 조건이 막아 주긴 해도 우연에 기댄 보호다. 새 테이블이므로 `household_invites`에 `accepted_by TEXT REFERENCES users(id)`를 `0005`에 넣고, ①을 `UPDATE … SET used_at=?, accepted_by=? WHERE token_hash=? AND used_at IS NULL AND expires_at>?`로 하고, 뒤 문장은 모두 `EXISTS (… accepted_by = ?B)`로 가드한다. 상한(합계 500, 인원)·초대자 `household_id IS NULL`·B `household_id IS NULL`도 같은 가드에 넣는다. 사전 검사(자기 초대·409 종류)는 실패 뒤 오류 분류용으로만 쓴다. 성공 판정은 마지막 문장의 `meta.changes`(users 2행)로 한다. `households` 행은 앱에서 id를 만들어 바인딩해 UPDATE가 참조하게 한다.

2. **가구에서는 import·POST 상한을 느슨하게 두지 않는다.** 지금 import는 "SELECT로 센 뒤 INSERT, 경합으로 상한을 조금 넘는 것 허용"이다(`handleListings.ts` 주석). 혼자 쓸 때는 허용 가능하지만, 가구에서 500을 넘으면 `isListingOrder`의 500개 한도 때문에 순서 PUT이 계속 400이 되는 장애로 이어진다. 또 두 구성원이 같은 id를 동시에 import하면 `ON CONFLICT (user_id,id)`가 서로 못 막아 가구 안에 중복 id가 생긴다(PK에 user_id가 있기 때문). 위 확인대로 한 문장(`NOT EXISTS` 가구 범위 + 합계 조건)으로 바꿔 사전 SELECT를 없애면 원자적이다. POST는 이미 한 문장이라 범위만 바꾸면 된다. `existing` 카운트는 가구 범위로 센다.

3. **순서 병합에서 "있는 매물만" 남기고 500을 넘기지 않는다.** `A 순서 ++ (B 순서 − A 순서)`는 지워진 매물의 id까지 합쳐 최대 1000개가 될 수 있고, 저장된 값이 `isListingOrder` 한도를 넘는다. 합친 뒤 가구 매물에 실제 있는 id만 남겨 저장한다. SQL JSON으로 하기 번거로우면 Worker에서 계산해 batch에 바인딩하고, "A·B의 `listing_order`가 읽은 값 그대로일 때만" 가드를 단다(낙관적 비교). id를 새로 받은 B 매물은 순서에 없으므로 맨 위에 온다. 이것은 의도한 동작으로 스펙에 한 줄 적는다.

4. **로그인 콜백 쿠키 규칙 3개를 스펙에 못 박는다.** 열린 리다이렉트는 구조상 없다(Location이 `${origin}/#/invite/${token}`이고 토큰은 `^[A-Za-z0-9_-]{22}$`만). 다만 (a) 모양 검사는 로그인 시작이 아니라 **콜백에서 쿠키를 읽을 때 다시** 한다(쿠키는 클라이언트 값이고 `readCookie`는 검사하지 않는다). (b) `?invite=` 없이 시작한 로그인은 기존 `mf_oauth_invite`를 `Max-Age=0`으로 지운다. 그러지 않으면 초대 링크로 로그인을 시작하다 중단한 사용자가 10분 안에 보통 로그인을 하면 초대 화면으로 간다. (c) 취소·실패(`fail`)에서도 쿠키를 지운다(스펙은 성공 때만 적었다). 쿠키 Path는 state 쿠키와 같은 `/api/auth/kakao`.

5. **수락 화면 문구에 권한을 분명히 쓴다.** 초대는 "상대 목록을 구경"이 아니라 **내 목록 전체를 초대한 사람이 보고 고치고 지울 수 있게 되는** 동작이다. 악의적인 초대 링크를 받은 사용자가 눌러 버리면 데이터가 노출된다. 지금 문구는 "합쳐집니다"뿐이다. "초대한 사람이 내 저장 목록 전부를 보고 수정·삭제할 수 있습니다. 나가도 상대가 이미 본 내용은 되돌릴 수 없습니다"를 넣는다(fe 문구이지만 계약의 위험 고지이므로 be가 요구한다). 나가기 확인창에도 "함께 쓰는 동안 상대가 지운 매물은 돌아오지 않습니다"를 넣는다.

6. **초대 생성은 한 batch로 한다(1인 1초대).** "내 미사용 초대 삭제 → 만료 정리 → 새 행 INSERT"를 한 batch로, 이미 2명이면 INSERT가 안 되게 가드한다. 분리하면 동시 생성에서 미사용 초대가 둘 남는다. 새 테이블이므로 `CREATE UNIQUE INDEX household_invites_one_open ON household_invites (inviter_id) WHERE used_at IS NULL`을 같이 두면 DB가 보장한다(batch가 삭제를 먼저 하므로 정상 경로는 막히지 않는다). 수락 시에는 A·B 양쪽의 미사용 초대를 같은 batch에서 지운다(B가 만든 초대가 남아 가구 밖 사람이 끼어드는 경로 차단).

## 질문별 검토

### 마이그레이션 `0005`가 추가만인가 / AC-0

- 추가만이다: `CREATE TABLE` 2개, `ADD COLUMN`(NULL), `CREATE INDEX` 2개. 기존 행을 읽거나 쓰는 문장이 없다. `CREATE INDEX users_household_id`는 `users` 전체를 한 번 읽지만 값은 바꾸지 않는다.
- AC-0(a)의 4개 쿼리는 `household_id`를 선택 컬럼에 넣지 않아 직전·직후 `diff`가 빈다. 아래를 더하면 좋다: `PRAGMA table_info(users)`로 컬럼 순서(household_id가 맨 끝), `SELECT name FROM sqlite_master`로 새 객체 4개 확인.
- 확인 못 한 것: wrangler가 마이그레이션 파일을 한 트랜잭션으로 적용하는지(중간 실패 시 일부만 적용되는지). 다시 돌리면 "duplicate column"으로 막히므로 `--local`에서 먼저 돌리고, 원격 적용 전 `time-travel info`로 복원 지점을 적어 둔다는 3-1이 맞는 안전장치다.
- 롤백: 새 스키마에서 옛 Worker는 문제없다(옛 코드는 `household_id`를 읽지도 쓰지도 않는다. AC-8 확인 대상). 반대로 가구가 생긴 뒤 **새 Worker를 옛 버전으로 되돌리면** 옛 코드는 `users.budget/listing_order`만 보고 구성원 매물을 못 본다. 그 사이 옛 코드가 쓴 예산·순서는 나가기 때 가구 값으로 덮인다. 롤백은 "가구가 아직 없을 때만 안전"을 PR 설명에 적는다. 하향 마이그레이션은 만들지 않는다(삭제 금지 규칙).
- 배포 순서(마이그레이션 → 옛 Worker 확인 → PR)는 맞다. Workers Static Assets는 Worker와 한 번에 배포되므로 새 클라이언트와 옛 Worker가 섞이는 구간은 없다. 오래 열린 옛 탭 + 새 Worker는 `/api/me`의 추가 필드를 무시하면 되어 안전하다.

### 혼자 쓰는 사용자의 응답이 같은가

- 행 집합·순서 같음(플랜 확인). 서버가 정렬하지 않고 클라이언트가 정렬하므로 순서 차이가 있어도 화면은 같다. 그래도 바이트 동일을 약속했으므로 `listListings`에 `ORDER BY user_id, id`를 명시하는 것을 권한다(현재 암묵적인 인덱스 순서와 동일, 플래너가 바뀌어도 고정). `/api/me`만 `household:null`이 늘어난다(AC-0(b)에 이미 명시). 요약 표의 "바이트 단위로 같아야"는 me를 예외로 적어 두는 편이 정확하다.
- 범위 조각은 `household_id IS NOT NULL AND`가 없어도 된다(`= NULL`은 거짓). 한 함수(`householdScopeSql`)에만 두고 listings·budget·order·me가 같이 쓰게 한다. 같은 판단을 여러 곳에 두지 않는다는 원칙에도 맞다.

### id 충돌, PUT/PATCH/DELETE의 구성원 매물 찾기

- PK `(user_id,id)`는 가구 안 id 유일성을 보장하지 못하고, DB 수준에서 보장할 방법도 없다(가구 밖 두 사용자는 같은 id가 합법). 그래서 불변식은 문장 수준으로만 지킨다: 수락(이름 바꾸기, ③) · import(조건 2) · POST(서버가 만든 128비트 id라 충돌 가능성 무시 가능).
- 범위 조각의 `id = ?` 조건 UPDATE/DELETE는 불변식이 깨지면 두 행을 모두 바꾼다. 방어 코드를 더할 필요는 없고, 위 조건 1·2로 깨지지 않게 하는 쪽이 단순하다.
- ③의 부작용 두 가지: B가 계산 화면에서 자기 매물 X를 편집 중이었다면 수락 뒤 X가 A의 X를 가리켜 B의 덮어쓰기가 A의 매물을 덮는다(같은 id가 A 쪽으로 우선 해석되므로). 드문 경우지만 스펙에 "수락 성공 시 fe가 편집 중 상태(editingId)를 해제"를 한 줄 적는다. 또 한 기기에서 로그인한 B가 이미 A 쪽에서 지워진 X를 로컬에서 다시 이전하는 경우는 import가 "없는 id"로 보아 되살린다(계정별 `importedIds`는 계정 단위라 가구 단위 삭제를 모른다). 허용 가능한 한계로 기록한다.

### 수락·나가기 batch 원자성, 500 합계 경합

- 조건 1·2를 지키면 배치 안 가드로 원자적이다. 나가기는 인원과 무관하게 `WHERE household_id = ?hid`로 문장을 한정하면 두 사람이 동시에 나가도 한쪽은 0행이 되고 FK(`households` 삭제 전에 참조 제거)가 어긋나면 배치 전체가 실패한다. 순서: 값 복사 → `household_id = NULL` → 초대 삭제 → `households` 삭제는 스펙 그대로 맞다. 가구가 이미 없으면 404.
- 합계 500은 수락 가드(두 사람 매물 수 합)와 import·POST 한 문장에서 같은 경계를 쓴다. 상수를 `ACCOUNT_LISTINGS_MAX`와 `isListingOrder` 한도에서 하나로 맞춘다.

### 예산·순서 저장 위치

- 가구가 있으면 `households`, 없으면 `users`는 단순하고 맞다. `users.budget/listing_order`는 가구에 있는 동안 휴면 값이 되고 나가기 때 가구 값으로 덮인다. 따라서 B의 합치기 전 예산은 나가도 돌아오지 않는다(U2·U3과 일치, 제품 결정이므로 문구에 반영만).
- `budget`/`listing_order` 읽기·쓰기·import의 `COALESCE`가 대상 테이블만 다르다. 대상 선택(`users` vs `households`)도 범위 조각과 같은 파일에 두어 판단을 한 곳에 둔다. 가구 UPDATE는 `WHERE id = (SELECT household_id FROM users WHERE id = ?)`로 한 문장이다.

### 초대 토큰 보안

- 128비트 랜덤 + SHA-256 해시 저장 + 7일 + 1회용: 기존 `ownerKey`·세션 패턴과 같고 충분하다. 조회는 PK 직접 조회라 타이밍 비교 문제가 없다. GET 공개 응답이 `{expiresAt}`만이라 초대자 정보가 새지 않는다. 존재·끊김·사용·만료를 모두 404로 합친 것도 좋다.
- 토큰이 `/#/invite/{token}`(프래그먼트라 서버·Referer에 안 나감)과 `login?invite={token}` 쿼리에는 나타난다. 쿼리는 로그에 남을 수 있으나 1회용·7일이라 수용 가능하다. 쿠키로 옮긴 뒤 URL에 토큰이 남지 않게(콜백 302가 프래그먼트로 보냄) 한 점도 좋다.
- 수락은 POST + Origin 검사 + SameSite=Lax 세션이라 CSRF는 막힌다. 남는 위험은 조건 5의 사회공학이다. 초대 생성 요청 속도 제한은 없지만 1인 1초대·로그인 필요라 남용 여지가 작다.
- 평문 토큰은 생성 응답에서만 보인다(해시 저장). 시트를 닫으면 링크를 다시 볼 수 없고 새로 만들면 이전 링크가 끊긴다. UX 문구에 적어 둔다.

### 30초 폴링 비용

- 계산(추론, 한도는 기억한 값이라 Cloudflare 문서로 확인 필요): 무료 Workers 하루 요청 10만 건, D1 하루 읽은 행 500만·쓴 행 10만. 함께 쓰는 탭 하나는 me·목록·예산·순서 4건/30초 = 시간당 480건. 둘이 8시간 보면 하루 약 7,700건으로 한 부부가 한도의 8% 안팎이고, 부부 십여 쌍이 같은 날 쓰면 한도에 닿는다. 읽은 행은 `/api/listings`가 지배한다: 매물 n개면 폴링 1회에 n행. n=30이면 하루 부부당 약 6만 행으로 무시할 수준이고, n=500이면 부부당 약 100만 행(한도의 20%)이다.
- A6의 "문제없다"는 개인·소규모 사용이 전제이며, 근거 숫자가 스펙에 없다. 스펙에 위 계산을 한 줄 넣고, 간격 `30_000`을 한 상수로 두며, 출시 뒤 대시보드로 요청 수를 한 번 확인하는 항목을 3-3에 추가한다. 한도 초과 시 `/api/*`만 실패하고(정적 자산은 `run_worker_first` 밖) 앱 전체가 계산기로는 계속 동작한다는 점은 안전하다.
- 줄이는 방법(지금은 불필요): 숨은 탭 중단(이미 기본값), 포커스 재조회로 충분한 데이터(예산·순서)는 폴링에서 제외, 나중에 문제가 되면 `/api/me`에 가구 변경 버전을 넣고 바뀔 때만 목록 조회.

## 결정 필요 항목 의견

- **D1 (모델 A)**: 찬성. 근거: 기존 행·PK를 건드리지 않아 AC-0를 지키며, 플랜이 같은 PK 인덱스를 써서 혼자 쓰는 경로의 비용이 같다. 필수 조건 1·2·6을 전제로 한다.
- **D2 (포커스 + 가구일 때만 30초 폴링)**: 조건부 찬성. 근거: 새 인프라가 없고 되돌리기 쉽다. 단 혼자 쓰는 사용자는 주기 요청 0건(AC-0(e))이어야 하며, 비용 계산을 스펙에 넣고 간격 상수화.
- **D3 (서버 쿠키로 복귀)**: 조건부 찬성. 근거: 콜백 한 곳에서 끝나고 토큰 모양을 검사해 열린 리다이렉트가 없다. 조건 4의 세 규칙(콜백 재검증, 비초대 로그인 시 쿠키 삭제, 실패 시 삭제)을 추가한다.

## 리스크 (남는 것)

- 구성원 누구나 상대가 넣은 매물을 지울 수 있고 되돌릴 수 없다(A3). 나가면 각자 자기가 넣은 것만 가져가므로, 상대가 지운 내 매물은 영구 손실이다. 문구 고지(조건 5)로 충분한지는 사용자 확인 대상이다.
- 가구에 있는 사용자가 한 기기에서 다른 계정으로 같은 로컬 매물을 이전해 되살아나는 경우(위 id 충돌 항목).
- 롤백이 가구 생성 뒤에는 불완전하다(위 마이그레이션 항목).
- wrangler 마이그레이션의 원자성과 D1 batch의 격리 수준은 문서로 확인하지 못했다. 구현 시 `--local`의 동시 수락 시험(`curl` 두 개)으로 조건 1을 검증하고, 원격에서는 AC-6의 동시 수락 항목이 같은 역할을 한다.
