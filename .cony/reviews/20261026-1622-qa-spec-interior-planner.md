# 우리 집 인테리어 플래너 스펙 — qa 검토

날짜: 2026-10-26 · 대상: `.cony/specs/interior-planner.md` (초안) · 검토만 함(제품 코드·테스트·스펙 수정 없음). 하네스 검증용 임시 프로젝트는 scratchpad에만 만들었다.

판정: **조건부 찬성** (구조는 테스트하기 좋다: 계산이 `summarizeInteriorPlan(now 주입)`, 검증이 한 함수, 태스크 0이 먼저. 다만 아래 "조건" 1~8이 풀려야 AC가 판정 가능하다. 특히 예시 값 하나(앞으로 낼 돈)가 정의를 구분하지 못하고, 하네스 패키지 이름이 스펙 문구와 다르다.)

## 근거 (최대 3개)

1. **예시 값 계산은 대부분 맞지만, 핵심 하나를 구분하지 못한다.** 아래 "AC 예시 직접 계산" 참고. P의 지급 합계가 항목마다 확정 금액과 같아서 "앞으로 낼 돈 = 확정 − 지급함"과 "미지급 지급 줄의 합"이 둘 다 1,250이다. 두 정의는 AC-4 후반(견적 D 확정)에서 갈라지는데 AC가 기대값을 적지 않았다.
2. **하네스는 `@cloudflare/vitest-pool-workers`가 아니라 `@cloudflare/vitest-plugin`이어야 한다.** pool-workers 최신 0.23.0의 peer는 `vitest ^4.1.0`뿐이라 이 프로젝트의 vitest ^5.0.5와 맞지 않는다. 후속 패키지 plugin 1.4.7은 peer `^4.1.0 || ^5.0.0`, 의존 wrangler 4.152.0(프로젝트 ^4.151.3과 호환). Node 쪽 miniflare 직접 사용은 Worker 코드가 `crypto.subtle.timingSafeEqual`(`server/auth/session.ts`)을 쓰는데 Node에는 없어서(`typeof` → undefined 확인) 세션 인증 경로가 막힌다. 실제 설치·실행으로 확인했다(아래 "0-3").
3. **0-4 범위는 2-1 변경 전 고정용으로 거의 충분하지만 네 군데가 빈다.** AC-0(b)의 `/api/me`·`/api/budget`·`/api/listing-order` 골든 응답, 수락 실패 분기(만료·사용됨·500개 초과), 동시 나가기 404를 확실히 만드는 방법, 라우터 경로 순서. 아래 "0-4".

예시가 구분하지 못하거나 틀린 곳:

- **앞으로 낼 돈 정의 (조건 1).** 세 후보 정의가 P에서는 모두 1,250이지만 AC-4의 변형에서 갈린다. (가) 전체 확정 − 전체 지급함, (나) 미지급 지급 줄의 합, (다) 확정 항목별 max(0, 확정 − 그 항목 지급함)의 합.
  - P에서 견적 D만 확정으로 바꾼 경우(AC-4 문장을 독립으로 읽음): 확정 1,430, 지급함 280 → (가) 1,150, (나) 250+1,000 = 1,250, (다) ①250 + ③(1,150−250 = 900) = 1,150.
  - 샷시 잔금 지급함 + 견적 D 확정(누적으로 읽음): 확정 1,430, 지급함 1,280 → (가) 150, (나) ①잔금 250 = 250, (다) ①250 + ③max(0, 1,150−1,250) = 250.
  - 즉 독립 읽기는 (나)를, 누적 읽기는 (가)를 구분한다. AC-4가 독립인지 누적인지부터 밝히고, 정의를 한 문장으로 고정해 해당 값을 적어라. 제안은 (다)다(항목 과지급이 다른 항목의 남은 돈을 가리지 않고, A4 "지급 합계가 달라도 막지 않음"과 맞는다). 과지급(지급함 > 확정)이 있는 항목의 처리가 이 예시로 처음 드러난다.
- **P에 항목 상태가 없다 (조건 2).** "견적 받기" 목록(주방가구만)과 A3(확정하면 상태 자동 상승)은 상태에 달려 있다. P에 ① 확정 ② 견적 중 ③ 확정 ④ 계획을 명시하고, "견적 받기" 정의를 적어라(견적 0개이고 미확정? 상태 계획·견적 중만?). ②는 견적이 있으나 미확정이라 어느 할 일에도 안 나오는데 의도인지 확인이 필요하다("확정하기" 할 일이 없다).
- **경계값이 없다.** 남은 예산이 정확히 0(총 예산 2,630 → 남은 0, "초과" 아님; 2,629 → 초과 1), 항목 확정 = 예산(초과 아님), 예산이 없고 확정만 있는 항목(초과 표시 없음), 예산도 확정도 없는 항목(0으로 합산), 지급일 = 오늘(11-10, "지남" 아님/오늘?), 지급일 없는 미지급 줄(어디에 정렬?). AC-2/4에 한 줄씩 추가를 제안한다.
- **"13단계" vs 공종 프리셋 14개 (조건 3).** U3 프리셋은 철거·샷시·설비·전기·목공·타일·욕실·도장·필름·도배·바닥·주방가구·조명·입주 청소 = 14개인데, 공정 순서 시트 문구는 "타일·욕실"을 한 단계로 묶어 13단계다. 공종별 정렬에서 타일과 욕실의 앞뒤(같은 순위 + 이름순? 타일 먼저?)를 정하고, AC-3의 "13단계"가 시트 단계 수임을 명시하라. 직접 입력 공종 "맨 뒤 이름순"은 예시가 없다. "단열·방충망" 같은 직접 입력 2개로 순서를 못 박아라(한글 가나다순 기준, 영문 혼용 시 정렬 규칙 포함).
- **D5의 반올림 문장이 기존 코드와 반대다 (조건 4).** D5는 "1만원 미만은 반올림 입력(123.5만 → 124)"라 했지만, 재사용하겠다는 `src/lib/utils/amount.ts`의 `validateAmount`는 소수를 `notInteger`("정수(만원 단위)로 입력하세요") 오류로 거부하고 반올림하지 않는다. 스펙 AC-5도 소수 예시가 없다. 기존 컴포넌트 그대로(거부)로 정하고 D5 문장을 고치거나, 반올림이면 새 동작으로 AC를 쓰라. 내림·올림·반올림 구분용 예시를 넣을 거면 `123.4`, `123.5`, `0.4`(→0이라 오류), `999999999.5`(→상한 초과)이고, 거부로 정하면 `123.5` → 오류 한 줄이면 된다.
- **표시 문구와 `formatManwon` 불일치 (조건 4).** AC는 "50만 초과", "예산 초과 130만", "2,630"이라 쓰는데 기존 포맷터는 "50만원", 10,000 이상은 "1억 2,000만원"이다. 요약에 쓸 문자열 형식(단위 유무·억 표기)을 AC에 못 박고 총 예산 12,000 같은 억 단위 예시를 하나 넣어라. 안 그러면 화면 테스트가 어느 쪽을 기대값으로 삼을지 qa가 임의로 정해야 한다.
- **AC-5 필드별 범위 빠짐.** 견적 금액은 1~999,999,999로 읽히지만 타입 주석엔 없다. 지급 금액 0 허용 여부, 지급 줄 이름 1~10자 경계(10/11), 견적 업체 30/31자, 메모 500/501자, 날짜 `2026-02-29`(정규식은 통과하지만 달력에 없음)·`2028-02-29`(유효)·`2026-1-1`(형식), 끝 날짜 = 시작(통과). 길이는 UTF-16이 아니라 코드포인트로 센다고 `countChars` 기준을 명시하라(이모지 경계).
- **AC-5 "16KB 넘는 항목 413"의 최악값.** 내가 계산했다. 짝 없는 서로게이트(6바이트/글자)로 채운 최악 항목 = 공종 120 + 메모 3,000 + 견적 5×(id 64+업체 180+연락처 180+메모 1,200+금액·키 ~65 ≈ 1,690 → 8,450) + 지급 5×~230(1,150) + id·날짜·키 ~400 ≈ **13.1KB**(id가 64자까지 허용되므로 스펙의 32자 가정보다 큼). 16KB 안이라 정상 최악 항목이 413이 되지 않는다(여유 약 18%). 이 최악 항목이 200이고 16KB+1바이트가 413인 두 케이스를 AC-5에 적고 테스트로 고정하라. 같은 이유로 POST 플랜의 `items ≤ 100`은 최소 항목(~170바이트)×100 ≈ 17KB가 플랜 쓰기 16KB를 먼저 넘으므로 "항목 101개 → 400"을 만들 수 없다. 가져오기 줄은 매물 추가 비용 최대 30줄이니 `items ≤ 30`으로 줄이거나 본문 한도를 따로 정하라.
- **AC-6 변환 경계 (조건 5).** 추가 비용 줄 이름은 최대 30자(`EXTRA_COST_LABEL_MAX_LENGTH`)인데 공종 이름은 1~20자다. 25자짜리 "인테리어" 줄을 가져오면 공종 규칙 위반이다(잘라내기? 오류? 메모로?). 30줄 합계가 총 예산 상한 999,999,999를 넘을 수 있는 경우(예: 줄 2개 6억+6억)도 규칙이 없다. 인테리어 줄 0개 → 체크박스 없음(스펙에 있음), 1개, 30개를 변환 함수 테스트 표에 넣을 것.
- **AC-9 SQL이 운영 DB에서 틀린다 (조건 6).** `SELECT COUNT(*) FROM interior_plans WHERE hidden_household_id IS NOT NULL`은 전체 가구의 합이다. 운영에 다른 가구가 있으면 1이 아니다. `WHERE hidden_household_id = '{가구 id}'`로 바꾸고 B의 플랜이 정확히 1개(PB)임을 전제로 적어라.
- **AC-10 시나리오 정밀화 (조건 6).** `markDeviceImportsDone`은 수락한 그 기기에서 `account-imports`(그 시점 기기 매물 id), `budget-imports`, `listing-order-imports`에 B를 이미 기록한다. 그래서 B가 이 기기에서 수락했다면 "4개 기록 키에 B userId가 추가되지 않고"는 거짓이고, 나간 뒤 예산·순서는 이미 완료 표시라 옮겨지지 않는다(수락 후 새로 저장한 매물만 옮겨진다). AC에 "B는 다른 기기에서 수락(이 기기엔 B 기록 없음)" 또는 "기록 키가 로그인 전후로 바이트 같음"으로 전제를 쓰라. 또 "훅 테스트로 `household !== null`이면 `send` 0회"는 `useAccountImport`·`useBudgetSource`·`useListingOrderSource` 각각에 필요하고(스펙 0-1이 셋을 고친다), 변이 확인도 셋 모두 해야 한다. 한 훅만 지켜도 나머지 둘이 열려 있다.
- **"기존 13개 키"는 코드에 12개다 (조건 7).** `src` 전체에서 `loan-calculator/*` 키를 세면 account-imports·budget·budget-imports·draft·listing-order·listing-order-imports·listings·privacy-mode·sent-shares·session-hint·text-size·trade-lookup = 12개다(`ocrSession` 등은 다른 저장소). AC-0(c)(g)는 개수 대신 "`interior-plans`·`interior-plan-imports` 외 모든 키에 쓰기·삭제 0회"(허용 목록 방식)로 쓰는 편이 정확하고, 이후 키가 늘어도 깨지지 않는다.
- **플랜 3개 상한과 나가기.** 가구 범위에서 B가 만든 PC와 숨겨졌던 PB가 나가면 B에게 3개를 넘을 수 있다(예: A 1개, B 숨김 3개, 함께 쓰는 동안 B가 PC 2개). 매물 500개 경계와 같은 의도된 상태라면 AC-5/9에 "그 상태에서 GET은 4개 이상 돌려주고 POST만 400, [계획 만들기] 비활성은 `>= 3`"을 적어라.
- **AC-8 재시도 경계.** 이미 플랜이 3개인 상태에서 같은 본문(이미 들어간 id)을 다시 보내면 `{imported: 0}`이어야 하고 400이면 안 된다(재시도 안전의 핵심). 다른 id면 400. INSERT…SELECT가 둘 다 0행이라 핸들러가 어떻게 구분하는지 AC에 한 줄 적고 하네스로 고정하라.

## 0-4 최소 서버 테스트 범위

2-1이 건드리는 것은 `householdScope.ts`(새 SQL 상수), `handleHousehold.ts`(수락·나가기 batch에 문장 추가), `worker/index.ts`(경로 8개 추가)다. 그 변경 전 동작을 고정하려면 아래를 0-4에 더해야 한다.

현재 목록이 충분한 부분: `LISTING_SCOPE_SQL`, listings CRUD/import, 수락(숨김·가구·동시 수락·`ownInvite`·`alreadyInHousehold`), 나가기(복귀·A 값·B 값·동시 나가기 404).

추가 필요:

1. **골든 응답**: 혼자·가구 계정 각각 `GET /api/me`·`/api/listings`·`/api/budget`·`/api/listing-order`(및 PUT/import의 `COALESCE`)의 응답 본문. AC-0(b)가 바로 이것인데 0-4 목록에 없다. 이 응답을 0001~0006과 0001~0007 두 번 돌려 같아야 한다.
2. **수락 실패 분기** (`describeAcceptFailure`): 없는/만료/이미 사용된 토큰, 토큰 형식 오류, A의 매물 501개 → 409 `householdLimit`(시드는 SQL로 싸게). 성공 판정이 `results[results.length-1]`이므로 실패 시 아무것도 안 바뀐다는 단언(B 매물 숨김 0, 가구 0행, `users.household_id` null)도 포함.
3. **수락 후 상태 전체**: `households`가 A의 예산·순서를 복사, B의 `users.budget`·`listing_order` 불변, 두 사람의 미사용 초대 삭제, B 매물 `hidden_household_id` = 가구 id, A·B 매물 id가 같아도 섞이지 않음.
4. **나가기 후**: 숨김 해제, 함께 쓰는 동안 B가 넣은 매물은 B 소유, A가 지운 매물은 돌아오지 않음, 두 번째 나가기 404.
5. **동시 실행을 확실히 재현하는 방법**: `Promise.all`로 두 요청을 보내면 순서가 보장되지 않는다. `acceptHouseholdInvite`·`leaveHousehold`는 `db`를 인자로 받으므로 핸들러를 직접 호출하고 `db`를 Proxy로 감싸 "첫 SELECT 이후, batch 전에" 경쟁 요청을 끼워 넣어라. 그래야 `cleared.meta.changes === 0`(나가기)과 마지막 문장 변경 수 판정(수락)을 진짜로 탄다. 2-1이 문장을 추가해 인덱스가 밀리면 이 테스트가 실패해야 한다(변이 확인: `[, , , cleared]` 인덱스를 한 칸 옮겨 실패하는지, `householdExists` 가드를 지워 실패하는지).
6. **라우터**: `routeApi`는 경로를 먼저 맞고 메서드를 검사한다. 2-1이 `/api/interior-plans/import`를 `/api/interior-plans/:id`보다 뒤에 두면 POST import가 405가 된다(`/api/listings/import`와 같은 함정). 지금 listings로 이 순서 규칙을 고정하는 테스트(`POST /api/listings/import`는 200대로 import 핸들러에 닿고, 같은 경로에 PUT을 보내면 `:id` 핸들러가 아니라 405 + `Allow: POST`)와 401/403/404/405 각 1건을 0-4에 넣으면 2-3이 같은 틀로 plan 경로를 검증한다.
7. **계약**: 0-4 테스트는 `worker/index.ts`의 `default.fetch`로 호출(요청 → 라우터 → 핸들러)하고 세션은 `sessions` 행을 직접 심어 쿠키 `mf_session={id}.{secret}`(해시는 `sha256Hex(secret)`)로 만든다. 핸들러 직접 호출은 5번 같은 경쟁 재현에만 쓴다.

1. 하네스 설정이 클린 체크아웃/CI에서만 깨질 수 있다(dist 없음, workerd 바이너리 설치, `pnpm.onlyBuiltDependencies`는 이미 workerd 포함). 0-3 PR에서 CI 한 번 통과를 증거로.
