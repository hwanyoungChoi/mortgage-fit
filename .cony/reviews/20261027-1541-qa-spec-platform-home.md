# 홈 허브와 하단 탭 (platform-home) 스펙 — qa 검토

날짜: 2026-10-27
대상: `.cony/specs/platform-home.md` 전체 (AC-0~7, 태스크 1~3, D1~D5, U1~U11, A1~A9)
관점: 테스트 가능성(판정 가능한 문장인지, 기대값이 구체적인지, 빠진 경계·상태), 기존 테스트 영향, AC-0 고정 방법

## 판정: 조건부 찬성

방향(D1 A·D2 A·D3 A·D5 B)은 테스트하기 좋은 구조다. 경로 규칙은 `parseRoute` 순수 함수 표로, 탭·[가가]는 `AppRoutes` 통합 몇 개로, 홈 상태는 순수 함수 상태표로 고정할 수 있다. 다만 아래 조건 8개를 스펙에 넣어야 한다. 앞의 4개(C1~C4)는 넣지 않으면 AC가 쓴 그대로는 테스트가 거짓 실패하거나 아무것도 지키지 못한다.

## 근거

1. **예시 값은 맞다.** `makePlanP`의 앞으로 낼 돈은 ① 280-30=250 + ③ 1,250-250=1,000 = 1,250(`summarizeInteriorPlan.test.ts:53`과 일치), `formatManwon(125000)`은 eok=12, man=5000이라 "12억 5,000만원"이다. 다만 아래 "예시 보강"의 구분 못 하는 부분이 있다.
2. **AC-0는 기존 패턴으로 고정할 수 있다.** `AppRoutes.storageKeys*.test.tsx` 3개가 이미 같은 틀(시드 → 스파이 Storage → 탭 순회 → `===`)이다. 다만 스펙 문장 그대로는 재현되지 않는 곳이 3군데 있다(C1~C3).
3. **AC-3(겹침·인쇄·키보드)과 AC-5의 "가장 크다"는 jsdom으로 판정할 수 없다.** CSS 모듈이 레이아웃으로 적용되지 않는다. 자동 테스트 대상이 아니라고 스펙이 명시하고 측정 방법을 적어야 한다(C6).

## 조건 (스펙에 넣을 것)

### C1. AC-0의 "setItem·removeItem·clear 0회"와 session-hint 예외를 한 문장으로 맞춘다

지금은 "0회"와 "단 session-hint는 기존 예외"가 모순처럼 읽힌다. 예외를 정확한 형태로 못 박지 않으면 `session-hint`에 대한 아무 쓰기나 통과한다. 기존 테스트가 보여 주는 실제 형태:

- 로그인 확인 전(pending): 쓰기 0회.
- 로그아웃 확인 후: `removeItem loan-calculator/session-hint` 1종만 허용(`storageKeys.test.tsx`가 `Set`으로 고정).
- 로그인 후: `setItem loan-calculator/session-hint "1"`만 허용(`storageKeys.loggedIn.test.tsx`의 `expectOnlySessionHintMark`).

AC-0에 이 세 줄을 그대로 쓴다. 14개 키 중 `session-hint` 한 개를 뺀 13개는 `===` + 쓰기 0회다.

### C2. AC-0 로그인 경로는 "이전이 끝난 상태"를 시드로 못 박는다

"로그인 상태(가짜 API)에서도 같다"는 시드 없이는 거짓이다. 기기에 안 옮긴 매물·예산·순서·계획이 있는 계정은 앱 시작 때 `account-imports`·`budget-imports`·`listing-order-imports`·`interior-plan-imports` 4개 키에 정상적으로 쓴다(기존 동작이고 `AppRoutes`가 홈 이전부터 전역으로 돌린다). 그러면 "홈이 쓰지 않았다"를 가를 수 없다. 기존 테스트가 쓰는 두 시드를 그대로 적는다.

- 혼자 쓰는 계정: 4개 imports 키에 해당 userId를 모두 시드(이전 끝남) → 쓰기 0회.
- 가구 계정(`isInHousehold: true`): 이전 4개 모두 건너뜀 → 쓰기 0회.

14개 키 시드에는 `interior-plans`(유효한 계획 P)도 넣는다. 기존 시드는 12개이고 새 키 2개는 비어 있었다. 이번엔 기존 키 14개가 모두 차 있어야 홈이 계획 원문을 다시 직렬화해 쓰는 버그를 `===`로 잡는다. 시드 원문은 기존처럼 들여쓰기(`JSON.stringify(x, null, 2)`)로 적어 다시 쓰면 걸리게 한다.

### C3. 스파이는 "주입 Storage 인스턴스" + "기본 localStorage의 Storage.prototype" 두 가지로 나눈다

스펙은 "스토리지 인스턴스와 `Storage.prototype` 모두 스파이"라고 쓴다. 기존 테스트의 `createMemoryStorage`는 `Storage`를 상속하지 않는 평범한 객체라 `Storage.prototype` 스파이는 아무것도 못 잡는다. 필요한 구성:

- (가) 기존처럼 `storage` prop에 스파이 메모리 스토리지를 주입해 `walkThroughTabs` 식 순회(대부분의 AC-0).
- (나) 1개 테스트는 `storage` prop 없이 jsdom `localStorage`를 시드하고 `vi.spyOn(Storage.prototype, "setItem" | "removeItem" | "clear")`로 같은 순회. 주입 경로를 우회해 `window.localStorage`를 직접 쓰는 새 코드(홈이 직접 쓰는 경우)를 잡는 용도다.

또 "홈에서 쓰기 0회"는 순회 끝에서 한 번만 보면 어느 화면의 쓰기인지 알 수 없다. 체크포인트를 넣는다: 홈이 처음 그려지고 안정된 직후(`findBy` 뒤) `setItem.mock.calls`가 비어 있음 → 이후 각 이동 뒤에도 같은 단언. AC-0(a)에 "홈이 그려진 직후 시점에서도 0회"를 한 줄 추가한다.

### C4. 홈 요약 입력값의 경계를 정의한다 ("올바른 금액")

U5/AC-6의 "draft 매매가가 올바른 금액이면"을 `validateAmount(salePrice).status === "valid"`(= `amount.ts`)로 못 박는다. 그래야 아래 표가 기대값이 된다. 지금 AC-6은 `""`와 `"12a"` 두 개뿐이다.

| draft.salePrice | 기대 (대출 계산 카드)                                         |
| --------------- | ------------------------------------------------------------- |
| `"125000"`      | 작성 중 · 매매가 12억 5,000만원                               |
| `"1"`           | 작성 중 · 매매가 1만원                                        |
| `"10000"`       | 작성 중 · 매매가 1억원 (`formatManwon`의 man===0 분기)        |
| `"125,000"`     | 12억 5,000만원 (붙여넣기 쉼표는 `stripAmountFormatting`이 뗌) |
| `" 125000 "`    | 12억 5,000만원 (앞뒤 공백)                                    |
| `"0"`           | 소개 문구 (notPositive)                                       |
| `"12.5"`        | 소개 문구 (notInteger)                                        |
| `"12a"`, `""`   | 소개 문구                                                     |
| `"999999999"`   | 99,999억 9,999만원 (최댓값, `MAX_AMOUNT`)                     |
| `"1000000000"`  | 소개 문구 (10자리 tooLarge)                                   |

draft 원문이 깨진 경우는 스토어가 `DEFAULT_DRAFT`로 읽으므로 "손상"이 아니라 소개 문구가 된다. 스펙이 "draft는 손상 상태가 없다"고 한 줄 써야 한다(AC-7(e)는 `listings`만 다룬다). `listingId`가 붙은 draft(저장한 매물을 수정 중)도 "작성 중"으로 보이는지 정한다(제안: 보인다).

### C5. AC-7 상태표를 카드별 × 상태별로 채운다

AC-7은 매물 카드의 실패·손상만 있고, 우리 집 카드의 손상·로딩 단독, 계정 확인 실패는 산문에만 있다. 홈이 본문에서 "카드마다 따로"라고 하므로 카드 독립을 단언하는 조합이 필요하다. 추가할 AC 행(순수 함수 입력 → 출력 표로 쓰면 가장 싸다):

| #   | 상태                                 | 매물 카드                                   | 우리 집 카드                | 대출 계산 카드       |

빠진 규칙을 스펙이 정해야 한다.

- 행 8/9: 스펙 산문은 "계정 확인 실패 → 불러오지 못했습니다"로 일률적이지만 기존 규칙은 session-hint 있는 브라우저만 error이고 없으면 로컬이다(`accountSourceStatus.ts`). 홈이 이 함수를 그대로 쓴다고 명시(제안).
- 매물 0개(로그인 서버 0개 포함)와 계획 0개는 소개 문구로 한다고 명시(스펙은 "n ≥ 1"만). 함께 쓰는 중 매물 0개는 "함께 쓰는 목록 · 매물 0개"인지 소개인지 정할 것.
- 개수 경계: 1개("저장한 매물 1개"), 계획 3개(상한), 앞으로 낼 돈 0("0만원", 이미 있음), 앞으로 낼 돈이 1억 이상일 때의 표기(`12500` → "1억 2,500만원").
- 세션 만료(`isSessionExpired`, 401)와 재조회 실패(`isRefreshFailed`, 받아 둔 목록은 있음)에서 홈이 무엇을 보이는지. 제안: 받아 둔 값을 유지하고 오류 문구는 쓰지 않는다. 지금 스펙에는 없다.
- 계획 "목록 순서"의 기준(로컬: 저장 순서, 서버: 응답 순서). AC-6은 "계획 3개면 3줄이 목록 순서로"이므로 이름이 서로 다른 계획 3개를 `createdAt` 역순 등으로 시드해 순서가 구분되게 한다.
- "로딩 중 로컬 값을 먼저 그렸다 바꾸지 않는다" 판정: `/api/me`를 deferred promise로 두고 첫 렌더 직후 로컬 매물 개수 텍스트가 DOM에 없음을 확인하고, resolve 뒤에야 서버 값이 나타남을 확인한다. 최종 상태만 보는 테스트는 이 규칙을 못 지킨다.
- AC-7(a)의 "서버 매물 2개·로컬 매물 5개"는 C2의 시드(이전 끝남)가 없으면 이전이 일어나 5개가 서버로 올라가므로 "2개"가 틀린다. 시드를 적을 것.
- 가리기 켬은 AC-6에서 정상 요약만 검증한다. 가리기 켬 + 로딩/실패에서 문구가 가려지지 않는지도 한 줄(문구엔 금액이 없으니 그대로 보임).

### C6. 자동 테스트로 못 하는 AC는 "무엇으로 판정하는지" 적는다

- AC-3: jsdom은 CSS 모듈 레이아웃을 계산하지 않는다. 프로젝트에 브라우저 자동화(Playwright 등)가 없다(`package.json` 확인). 리드 화면 확인 기록에 최소 측정값을 요구한다: 360×780에서 요약 줄 bottom === 탭 줄 top(`getBoundingClientRect`), `document.documentElement.scrollWidth <= 360`, 스크롤 끝의 [이 지역 실거래가 보기] 버튼 bottom <= 요약 줄 top. "맞닿고 겹치지 않는다"만으로는 판정자마다 다르다. 자동화 도입이 필요하면 qa가 따로 보고한다(지금 도입하지 않는다).
- AC-5 "대출 계산 카드가 가장 크다(제목 `--fs-title`, 나머지 `--fs-section`)": CSS라 jsdom에서 못 본다. 자동 테스트는 DOM 순서(대출 계산 → 매물 → 우리 집)까지만, 크기는 AC-3과 같은 화면 확인으로 옮긴다.
- AC-5 "숫자 순번·'단계'·'완료'·'잠김' 글자가 없다": 부정형 텍스트 단언은 쉽게 거짓 통과한다. 판정식을 적는다: 홈에 `ol` 없음, 카드 제목 텍스트가 `/^\s*\d+[.)]/`에 걸리지 않음, 홈 텍스트에 `/단계|완료|잠김|준비 중/` 없음. 숫자는 요약("3개")에 정상적으로 나오므로 "숫자 글자 없음"이 아니라 "순번 모양 없음"으로 쓴다.
- AC-0(c) `git diff main -- server migrations worker wrangler.jsonc`는 vitest가 아니라 검증 명령이다. 기록에 출력(빈 출력)을 남기는 항목으로 취급하고, 브랜치가 뒤처질 수 있으므로 `git diff $(git merge-base main HEAD) -- server migrations worker wrangler.jsonc`로 적는다. 서버 테스트(`vitest.d1.config.ts`)는 실행 대상에 넣지 않아도 되나 `pnpm test` 전체가 초록이어야 한다.

### C7. AC-4의 `banner` 질의가 테스트 도구에서 여러 개로 잡힌다

`Listings`, `PlanScreen`, `Share`, `Invite`가 이미 자기 `<header>`를 가진다(`MortgageListings.tsx:499`, `PlanScreen.tsx:76`, `MortgageShare.tsx:177`, `MortgageInvite.tsx:267`). 실제 브라우저에서는 `main` 안의 `header`가 banner가 아니지만 testing-library(aria-query)는 위치 조건을 보지 않는다. 직접 확인했다: `<header>`(전역) + `<main><section><header>`(화면)을 testing-library/dom에 넣으면 `queryAllByRole("banner")`가 2개를 돌려준다. 그래서 AC-4를 쓰인 대로 `getByRole("banner")`로 테스트하면 저장 목록·우리 집 계획·공유·초대 화면에서 "여러 개 발견" 오류가 난다. 스펙에 둘 중 하나를 쓴다.

- 전역 머리 줄에 이름을 준다(예: `aria-label="모기지핏"`)고 하고 AC-4를 `getByRole("banner", { name: "모기지핏" })`로 쓴다(`navigation "화면"`과 같은 방식). 또는
- 전역 머리 줄을 `body > #root > header`의 직접 자식으로 식별하는 질의를 qa가 쓴다고 명시.

어느 쪽이든 "화면 안 `<header>`가 있어도 전역 머리 줄은 하나"를 AC-4에 못 박는다. 그리고 제품 코드는 전역 머리 줄이 `<main>` 바깥에 있어야 한다(스펙 DOM 순서 header → main → nav와 일치).

### C8. 기존 테스트 수정의 감사 방법을 태스크에 넣는다

1-1에서 fe가 기존 테스트를 고치게 돼 있다("단언 약화 금지"). qa 원칙(테스트 파일은 qa가 쓴다)과 겹치므로 규칙을 명시한다.

- fe는 기계적 이름 변경만 한다: 시작 해시 `#/` → `PATHS.calculator`, 탭 링크 이름 "저장 목록" → "매물", 해시 단언 `"#/"` → `"#/calculator"`. 그 밖의 변경(단언 삭제·`toBe`→`toBeTruthy` 등)은 1-2에서 qa가 되돌려 이유를 요구한다.
- 1-2 시작 시 qa가 `git diff main -- '*.test.ts' '*.test.tsx'`에서 삭제된 `expect` 줄 수를 센다. 삭제된 단언은 0이어야 한다(바뀐 단언은 허용).
- 2-1(읽기 훅 분리)은 "동작 무변경"이므로 `useInteriorPlanSource.test.tsx`와 `MortgageHome*.test.tsx`를 **한 줄도 수정하지 않고** 통과해야 한다고 AC에 쓴다. 테스트 diff가 비어 있다는 것이 회귀 없음의 증거다.

## 경로·기존 링크 (AC-1에 더할 통합 표)

AC-1은 `parseRoute` 단위만 있고, 화면 도착·주소 정규화·이력 증가를 같이 보는 `AppRoutes` 표가 없다. 아래 표를 `it.each`로 한다 (각 행: 시작 해시 → 보이는 화면, 최종 해시, `history.length` 불변, `aria-current` 탭).

## 예시 보강 (구분 못 하는 값)

- 앞으로 낼 돈 `1,250`은 샷시 확정 견적 금액(E 1,250)·"전체" 공간 합계(1,250)와 같은 숫자다. 계획 P만 쓰면 "확정 견적 중 최대 금액"이나 "전체 공간 합계"를 내는 버그와 구분이 안 된다(오늘 `summarizeInteriorPlan`이 그렇게 틀릴 가능성은 낮지만 홈이 새 코드로 계산을 부르면 달라질 수 있다). 홈 AC는 `summarizeInteriorPlan(plan, now).upcomingTotal`을 그대로 부른다는 점을 순수 함수 쪽에서 이미 검증하므로, 홈 테스트에는 P에서 한 줄(지급 `isPaid`)만 바꿔 값이 달라지는 케이스(예: 샷시 잔금을 지급함으로 → 250)를 하나 더한다. 지급함으로 바꾸면 홈이 다시 계산해 "250만원"이 보여야 한다(`paySashBalance` 픽스처가 이미 있다).
- 12억 5,000만원은 eok·man 두 분기를 모두 지난다. `10000 → "1억원"`, `1250 → "1,250만원"`(eok=0)도 한 칸씩 더한다(C4 표).
- `3개`는 매물 3개 + 서버/로컬 구분이 안 된다. AC-7(a)는 서버 2·로컬 5로 구분되어 있어 좋다. AC-6은 로컬 3, 서버 값을 다른 수(예: 서버 2)로 해서 로그인 전후를 구분하는 쌍을 둔다.
- 계획 이름 "우리 집"이 탭 이름 "우리 집"과 같아 `getByText("우리 집")`이 모호하다. 테스트는 항상 `within(card)` 또는 role 질의로 좁혀야 한다. 같은 이름 충돌 자체를 보호하는 케이스(계획 이름 "우리 집")를 그대로 두는 것은 좋다.

## AC-2·AC-4 테스트 방법 메모

- 링크 이름은 정확히 문자열 일치로 질의한다(`name: "계산"` vs 카드 `name: "대출 계산"`은 정규식을 쓰면 충돌). 정규식 질의 금지를 qa 규칙으로 둔다.
- `aria-describedby` 판정은 `toHaveAccessibleDescription`(jest-dom)으로 가능하다.
- `inert` 판정은 기존 `closest("[inert]")` 패턴을 그대로 쓴다(`MortgageCalculator.test.tsx:137`). 시트가 열린 동안 header·main·nav 셋 다 `closest("[inert]") !== null`이어야 하고 시트는 null. 셋을 한 컨테이너로 감싸도 되고 각각 inert여도 되지만, 시트를 다시 닫은 뒤 포커스가 [가가]로 돌아오는지(`toHaveFocus`)까지 본다.
- 아이콘 `aria-hidden="true"`: lucide는 기본으로 붙이지만 스펙이 단언하므로 구현에서 명시 prop으로 두는 쪽이 안전하다. 테스트는 `nav.querySelectorAll("svg")` 전부가 aria-hidden이고 4개임을 본다.
- `nav`가 `main` 뒤: `main.compareDocumentPosition(nav) & Node.DOCUMENT_POSITION_FOLLOWING`.
- `history.length` 불변은 기존 테스트가 이미 쓰는 패턴이다.

## D1~D5 (테스트 가능성 관점)

- **D1 A 찬성.** `parseRoute` 한 함수의 표로 전부 판정된다. B는 "해시 없이 열 때만 홈"이라는 진입 경로 의존 상태를 만든다(`""`과 `"#/"`가 달라져야 하는데 앱이 곧바로 `#/`로 정규화하므로 구분 자체가 불가능한 상태), 테스트도 불가능하고 사용자도 재현하기 어렵다. C도 판정은 쉽지만 요청과 다르다는 스펙의 근거에 동의.
- **D2 A 찬성.** 라우트 이름이 경로와 화면에 일치해 기존 `MortgageHome*.test.tsx` 약 85개 it을 건드리지 않는다. B는 그 파일들의 이름·import·`PATHS.home` 사용을 일괄 변경해야 하고, C는 별칭 리다이렉트라는 추가 상태를 만든다.
- **D3 A 찬성.** [가가]가 화면마다 하나만 있는 구조라 AC-4가 `AppRoutes` 통합 테스트 1개로 모든 화면을 `it.each`로 덮는다. B는 홈에서만 나타나 "계산 화면에서 글자 크기를 못 바꾼다"는 회귀를 만든다. C는 화면마다 구현이 달라 6곳을 따로 테스트해야 한다. 조건은 C7(banner 질의).
- **D4 A 찬성, 단 조건 하나.** 테스트 가능성은 A·B·C가 같다(jsdom은 svg를 그대로 낸다). A의 qa 관점 이슈는 의존성이 `pnpm build` 크기 경고(메인 청크 500KB)를 더 키우는지다. 1-1 직후 번들 크기를 기록으로 남긴다. lucide 아이콘이 `aria-hidden`을 자동으로 붙이는지 버전에 따라 다를 수 있으니 구현이 명시 prop으로 넣는다.
- **D5 B 찬성.** 읽기와 쓰기를 분리하면 홈이 쓰기 함수를 손에 쥐지 않는다는 구조적 보장이 생기고, 순수한 읽기 훅은 `renderHook` 하나로 상태(loading/error/loggedOut/loggedIn/household)를 전수 테스트할 수 있다. C는 모든 화면에서 조회가 돌아 우리 집 밖 화면의 `fetch` 호출 횟수 단언을 전부 흔든다. 조건: C8의 "2-1에서 기존 테스트 diff 0".

1. (높음) AC-0를 스펙 문장 그대로 구현하면 첫 실행부터 session-hint 예외와 imports 4키 쓰기로 실패하거나, 예외를 넓혀 아무것도 못 잡는다(C1·C2).

3. (중간) `#/`로 시작하는 기존 테스트가 부정형 단언이면 조용히 통과한다. 1-1 직후 감사가 필요하다.
4. (중간) 홈 로딩 중 로컬 값 플래시는 최종 상태 단언만으로는 못 잡는다(C5의 deferred 방식 필요).
5. (중간) 홈이 계산 화면 draft를 읽지만 draft는 손상 상태가 없어 "작성 중"이 거짓으로 비는 사례를 사용자에게 알릴 길이 없다. 의도라면 스펙에 명시.
6. (낮음) AC-3 수동 항목은 판정 기준이 없으면 리드마다 달라진다(C6).

## 자동 테스트로 못 하는 항목 (화면에서 직접 확인)

- 요약 줄과 탭 줄이 겹치지 않음, 스크롤 끝에서 버튼·마지막 카드·표 "계" 줄이 가리지 않음, safe-area 여백, 키보드가 뜰 때 탭이 키보드 뒤에 있음, 시트가 탭 줄을 덮음, 인쇄 미리보기에 탭·머리 줄 없음, 가로 스크롤 없음, 최대·최소 글자 크기에서 탭 라벨 한 줄, 대출 계산 카드가 가장 크게 보임, 선택 탭의 알약·굵은 라벨이 무채색 팔레트에서 구분됨.
