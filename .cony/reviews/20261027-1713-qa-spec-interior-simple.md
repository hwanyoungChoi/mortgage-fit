날짜: 2026-10-27

## 근거

1. **예시 값은 맞고, 잘못된 구현을 가른다.** P: 확정 R1+R3+R5 = 180+370+250 = 800, 남은 1,000−800 = 200, 총 예산 700이면 −100(초과 100), R4 체크 800+400 = 1,200(초과 200), R1 해제 1,200−180 = 1,020(초과 20), 표 계 8,000,000원, CSV는 머리 1 + 줄 5 + 계 1 = 7행으로 모두 맞다. 견적을 다 더하면 1,350, "구분당 확정 하나" 버그면 R4 체크 뒤 830이라 800/1,200과 구분된다. L: 확정 370, 남은 3,000−370 = 2,630이 맞다. 옛 방식 합계(Y 예산 200 포함 570)나 X 예산(350)을 섞은 구현과 구분된다. D2 a(400)와 b(770)도 구분된다.
2. **순수 함수로 빼기 좋은 구조다.** 줄 펼치기·묶기·합계·쓰기 입력 만들기를 `src/lib/utils/`의 순수 함수로 두라는 1-1이 테스트에 가장 유리하다. 값을 판단하는 코드가 컴포넌트에 묻히지 않는다.
3. **AC-0은 가장 중요한데 지금 문장으로는 두 군데가 구멍이다.** (i) 기존 `AppRoutes.storageKeys*` 테스트가 "그대로 통과"해도 AC-0(d)(L을 열기만 해도 `interior-plans` 원문 `===`)를 지키지 못한다. (ii) AC-0(c)의 `validateInteriorItemFields(input)` deep equal은 "숨은 값이 보존됐는가"를 증명하지 못한다. 아래 C1, C2.

## 조건 (스펙에 넣을 것)

### C1. AC-0(b)를 사실대로 고쳐 쓴다

현재 테스트가 하는 일:

- `AppRoutes.storageKeys.test.tsx`·`.loggedIn`·`.listingEntry`: `ALLOWED_KEYS`에 `interior-plans`가 들어 있다. 그 키의 쓰기를 막지 않는다.
- `AppRoutes.storageKeys.hub.test.tsx`: `interior-plans` 포함 13개 키 `===`와 쓰기 0회(session-hint 제외)를 점검하고, 시드는 옛 P(`makePlanP`)이며 [우리 집] 탭에서 플랜 화면이 실제로 열린다. 가장 가까운 틀이지만 목록·표 보기·가리기·확정 토글은 안 거친다.
- 이 파일은 diff 0이 불가능하다. 허브 카드 문구(`앞으로 낼 돈 1,250만원`, 181·186·191행)와 `expectHomeSettled`의 `전체 샷시 열기`(222행)가 바뀌어야 한다. **허용하는 수정은 이 두 종류의 기대 문자열뿐**이고 `ALLOWED_WRITES`·`expectUntouched`·`NON_HINT_KEYS` 단언은 한 글자도 바뀌면 안 된다고 스펙에 쓴다. 나머지 `storageKeys*`·`listingEntry`·`householdPlans`는 diff 0.

AC-0(b)를 이렇게 쓴다. "기존 `storageKeys*` 테스트는 허브 카드·플랜 화면 기대 문자열 외 diff 0으로 통과한다. 그리고 AC-0(d)용 새 테스트가 있다(C3)."

### C2. AC-0(c)를 둘로 쪼갠다

`validateInteriorItemFields(input)`이 `input`과 deep equal이라는 것은 "알려진 키만 있고 형식이 맞다"는 뜻일 뿐이다. 새 화면이 `payments`·`startDate`·`quote.contact`를 PUT에서 빠뜨려도 이 단언은 통과한다(저장소 `updateItem`도 검증 통과한 값으로 전체 교체한다). D1 A의 유일한 남은 위험이 바로 그 누락이므로 별도 단언이 필요하다.

- (c1) 형식: `expect(validateInteriorItemFields(input)).toStrictEqual(input)`. **`toEqual`이 아니라 `toStrictEqual`**. `toEqual`은 `{ memo: undefined }`와 `{}`를 같게 보므로 "비고 없음 → `memo` 키 없음", "해제 → `confirmedQuoteId` 키 없음"(AC-2a, AC-3)을 못 잡는다. 검증기는 undefined 키를 만들지 않으므로 `toStrictEqual`이 그 버그를 잡는다.
- (c2) 보존: 모든 쓰기 함수에 대해 `omit(input, 바꾼 키) toStrictEqual omit(원래 항목에서 id·createdAt·updatedAt 뺀 것, 바꾼 키)`. 바꾼 키는 함수별로 고정한다: 줄 수정 = `trade`·`memo`·`quotes[i]`의 `vendor`·`amount`·`memo`·`confirmedQuoteId`, 확정 토글 = `confirmedQuoteId`만, 줄 삭제(n≥2) = `quotes`·`confirmedQuoteId`만.
- (c3) **키 빠짐 방지**: fixture는 모든 선택 키를 채운 항목 하나(`budget`·`quotes`(`contact`·`memo` 포함)·`confirmedQuoteId`·`payments`(`dueDate`·`isPaid` true/false)·`startDate`·`endDate`·`memo`, 상태 5종 각각)여야 한다. 키 목록은 `{ ... } satisfies Record<keyof InteriorItemInput, true>`와 `Record<keyof InteriorQuote, true>`, `Record<keyof InteriorPayment, true>`로 선언한다. 나중에 항목에 키가 추가되면 이 선언이 컴파일 오류가 되어 테스트도 같이 고치게 된다.

### C3. AC-0(d)는 새 파일로 고정한다

기존 테스트 파일을 늘리지 말고(diff 0 규칙) 새 파일 `src/AppRoutes.storageKeys.interiorSimple.test.tsx`를 만들어 허브 테스트의 helper(`createMemoryStorage`·`stubApi`·`json`)를 복사해 쓴다. 틀은 `hub.test`와 같다(시드 → 스파이 Storage → 단계마다 단언).

- 시드: 14개 키 전부. `interior-plans` 원문은 **들여쓰기한 JSON**(`JSON.stringify(x, null, 2)`)이어야 한다. 다시 직렬화하면 원문이 달라져 `===`에 걸린다. 계획은 L과 옛 P(payments·상태 5종·날짜·연락처가 든 계획) 두 개를 한 원문에 넣는다.
- 단계: [우리 집] 진입 → 목록 → 줄 시트 열었다 닫기(저장 안 함) → [표] → [CSV 내려받기]·[인쇄·PDF] → 가리기 켜기/끄기 → [목록] → 홈 → 뒤로 가기. 각 단계 뒤 `interior-plans` 포함 13개 키 `===`, `setItem`·`removeItem`·`clear`는 허용 목록(모드별 session-hint) 밖 0회.
- 모드: 로그아웃(주입 스파이 + jsdom `Storage.prototype` 스파이 1개) / 로그인 혼자(이전 4키 시드, 서버 GET이 L을 돌려줌) / 가구. 로그인·가구는 `api.writes()`가 `[]`(POST·PUT·PATCH·DELETE 0건)여야 한다.
- 대조군(스파이가 살아 있음): 같은 파일에서 L의 줄 하나를 체크하면 `interior-plans`에 `setItem` 정확히 1회(로그인 모드는 PUT 정확히 1건)이고, 그 PUT의 항목 외 다른 항목 원문은 `===`.

### C4. AC-0(a)의 명령을 거짓 통과가 안 나오게 쓴다

`git diff $(git merge-base main HEAD) -- <경로들>`는 두 가지로 거짓 통과한다.

- 아직 커밋하지 않은 새 파일(예: `migrations/0008_*.sql`)은 diff에 나오지 않는다. `git status --porcelain -- server migrations worker wrangler.jsonc src/lib/utils/validateInteriorPlan.ts`도 비어야 한다고 쓴다.
- 경로 오타도 빈 출력이다. 지금 경로는 모두 실제로 있음을 확인했다(`server`·`migrations`·`worker`·`wrangler.jsonc`). 검증 때 `ls`로 먼저 확인하고, 명령은 `git diff --exit-code <mb> HEAD -- ...`(종료 코드로 판정)로 쓴다.
- `types/interiorPlan.ts` 판정: `git diff -U0 <mb> -- src/lib/types/interiorPlan.ts | grep '^[+-][^+-]'`의 출력이 `InteriorProcessSource` 타입과 그 주석 줄뿐이고 `+` 줄이 0개.
- `src/lib/constants/interiorPlan.ts`도 같은 방식: `-` 줄은 "지울 목록"의 이름뿐이고 `+` 줄 0개(길이·개수 상한 불변). 상한 상수 값 자체는 `validateInteriorPlan.test.ts`(30/31, 200/201, 500/501 경계)가 고정하므로 이 테스트가 diff 0이어야 한다고 AC-0(e)에 추가한다.
- AC-0(e)에 추가: `interiorPlanStorage.test.ts`·`validateInteriorPlan.test.ts`·`interiorItemConflict.test.ts`·`useInteriorPlanImport.test.tsx`·`AppRoutes.householdPlans.test.tsx`. 이들이 쓰는 `src/test/interiorPlanFixture.ts`는 **추가만 가능, 기존 export 수정 금지**(7개 테스트 파일이 공유하므로 값을 슬쩍 바꾸면 diff 0 테스트의 의미가 바뀐다).

### C5. 새 예시 계획 이름이 옛 fixture와 충돌한다

스펙의 P·L은 `interiorPlanFixture.ts`의 `makePlanP`(옛 P)와 이름은 같고 내용이 다르다. 새 fixture는 새 파일 `src/test/interiorSimpleFixture.ts`에 `makeSimplePlanP`·`makePlanL`로 둔다(스펙에도 이 이름으로 적는다). 옛 `makePlanP`는 지우지 않고 AC-0의 "더 복잡한 옛 계획" 시드와 허브 1,530 검산에 쓴다.

### C6. 비고 칸의 초기값과 합성 문구를 구분한다 (AC 추가)

견적 0개 항목의 비고에 "예산 200만원"이 화면에 보인다(U9). 이 문구는 표시용이지 `item.memo`가 아니다. 줄 시트의 비고 입력 초기값이 `item.memo`가 아니라 화면 문구라면 Y를 저장할 때 "예산 200만원"이 `memo`로 저장되어 이후 표시가 "예산 200만원 · 예산 200만원"이 되고 저장 값이 바뀐다. AC-4(b)에 추가: Y의 시트를 열면 비고 칸은 비어 있고, 저장한 PUT에 `memo` 키가 없다. 같은 이유로 표·CSV의 비고는 `item.memo`(있으면)에 예산 조각(견적 0개일 때만)을 이은 것이고 "미확정"·"최저"·"초과" 조각은 없다(L CSV 행으로 고정).

### C7. 확정 체크의 "저장 중" 표시를 하나로 정한다

스펙은 "저장 중 그 체크만 비활성, 실패하면 원래 상태로 돌린다"라고 한다. 낙관적 갱신이면 체크는 켜졌는데 요약은 옛 값인 순간이 생기고, 테스트가 무엇을 기대할지 갈린다. 제안: **체크와 요약 모두 저장소/캐시 값에서 파생**(낙관적 갱신 없음). 저장 중에는 체크가 원래 상태 그대로 비활성(`aria-busy`)이고 성공하면 체크·요약이 같이 바뀐다. 그러면 "실패하면 원래대로"는 자연히 성립하고, 테스트는 지연 응답(`PENDING`) 중 체크 상태와 요약 값을 단언하면 된다.

그리고 **같은 항목의 다른 줄도 잠근다.** 항목 하나가 여러 줄이 될 수 있다(옛 항목 n≥2). 첫 PUT이 끝나기 전에 같은 항목의 형제 줄을 누르면, 두 번째 PUT이 첫 결과가 반영되기 전 캐시로 항목 전체를 만들어 첫 변경을 덮는다(서버 PUT은 전체 교체). AC-3에 추가: 지연 응답 중 같은 항목의 형제 줄 체크는 비활성이거나 PUT이 직렬화되어 최종 항목에 두 변경이 모두 있다.

### C8. 가리기: 접근 가능한 이름과 요약, 시트

"확정 체크의 접근 가능한 이름은 `{구분} {업체} {세부내용} 확정`"이면 가리기에서도 세부내용이 `aria-label`로 DOM에 남는다. 기존 표 테스트는 `innerHTML`에 값이 없는지 본다(`MortgageHome.table.test.tsx` "가리기 켜짐"). AC-1을 이렇게 판정 가능하게 쓴다.

- 가리기 켜짐: 컨테이너 `innerHTML`에 세부내용("실크 전체"), 비고, 금액 문자열("180"·"1,800,000"·"800만원" 등)과 `aria-label`·`title`이 없다. 체크 이름은 `{구분} {업체} 확정`으로 줄어든다. 요약의 지출 예정·남은·총 예산·"예산 초과 n만원"도 가려진다. 견적 0개 줄의 합성 비고("예산 200만원")도 가려진다.

### 기계적 감사 절차

1. `git diff --name-status <mb> HEAD -- '*.test.*' 'src/test/*'`로 삭제(D)·수정(M)된 테스트를 뽑고, D는 모두 위 "지워도 되는 것"에 대응하는지 표로 적는다. 대응 못 하는 D는 실패.
2. M 파일마다 제거된 `expect(`·`it(` 줄(`git diff -U0 | grep '^-.*\(expect(\|it(\|it\.each\)'`)을 분류한다: (R) 주제가 지워짐, (T) 새 테스트로 옮김(새 테스트 이름 병기), (X) 설명 없음. **X가 0이어야 통과**.
3. 다음 키워드가 든 제거된 줄은 반드시 (T)여야 한다: `toBe(seed`, `setItem`, `removeItem`, `clear`, `writes()`, `household`, `가구`, `import`, `corrupt`, `unavailable`, `INTERIOR_ITEM_MAX_COUNT`, `999999999`, `1000000000`, `privacy`, `가리기`, `conflict`.
4. 기대값 완화 금지: `toBe`→`toContain`/`toMatch`, `toEqual`→`objectContaining`, `toHaveLength(n)`→`toBeGreaterThan`, 호출 횟수 단언(`.toBe(0)`·`toHaveLength(0)`) 삭제, `it.skip`·`it.todo`·`.only`·`describe.skip`, `waitFor` 시간 늘리기, 스냅샷 갱신. 검색: `git diff <mb> HEAD | grep -E '^\+.*(\.skip|\.todo|\.only|objectContaining|toContain\()'`.
5. 개수: 파일별 `it` 수의 전후를 표로(줄어든 만큼이 R/반전과 맞는지).
6. 죽은 코드: 지울 이름 목록(`ItemSheet`·`SpacesSheet`·`ProcessSheet`·`PlanTodos`·`QuoteRow`·`PaymentRow`·`ItemGroups`·`ItemRow`·`ListView`·`INTERIOR_TRADES`·`INTERIOR_PROCESS_*`·`InteriorProcessSource`·`INTERIOR_ITEM_STATUS_LABELS`·`INTERIOR_PAYMENT_LABEL_PRESETS`·`countSpaceItems`·`INTERIOR_NO_SPACE_LABEL`·`createDefaultSpaces`·`interiorItemDraft`·`sortInteriorTrades`·`paymentTodos`·`quoteTodos`·`upcomingTotal`)을 `rg`로 `src server`에서 찾아 0건. `INTERIOR_ITEM_STATUSES`·길이/개수 상한은 남아 있어야 한다(있는지도 확인). `pnpm lint`는 미사용 export를 잡지 못하므로 이 검색이 필요하다.
7. 지운 뒤에도 남는 약속 확인(코드 변경 없이 통과해야 함): `pnpm vitest run server`(D1 하네스 포함 설정은 `vitest.d1.config.ts`) 와 AC-0(e) 목록.

## D1·D2 테스트 가능성 의견

**D1 A: 찬성.** 순수 함수 + 기존 jsdom·하네스로 모두 판정 가능하다. B는 "옛 번들 탭이 `{ plans }` 전체를 다시 쓰며 새 키가 사라진다"를 테스트로 막을 수 없다(스펙도 인정). C는 같은 데이터에 경로가 둘이 되어 가구 범위·이전 테스트를 전부 새로 만들어야 한다. 조건: C2(c2·c3)와 C3이 있어야 A가 안전하다고 말할 수 있다.

**D2 태스크 1의 a: 찬성.** 쓰기 1번이라 부분 실패 상태가 없고 단위 테스트가 쉽다. 조건: 공유 안내 문구(n≥2일 때만, n 표시)와 AC-4(d)를 테스트한다. 한계는 인정해야 한다. 체크가 다른 줄의 체크를 풀므로 "줄마다 확정"과 어긋나지만 합계는 보이는 체크의 합이라 돈 계산은 맞다.

**D2 b: 아래 둘이 해결되지 않으면 반대.** a보다 상태가 훨씬 많아 테스트가 어렵고 스펙이 "손실은 없다"고 한 것도 일부 틀렸다.

- **이중 계산(돈이 틀림)**: 이미 확정된 견적(예: 확정 q1)이 든 줄의 구분·비고를 고쳐 떼어 낼 때, ① 새 항목 `confirmedQuoteId: q1` 생성이 성공하고 ② 원래 항목에서 q1을 빼는 PUT이 실패하면 원래 항목도 q1을 확정한 채라 같은 견적이 둘로 보이고 **둘 다 체크되어 지출 예정에 두 번 들어간다**. 다른 기기가 동시에 같은 줄을 떼어 내도 마찬가지다(`addItem`이 둘 다 성공). 스펙의 AC-7 실패 예는 q2가 미확정인 경우뿐이라 이를 못 잡는다. 필요: 새 항목은 확정을 끈 채 만들고 ② 뒤에 확정을 켜는 3단계로 하거나, 같은 `quote.id`가 두 항목에 있으면 계산에서 한 번만 세는 규칙을 정하고, 실패 주입 테스트(① 성공·② 실패, 확정된 견적/미확정 견적 각각)로 지출 예정이 이중으로 나오지 않음을 고정한다.
- **항목 100개일 때**: 가득 찬 계획에서 옛 n≥2 항목의 줄을 떼어 내려면 `addItem`이 상한으로 거부된다. 이때 동작(제자리 a로 대체 / 안내 후 중단)을 정하고 테스트한다.
- 위치 이동도 AC에 적는다. 새 `createdAt`이라 떼어 낸 줄이 묶음 끝으로 간다(L에서 욕실나라 체크 후 순서: 하루바스 철거·방수, 하루바스 타일 덧방, 욕실나라). 체크를 누른 줄이 손가락 밑에서 사라지므로 AC-7에 기대 순서를 쓴다.
- React key는 `quote.id` 단독이 아니라 `item.id:quote.id`여야 한다(부분 실패로 같은 견적 id가 두 항목에 생길 수 있음). 중복 key 경고(`console.error`)가 없다는 단언을 부분 실패 테스트에 넣는다.

A2(옛 계획이 거의 없음)가 확인되면 **태스크 2를 빼고 a로 끝내는 쪽을 권한다.** 테스트로 보장하기 어려운 부분만 남는 b를 위험을 감수하고 넣을 이유가 약하다.

## 리스크

1. **(높음) 숨은 값 누락**: 새 화면이 PUT에서 `payments`·날짜·`contact`를 빠뜨리는 버그는 검증이 못 잡는다. C2 c2·c3과 C3으로만 막는다.
2. **(높음) 기존 테스트가 AC-0(d)를 지킨다고 믿는 오해**: C1, C3.
3. **(중간) 가리기 우회**: `aria-label`·시트·요약에 값이 남을 수 있다(C8).
4. **(중간) 확정 토글 경합**: 같은 항목의 형제 줄을 연달아 누르면 앞선 변경이 덮인다(C7).
5. **(중간) 묶음 순서 변동·위치 이동**: 줄 삭제나 D2 b에서 줄이 움직여 사용자가 혼란스럽다.
6. **(중간) D2 b 이중 계산**: 위 D2 항.
7. **(낮음) 숨은 지급·날짜 삭제**: 줄을 지우면 보이지 않는 기록도 사라진다(A6).
8. **(낮음) 옛 번들**: 실제 옛 번들 탭이 새 항목을 어떻게 보이는지(상태 "계획"으로 보임)는 자동 테스트가 없다.

## 자동 테스트로 확인할 수 없는 항목 (화면에서 직접)

- 목록 줄 레이아웃(업체/세부내용/견적/체크 정렬), 모바일 폭에서 줄 안 겹침, 체크 터치 영역 크기.
- 저장·확정 뒤 스크롤 위치 유지.
- 인쇄 미리보기에서 표가 한 장에 맞는지, 구분 병합.
- 옛 번들 탭 동시 사용: `git worktree`로 merge-base 빌드를 따로 띄우고, 같은 브라우저 한 탭은 옛 번들·한 탭은 새 번들로 L을 열어 서로 고쳐도 숨은 값이 남는지.
- 두 기기(가구)에서 한쪽 확정 → 30초 안에 다른 쪽 반영(실제 서버).
