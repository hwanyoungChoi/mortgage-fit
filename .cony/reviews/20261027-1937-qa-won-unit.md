# [우리 집] 금액 원 단위 입력·표시 (be 제안) — qa 검토

날짜: 2026-10-27
대상: `.cony/reviews/20261027-2000-be-proposal-won-unit.md` (A / A-1 / B / C)
관점: 테스트로 판정 가능한가, 예시 값 검산, 경계, 보존 테스트, 옛 파서 재현

## 판정

- **A: 조건부 찬성** (아래 조건 Q1~Q10을 AC로 넣는다는 전제)
- **A-1: 조건부 찬성.** 테스트 면적이 가장 작다(PATCH 매트릭스·설정 시트 변경 없음). 단 "입력·표시 모두 원" 요청을 못 채우므로 qa는 범위 선택에는 중립이고, 사용자가 견적만 원한다면 A-1이 가장 검증하기 쉽다.
- **B: 반대.** 키 하나(`amountUnit`)가 같은 이름 키 전부의 뜻을 바꾼다. 항목 PUT 검증이 플랜 단위를 모르므로 "항목 금액 + 단위"의 정합을 한 요청 안에서 판정할 수 없다. 기존 계획 변환 중간 상태가 10,000배 오독이라 테스트로 막을 지점이 없다.
- **C: 반대.** 부동소수 변환이 실제로 깨진다(아래 검산: `1.005 × 10000 = 10049.999999999998`, `0.07 × 10000 = 700.0000000000001`). "소수 4자리 이하" 판정과 소비처마다 반올림이 생겨, 경계값 테스트가 소비처 수만큼 늘어난다.

## 근거

1. **A의 새 규칙은 대부분 순수 함수로 닫힌다.** `quoteWonOf`·`planBudgetWonOf`·`budgetMergePatch`·`editedQuote`·검증 표가 모두 입력 → 출력이라 경계값 테이블 테스트로 판정된다. 판정 불가능한 곳은 "1단계 번들이 새 키를 지우는가"인데 be가 이미 보존 테스트를 요구했고, 아래에 구체 형태를 정했다.
2. **제안의 숫자는 맞다.** 검산표 참고. 다만 섞인 계획 예시는 "만원 ↔ 원 혼동"은 가르지만 "내림 ↔ 반올림"은 가르지 못한다(1,234,500은 만원 단위로 123.45라서 내림·반올림이 모두 123). 값을 더해야 한다.
3. **위험이 가장 큰 곳이 테스트 없이 두 군데 남아 있다.** (i) PATCH 병합 뒤 두 키 동시 존재는 GET을 가구 전체 조회 실패로 만든다(be R2). (ii) `amount: 0`이 이미 8e30cdd로 들어가 있어 제안의 "0 허용 개정이 필요 없어진다"와 충돌한다(아래 Q1). 둘 다 AC로 못 박으면 판정 가능해진다.

## 제안에서 사실과 다른 곳 (먼저 바로잡을 것)

- 제안 R4의 "추론: 아직 0 허용 코드는 없다. `isInteriorAmount`는 `>= 1`이다"는 **틀렸다.** 브랜치 8e30cdd가 `parseQuote`에 `isInteriorQuoteAmount`(0 또는 `isInteriorAmount`)를 이미 넣었다(`src/lib/utils/validateInteriorPlan.ts:73-75, 157`). 테스트(`src/lib/utils/interiorTbdAmount.test.ts`, `server/interiorPlans/interiorTbdAmount.d1.test.ts`)도 있다. 따라서 "amount 0 허용 개정이 필요 없어진다 → 1단계 diff가 줄어든다"는 주장은 되돌리는 diff가 필요하다는 뜻이 된다. 아래 Q1에서 결정한다.
- 제안은 "1단계(새 키를 모르는 번들, 지금의 065a94b)는 `amountWon`을 미정으로 읽는다"고 했다. **재현해서 확인했다**(아래 "옛 파서 재현").

## 조건 (AC·예시 값으로 추가)

### Q1. `amount: 0`의 처리를 먼저 결정하고 AC로 못 박는다

선택은 둘 중 하나다.

- (a) 8e30cdd의 `amount: 0` 허용을 **되돌린다**(0은 `amountWon`에서만). 0 표현이 하나라 모호하지 않다. 단 이미 있는 테스트 두 파일과 시트 코드를 고치므로 diff가 생긴다.
- (b) 그대로 둔다. 그러면 `amount: 0`과 `amountWon: 0`이 모두 유효한 0이 되고 `quoteWonOf`가 둘 다 "금액 있음 0"으로 읽어야 한다.

어느 쪽이든 AC에 이렇게 쓴다: `quoteWonOf({amountWon: 0}) === 0`, `quoteWonOf({amount: 0})`는 (a)면 검증이 거부해 도달하지 않음 / (b)면 0, `quoteWonOf({}) === undefined`(미정). 구현 함정은 `amountWon || …`·`amountWon ? … : …` 같은 truthy 판정이다. 0이 미정으로 떨어지거나 `amount × 10000` 분기로 샌다. 이 테스트가 그 함정을 가른다. 0일 때 확정하면 지출 예정에 0을 더하고 미정 건수는 세지 않는다(ADR-033 개정과 같은 단언).

### Q2. 검증 표를 값까지 AC로 쓴다 (경계 안팎)

`amountWon`(견적): 통과 `0`, `1`, `9_999_999_999_999`. 거부 `-1`, `1.5`, `"1"`, `null`, `NaN`, `Infinity`, `10_000_000_000_000`, `9_007_199_254_740_993`(안전 정수 밖).
`budgetWon`(총 예산): 통과 `1`, `9_999_999_999_999`. 거부 `0`, `-1`, `10_000_000_000_000`, `1.5`, `"1"`.
`amount`(옛 키): 지금 규칙 그대로(통과 1·999,999,999, 거부 1,000,000,000). `budget`도 같다.
두 키 동시: `{amount: 800, amountWon: 8000000}`는 거부, **같은 환산값이어도** 거부(어느 쪽도 고르지 않음). `{amount: undefined, amountWon: 1}`처럼 값이 `undefined`인 키는 "없음"으로 보는지 한 줄로 정한다(JSON을 거치면 키가 사라지므로 서버에서는 무관하고 로컬 객체 직접 호출에서만 의미). 결과 객체에는 알려진 키만 있고 `Object.hasOwn`으로 확인한다(`amountWon: undefined`가 남으면 실패).
플랜의 `budget` + `budgetWon` 동시도 같은 방식으로 거부한다.

### Q3. 읽기 함수는 한 곳이고 직접 읽기가 없음을 기계로 확인한다

`amount`·`budget`을 직접 읽는 곳이 `quoteWonOf`·`planBudgetWonOf`·항목 예산·지급 표시뿐임을 grep 결과로 PR에 첨부한다. 판정 가능한 형태: `rg "\.(amount|budget)\b" src` 결과가 허용 목록(검증 파일, 두 함수, 항목 예산·지급 표시, 타입, 테스트)에만 있다. 남기면 "일부 화면만 만원"인 조용한 단위 혼동이 생긴다. 이 테스트는 코드 리뷰에서도 판정 가능하지만 자동 테스트로 못 닫는 영역이라 목록으로 고정한다.

### Q4. 섞인 계획 합계·요약·허브·표·CSV를 한 계획으로 닫는다

계획 M: 총 예산 `{budget: 1000}`. 확정 견적 `{amount: 800}`, `{amountWon: 1234500}`, `{amountWon: 1235000}`, 미확정 `{amountWon: 999}`, 확정 미정 1건. 기대: 지출 예정 8,000,000 + 1,234,500 + 1,235,000 = 10,469,500원, 남은 −469,500(예산 초과 469,500원), 미정 1건. 총 예산을 `{budgetWon: 12000000}`로 바꿔 같은 단언을 반복한다(남은 1,530,500). 요약·표 머리·CSV 계 행·인쇄·허브 줄이 모두 같은 숫자를 보여야 한다(`buildInteriorPlanRows`·`summarizeInteriorPlan` 한 곳에서 나온다는 ADR-033 조건 4를 숫자로 확인). 그리고 **표시 문자열을 AC에 고정한다**: 제안의 "결정 필요 2"(1,234,500원 vs 1억 2,345만 6,000원)가 정해지지 않으면 테스트가 기대값을 쓸 수 없다. 정해지기 전에는 "표시 형식은 PM이 정한 뒤 AC에 넣는다"를 미결로 둔다.

### Q5. 상한 합계는 정확성을 직접 단언한다

항목 100개 × 확정 견적 `9_999_999_999_999` → 지출 예정 `999_999_999_999_900`(=1e15 − 100)이 **정확히** 나온다. 총 예산 `9_999_999_999_999`이면 남은 예산은 9,999,999,999,999 − 999,999,999,999,900 = `-989_999_999_999_901`. 이 값이 `Number.MAX_SAFE_INTEGER`(9.007e15) 안이라 부동소수 오차가 없다는 것을 테스트가 증명한다. 표·CSV에서 이 값이 지수 표기(`1e+15`)나 자리 잘림 없이 나오는지도 한 번 본다. 참고: Excel은 15자리를 넘는 숫자 정밀도를 잃는다. 지출 예정 최댓값 999,999,999,999,900은 15자리라 닿지 않지만, 한 자리만 늘려도 CSV를 Excel로 열었을 때 값이 달라진다. 이 한계를 스펙 비고로 남기고 `MAX_WON`을 14자리로 늘리지 않는다는 근거로 쓴다.
`Number.isSafeInteger`는 `MAX_WON` < 2^53이라 상한 검사에 가려지므로, 안전 정수 밖 값(`9_007_199_254_740_993` 등)은 상한 검사로 거부됨을 확인하는 정도면 된다.

### Q6. PATCH `budgetMergePatch`는 시작 상태 × 입력 매트릭스를 표로 고정한다

시작 상태 3가지: S1 `{budget: 1000}`, S2 `{budgetWon: 12345000}`, S0 (둘 다 없음). 입력과 기대(최종 플랜 데이터의 예산 키):

| 입력                                                                      | S1                                            | S2                                  | S0                   |
| ------------------------------------------------------------------------- | --------------------------------------------- | ----------------------------------- | -------------------- |
| `{budget: 500}`                                                           | `budget: 500`, `budgetWon` 없음               | `budget: 500`, `budgetWon` 없음     | `budget: 500`        |
| `{budget: null}`                                                          | 둘 다 없음                                    | 둘 다 없음                          | 둘 다 없음           |
| `{budgetWon: 5000000}`                                                    | `budgetWon: 5000000`, `budget` 없음           | `budgetWon: 5000000`, `budget` 없음 | `budgetWon: 5000000` |
| `{budgetWon: null}`                                                       | 둘 다 없음                                    | 둘 다 없음                          | 둘 다 없음           |
| `{name: "새 이름"}`만                                                     | 예산 키 **변하지 않음**                       | 변하지 않음                         | 변하지 않음          |
| `{budget: 500, budgetWon: 5000000}`                                       | 400                                           | 400                                 | 400                  |
| `{budget: 500, budgetWon: null}`                                          | 정의 필요(허용이면 `budget: 500`, 거부면 400) | 같음                                | 같음                 |
| `{budgetWon: 0}` / `{budgetWon: 10_000_000_000_000}` / `{budgetWon: "1"}` | 400                                           | 400                                 | 400                  |

- "이름만 바꾸는 요청이 예산 키를 건드리지 않는다"가 핵심이다. 현재 `PlanSettingsSheet`는 이름만 바꿔도 `budget`을 보내므로, 조건 4(바뀐 칸만 보내기)의 테스트는 **요청 본문에 `budget` 키가 없음**을 직접 단언해야 한다(S2 데이터 위에서 이름만 바꾼 뒤 `budgetWon`이 남는지도 같이).
- 마지막에서 두 번째 행(`budget` 숫자 + `budgetWon: null`)은 제안이 "두 키를 모두 숫자로 주면 400"만 정했으므로 허용/거부를 정해야 한다. 정하지 않으면 구현마다 다르다.
- 서버(`parsePlanPatchRequest`의 알려진 키 목록: `["name","budget","listingId","spaces"]`, `server/interiorPlans/parseInteriorPlanRequests.ts:67`)에 `budgetWon`이 없으면 `{budgetWon: n}`만 오는 요청이 "알려진 키 하나 이상" 검사에서 400이 된다. 이 행(`{budgetWon: n}` 단독 → 200)이 빠지지 않게 한다.
- 순수 함수 `budgetMergePatch` 표 테스트 + D1 하네스에서 같은 표의 4행(`budget`, `budget: null`, `budgetWon`, `budgetWon: null`) × S1·S2. D1 쪽은 **`SELECT data`로 원문을 읽어** `budgetWon` 키가 `null`이 아니라 아예 없는지 단언한다(제안의 "추론: `json_patch`가 null로 키를 지운다"를 테스트로 확정). `budgetWon: null`이 남으면 파서가 `null`을 거부해 GET이 통째로 실패하는데, 그때 원인이 PATCH인지 바로 보이도록 원문 단언을 따로 둔다.
- 로컬 `applyPlanPatch`(`src/lib/utils/interiorPlanStorage.ts`)는 같은 표를 로컬 저장소 끝에서 끝으로 한 번 더 돌린다(공용 함수를 쓴다는 설명만으로는 연결 누락을 못 잡는다).

### Q7. 보존(1단계 번들이 새 키를 지우지 않는다) 테스트의 구체 형태

원칙: 새 키를 가진 데이터를 만든 뒤 **다른 쓰기**를 하고, 원문에서 그 키가 같은 값으로 남는지 본다.

- 로컬: 계획 X(견적 `amountWon: 1234500`·`amountWon: 0`, `budgetWon: 12345000`)와 계획 Y를 저장소에 넣는다. Y에 줄 추가·수정·삭제·확정 토글·이름 PATCH를 각각 한 뒤 `storage.getItem` 원문을 `JSON.parse`해서 X 부분이 쓰기 전과 `toStrictEqual`로 같다. (로컬 `commit`이 스냅샷 전체를 재직렬화하므로 파서가 새 키를 담아야만 통과한다.)
- 같은 계획 안: 형제 견적 두 개 중 하나만 편집(`editLineInput`)하고 다른 견적의 `amountWon`이 그대로다.
- 서버 D1: 항목에 견적 [A `amountWon: 1234500`, B `amount: 800`]을 PUT → GET → B를 편집해 PUT → GET `toStrictEqual`로 A가 그대로. 계획에 `budgetWon`이 있을 때 계획 이름 PATCH 후 `budgetWon`이 그대로(앞 Q6의 name-only 행과 같다).
- 가져오기(`/import`)와 항목 복사·"추가 비용 가져오기" 경로: 새 키가 들어 있는 계획을 import해 GET `toStrictEqual`로 왕복한다.
- **버그를 되살려 실패를 확인한다**: 구현 후 qa가 `parseQuote`에서 `amountWon` 복사를 임시로 지워 위 테스트가 실패하는지, `editedQuote`에서 `amountWon`을 빼는 줄을 지워 "1단계 편집은 `amount`를 쓰고 `amountWon`을 빼야 한다" 테스트가 실패하는지 확인하고 되돌린다. 실패하지 않으면 그 테스트는 아무것도 지키지 않는다.

### Q8. `editedQuote` 두 단계 규칙을 표로 닫는다

1단계: 입력 견적 `{amountWon: 1230000}`(시트에는 `"123"`) 저장 → `amount: 123` 있고 `amountWon` **없음**. 입력 견적 `{amount: 800}` 편집 → `amount`만. 미정(키 없음) 줄에 값을 넣으면 `amount`만 생기고 `amountWon` 없음.
2단계: `amountWon` 있고 `amount` **없음**(옛 줄 `{amount: 800}`을 편집하면 `amountWon: 8000000`이고 `amount` 키 삭제). 금액을 비우면 둘 다 없음(`amount: undefined`·`amountWon: undefined`가 남으면 실패).
형제 견적은 원래 키 그대로(옛 줄을 다시 쓰지 않는다). 이 규칙이 AC-0(추가만)과 맞는지 `toStrictEqual`로 확인한다.

### Q9. 1단계 시트가 원 단위 값을 만원으로 채우는 규칙의 경계

`amountWon % 10000 === 0`이면 만원 문자열, 아니면 `""`. 경계 값: `amountWon: 10000` → `"1"`, `20000` → `"2"`, `10001` → `""`, `9999` → `""`, `1234500` → `""`, **`0` → `"0"`이 되고(`0 % 10000 === 0`) 1단계 입력 검증이 0을 거부하므로 필수/하한 오류가 난다. 제안은 "0원은 1단계 입력 규칙에 걸려 다시 입력"이라고만 썼으니 `""`로 열지 `"0"`으로 열지 정한다.** (이 값에 대한 현재 `interiorLineDraft.ts:41`의 `String(quote.amount)`와의 차이를 테스트가 드러낸다.) 어느 경우에도 쓰기는 0회이고 사용자가 만원으로 다시 입력해야 저장된다. `amountWon: 12000000`(1,200만원)이 `"1200"`이 되는지 큰 값도 한 번 본다.
총 예산 설정 시트도 같은 규칙: `budgetWon: 12345000` → 칸은 `""`(만원으로 안 떨어짐), 건드리지 않고 이름만 바꾸면 요청 본문에 `budget` 키가 없다.

### Q10. 목록·가리기·0원 표시

가리기 중에는 원 단위 금액(`1,234,500원`)도 구분자까지 통째로 빠지고 `innerHTML`·`aria-label`에 숫자가 없음을 허브·요약·표·목록 네 곳에서 확인한다(ADR-033 조건 6을 원 단위 포맷으로 다시). 미정 줄에는 "0원"·"0만원"이 나오지 않는다. 금액이 0인 줄은 "0원"이 나오고 미정이 아니다(둘의 구분).
홈 허브는 단위가 섞인 카드 두 개(계산기 만원, 우리 집 원)가 한 화면에 나란히 오는 상태를 스냅샷 한 장으로 고정한다. PM이 형식을 정한 뒤 문자열을 AC에 넣는다.

## 옛 파서 재현 (실행해서 확인함)

세 번들의 `parseInteriorPlans`를 같은 입력으로 돌렸다. 입력: 견적 하나(`amountWon: 1234500`, `amount` 없음) + 플랜 `budgetWon: 10000000`, 견적 확정.

| 번들                        | 결과                               | 의미                                                                                                                                                         |
| --------------------------- | ---------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| db36b56 (1단계 이전)        | `status: "corrupt"`                | 견적에 `amount` 키 없음 → 손상. ADR-033이 막으려는 위험과 같다                                                                                               |
| 065a94b (현재 브랜치 1단계) | `status: "ok"`                     | 견적의 `amount`·`amountWon` 모두 없는 것으로 읽는다(미정). **`amountWon`·`budgetWon` 키는 조용히 버려진다.** 이 스냅샷으로 쓰기 한 번이면 로컬에서 영구 손실 |
| 065a94b, `amount: 800`만    | `status: "ok"`, `amount: 800` 유지 | 비교용                                                                                                                                                       |

그리고 한 가지를 더 확인했다: 플랜의 `budgetWon`만 있는 경우(견적 `amount`는 있음)는 어느 옛 번들에서도 **손상으로 읽히지 않고** 예산이 없는 것으로 조용히 읽힌다. 즉 `budgetWon`은 손상 경고도 없이 사라지는 쪽의 위험이라, `amountWon`보다 더 조용하다. P⁺ 기록에 `budgetWon` 플랜을 넣어 "ok이지만 `budget`·`budgetWon` 둘 다 없음"을 한 줄로 남긴다.

재현 방법(저장소를 건드리지 않음): `git archive <커밋> src/lib | tar -x -C <빈 디렉토리>`로 두 커밋의 `src/lib`을 따로 풀고, `node_modules`를 심볼릭 링크로 연결하고, `@` 별칭을 `src`로 둔 vitest 설정과 위 입력으로 `parseInteriorPlans(JSON.stringify({version:1, plans:[…]}))`를 호출해 `status`를 단언한다(`console.log`는 이 설정에서 안 보이므로 `throw new Error`로 결과를 내거나 `expect(...).toBe`로 쓴다). 작업은 `.../scratchpad/old`(db36b56)와 `.../scratchpad/cur`(065a94b)에서 했고 제품 저장소 파일은 건드리지 않았다. ADR-033 조건 8의 "직전 커밋 파서로 P⁺ → corrupt, 다음 커밋 파서로 → ok" 기록과 같은 형식이고, P⁺에 `amountWon`·`budgetWon`을 추가해 두 번 기록한다(1단계 완료 때 기대: db36b56 corrupt, 새 1단계 파서 ok이며 키 보존).

## AC-0 (추가만, 옛 데이터를 다시 쓰지 않는다)

AC-0의 판정 문장을 이렇게 쓴다: 옛 키(`amount`·`budget`)만 가진 계획 N개를 저장해 둔 상태에서 새 코드로 **읽기만 하면** 원문이 바이트 단위로 같고, 다른 계획·견적을 쓸 때도 건드리지 않은 견적의 키는 그대로다. `parseInteriorPlans`가 `amount`를 `amountWon`으로 **정규화하지 않는다**는 제안(파서는 저장 형태를 바꾸지 않는다)을 `toStrictEqual`로 확인하는 것이 이 AC의 핵심 테스트다(GET 왕복 `toStrictEqual`을 ADR-033 조건 3에서 그대로 쓴다). 서버: 옛 키로 저장된 항목을 GET하면 같은 키로 나오고, PUT 없이 마이그레이션 SQL이 데이터를 바꾸지 않는다.

## 리스크

1. **`amount: 0`과 새 키의 이중 0.** Q1을 정하지 않으면 두 표현이 공존해 `quoteWonOf`의 truthy 함정과 표시 분기가 늘어난다.
2. **PATCH 두 키 동시 존재는 가구 전체 조회 실패.** 한 요청의 버그가 모든 계획을 읽지 못하게 한다(be R2). 거부 정책은 테스트하기 쉽지만 장애 폭이 크다. 완화로 "두 키가 있으면 `amountWon`이 이긴다"로 읽는 선택지가 있으나 읽기 분기가 늘고 규칙이 숨은 우선순위가 된다. qa는 지금 제안(거부 + 쓰기 쪽에서 막는 테스트)을 따르되, 모든 쓰기 경로(POST·PUT·import·PATCH·로컬 편집)가 두 키를 만들 수 없다는 테스트를 요구한다.
3. **표시 형식 미결.** 문자열을 모르면 AC가 숫자 의미만 지키고 화면은 판정 불가다. 구현 전에 정해야 한다.
4. **게이트 기간의 정밀도 손실(be R3).** 2단계 기기가 쓴 `1,234,500원`을 1단계 탭이 다시 입력받는 흐름은 자동 테스트로 닫지만 실제 두 탭 확인은 수동이다.
5. **옛 번들의 `budgetWon` 조용한 손실**(위 재현). 설정 시트 "바뀐 칸만 보내기"를 배포 전에 넣지 않으면 이름 변경이 예산을 지운다.

## 화면에서 직접 확인할 항목 (자동 테스트로 못 닫는 것)

- 같은 origin·같은 포트의 두 탭: 1단계 번들 탭에서 이름만 바꿨을 때 다른 탭에서 쓴 총 예산(원 단위)이 남는지, 원 단위 견적(1,234,500원)이 있는 줄을 1단계 탭에서 열었을 때 견적 칸이 비고 다시 입력을 요구하는지.
- 1,234,500원·0원·9,999,999,999,999원을 입력/저장한 뒤 새로고침 → 표시·CSV(Excel로 열기)·인쇄 미리보기 자리수와 줄바꿈.
- 모바일 폭에서 13자리 원 금액이 시트·요약·표에서 잘리지 않는지.
- 가리기 켠 상태의 요약·표·허브에서 원 단위 숫자가 보이지 않는지.

## 추가해 달라는 AC 요약 (예시 값 포함)

- AC-W0 옛 키만 가진 데이터는 읽기만 하면 원문 불변, 쓰기는 건드린 견적만 바뀜.
- AC-W1 검증 표(Q2): 통과 0·1·9_999_999_999_999, 거부 10_000_000_000_000·1.5·"1"·null·NaN, 두 키 동시 거부.
- AC-W2 `quoteWonOf`·`planBudgetWonOf`: `{amount:800}`→8,000,000, `{amountWon:0}`→0, `{amountWon:1}`→1, `{}`→미정.
- AC-W3 계획 M 합계(Q4): 10,469,500원 / 남은 −469,500(초과) / 미정 1건, 총 예산 12,000,000이면 남은 1,530,500.
- AC-W4 상한 합계(Q5): 100 × 9_999_999_999_999 = 999_999_999_999_900, 남은 −989_999_999_999_901.
- AC-W5 PATCH 매트릭스(Q6), D1 원문 단언 포함.
- AC-W6 보존(Q7)과 `editedQuote` 두 단계(Q8).
- AC-W7 1단계 시트·설정 시트 채우기(Q9), 이름만 바꿔도 요청에 `budget` 키 없음.
- AC-W8 가리기·0원 구분·허브 혼합 표시(Q10).
