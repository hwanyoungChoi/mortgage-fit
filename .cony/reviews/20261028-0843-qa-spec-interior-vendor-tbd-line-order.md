# 우리 집 업체 미정·줄 끌어 옮기기 스펙 — qa 검토

날짜: 2026-10-28

판정: **조건부 찬성**

스펙 전문을 읽고 현재 코드(f5ad2b0)와 대조했다. 예시 값은 직접 계산했다.

## 근거

1. AC-0은 보존의 위험 경로(옛 파서, 로컬 patch 합치기, 서버 PATCH, import)를 정확히 짚었고 대부분 판정 가능하다.
   - 확인한 사실: 현재 `parseQuote`는 `vendor` 없는 견적을 null로 만들어 전체 corrupt가 된다(`validateInteriorPlan.ts:169-175`). 알려진 키만 돌려주므로 `lineOrder`는 조용히 버려진다(`:232-255`). 스펙의 "V → corrupt, P+lineOrder → ok" 예측과 코드가 일치한다.
   - 스펙 인용 줄 번호도 맞다. `validateInteriorPlan.test.ts` 188~193행은 반전 대상이 192행(`vendor: undefined`)뿐이다. `handleInteriorPlans.ts:35`의 16KB와 PATCH 경로의 `json_patch`도 맞다.
2. 수용 기준 예시 값은 계산해 보니 맞다. 다만 구분력이 부족한 예시가 3곳 있다(아래 "예시 보강").
   - 지출 예정: 1,800,000 + 3,700,000 + 2,500,000 + R6 미정 0 + R8 300,000 = 8,300,000원. 총 예산 1000만원 기준 남은 예산은 1,700,000원이다. "금액 미정 1건"은 R6이다. R9는 미확정이라 세지 않는다.
   - CSV 11행(머리 1 + 줄 9 + 계 1)의 순서와 글자가 묶음 규칙과 일치한다.
   - AC-2의 6개 순서 예시는 모두 읽기 규칙대로 나온다.
3. 가장 큰 실행 위험은 **jsdom에서 dnd-kit 끌기를 자동 테스트할 수 있다는 가정**이다.
   - 이 저장소에는 dnd-kit 끌기 테스트가 하나도 없다. `들었습니다`·`ArrowDown`·`roledescription` 검색 결과가 소스와 css뿐이다. `CompactListingList`는 테스트 없이 배포됐다.
   - 그래서 AC-4의 "저장 목록 기존 끌기 테스트가 diff 0으로 통과"는 지킬 대상이 없는 기준이다. 저장 목록 끌기는 전역 승격 리팩터링(`CompactListingList`가 같은 export를 import)에서 **회귀 보호가 0**이다.

## 리스크

- **R1. dnd-kit jsdom 실현 가능성 미확인.** 여러 위험이 겹친다.
  - 레이아웃: `getBoundingClientRect`가 전부 0이라 `sortableKeyboardCoordinates`·`closestCenter`가 이동 대상을 못 찾는다. 줄마다 rect를 스텁해야 한다.
  - 포인터: 꾹 누르기(250ms)는 가짜 타이머 + mousedown/touchstart로 가능하다. 그 뒤 위치 이동은 rect 스텁이 필요하다.
  - 놓은 뒤 클릭 억제(시트가 안 열림)는 dnd-kit 내부 동작이라 jsdom에서 달리 보일 수 있다.
  - 스파이크 없이 AC를 확정하면 구현 막바지에 "자동 불가 → 수동" 항목이 쏟아진다.
- **R2. "흐린 글자"는 jsdom에서 판정할 수 없다.** 기존 `tbdAmount`도 스타일 단언이 없다(`PlanLines.module.css:155`). 클래스명 단언 + 수동 대비 측정으로 제한된다.
- **R3. 로컬과 서버의 빈 배열 처리가 다르다.**
  - 검증 함수는 `[]`를 받고 키를 쓰지 않는다(삭제처럼 동작).
  - 서버 PATCH는 `[]`를 400으로 막는다.
  - 로컬 `updatePlan(id, { lineOrder: [] })`는 스펙에 없다. 같은 `source.updatePlan` 뒤에서 세 출처가 다르게 반응할 수 있다.
- **R4. 서버 본문 한도 불일치.** D2는 PATCH만 128KB로 올린다.
  - `POST /api/interior-plans`(135행)는 16KB 그대로인데 `plan.lineOrder?`를 받는다. 줄 수가 많으면(대략 230개 초과) 413이 된다.
  - 화면은 안 보내지만 API 계약 표에는 있다. "받는다"와 "한도" 중 하나를 정해야 한다.
  - `/import`는 1MB라 문제 없다.
- **R5. 2단계 게이트는 자동으로 막을 수 없다.** main에 필수 체크가 없고 auto-merge를 쓰지 않으므로, qa 기록(`board.mjs`가 확인)이 유일한 기계적 관문이다. 기록 내용이 자기 보고에 그치면 구멍이 된다.
- **R6. 옛 파서 재현이 절차로만 적혀 있다.** (g)는 "결과를 기록"이라고만 쓰여 있어 재현 방법이 사람마다 달라진다.

## 조건

### C1. dnd-kit 스파이크를 먼저 한다

구현 착수 전, 또는 1-3 첫 커밋에서 다음 한 개 테스트가 jsdom에서 도는지 확인한다.

- 묶음 2개, 줄 rect 스텁, 키보드 Space → ArrowDown → Space로 `onReorder`가 한 번 불린다.
- 되면 AC-4 키보드·알림·Esc는 자동 테스트로 둔다.
- 안 되면 대안은 다음과 같고, 어느 AC가 수동으로 넘어가는지 스펙에 먼저 적는다.
  - 드롭 결정을 순수 함수 `lineOrderAfterMove` + `onDragEnd` 핸들러 단위로 뺀다.
  - 센서 설정(`LONG_PRESS`, `KEYBOARD_CODES`, 안내 문장)은 공유 export 값을 직접 단언한다.
  - 실제 끌기는 수동으로 한다.
- 저장 목록 끌기 테스트가 없다는 사실을 스펙에 반영한다. 승격 리팩터링에는 같은 스파이크 방식으로 `CompactListingList` 키보드 끌기 테스트를 **리팩터링 전에** 한 개 추가한다(테스트만 추가, 제품 코드 수정 없음). "기존 테스트 diff 0" 문구는 "승격 전에 추가한 테스트가 승격 후에도 통과"로 바꾼다.

### C2. 예시 보강 (구분력이 없는 값)

- **AC-2 "빈 줄 대체 자리"** (`L + ["item-z:q3", "item-y:", "item-x:q1", "item-x:q2"]` → 욕실 → 도배)는 버그 ④(`item.id:` 대체 자리 삭제)를 잡지 못한다.
  - 대체 자리가 없어도 Y는 위치 없음으로 맨 끝에 붙고, 도배 묶음이 어차피 욕실 뒤에 오기 때문에 결과가 같다.
  - 대체 값: `["item-y:", "item-z:q3", "item-x:q1", "item-x:q2"]` → 기대 [도배: Y] → [욕실: Z, X q1, X q2]. 대체 자리가 없으면 욕실이 먼저 와서 실패한다.
  - Y를 `item-y:qn`으로 채운 뒤에도 같은 순서인지 이 배열로 확인한다.
- **AC-3 끌기 저장**의 `P에서 R2를 R1 위로`는 전역 `arrayMove`를 잘못 쓴 구현(버그 ⑤의 변형)도 통과시킨다. 묶음이 기본 순서에서 연속이어서다. 다음을 더한다.
  - P⁺에서 도배 묶음은 R1, R2, R7이고 기본 항목 순서에서 R7은 R3~R6 뒤에 있다. R7을 R1 위로 놓으면 `["r7:rq7","r1:rq1","r2:rq2","r3:rq3","r4:rq4","r5:rq5","r6:rq6"]`이다.
  - `lineOrder`가 이미 묶음 순서를 바꾼 상태(예: AC-2 마지막 예시 `["r3:rq3","r1:rq1","r4:rq4","r2:rq2","r5:rq5"]`)에서 도배 묶음을 끌면 결과는 `[r3,r4,r5,r2,r1]` 형태, 즉 보이는 묶음 순서를 유지한다.
  - 끌기 두 번 연속: 두 번째 결과에 첫 번째 이동이 남아 있다.
- **AC-0(a)** "변경 전과 `toStrictEqual`"은 변경 후 코드로 기대값을 만들면 순환이 된다. 변경 **전**(f5ad2b0) 파싱 결과를 리터럴 JSON 골든으로 먼저 커밋한다.
- 구분 바꾼 줄(U7), 위치 병합의 세부 규칙은 AC가 비어 있다(아래 "순서 병합 경계").

### C3. 순서 병합 경계를 AC-2에 더한다

기대값은 읽기 규칙에서 직접 도출했다.

1. **자기 key와 `item.id:`가 둘 다 있으면** 자기 key의 자리가 이긴다. 예: `["item-y:", "item-x:q1", "item-y:qn"]`에서 Y(`item-y:qn`)는 3번째 자리다.
2. **견적이 여러 개인 항목에 `item:`만 있으면** 모든 견적이 같은 위치를 받고, 같은 위치끼리는 기본(견적) 순서를 유지한다.
3. **견적 하나를 지운 n≥2 항목**의 남은 견적은 자기 자리를 유지한다. **마지막 견적을 지워 견적 없는 줄이 되면** key가 `item:`로 바뀌어 대체 자리가 없으면 위치 없음이 된다(맨 끝). 이 동작을 AC로 고정하든 개선하든 정하고, 어느 쪽이든 테스트로 남긴다.
4. **구분을 바꾼 줄(U7)**: P + `["r2:rq2","r1:rq1","r3:rq3","r4:rq4","r5:rq5"]`에서 R2의 구분을 "욕실"로 바꾸면 R2가 가장 이른 위치라 묶음 순서가 [욕실: R2, R3, R4, R5] → [도배: R1]로 뒤집힌다. 이 반전이 스펙의 의도인지 예시로 확인받는다.
5. **구분 앞뒤 공백**: "도배 "와 "도배"는 같은 묶음이다(trim). 이동 함수의 `groupTrade`도 trim 기준인지 단언한다.
6. **`lineOrder` 전부 지워진 key**: 아무 줄도 매칭되지 않으면 결과가 기본 순서와 `toStrictEqual`이다.
7. 속성 테스트(작은 완전 열거): P의 5줄 순열 몇 개 × `lineOrderAfterMove`를 적용한 뒤 `buildInteriorPlanRows`로 다시 읽으면 "그 묶음 안만 arrayMove한 목록"과 같다(왕복 불변식). 구현을 몰라도 쓸 수 있는 가장 강한 단언이다.
8. `lineOrderAfterMove`: 줄 1개 묶음, 없는 activeKey/overKey, 다른 묶음의 overKey, active == over는 모두 null(쓰기 없음)이고 결과에 지워진 key·중복이 없으며 길이 = 현재 줄 수.

### C4. 빈 배열 정책을 하나로 정한다 (R3)

- 서버가 400이면 로컬 `updatePlan({ lineOrder: [] })`도 같은 실패를 내거나, 둘 다 키 삭제로 통일한다.
- 결정된 값을 AC-0(b)에 로컬·서버 각 한 줄로 고정한다.
- `lineOrder: null` = 삭제는 로컬(`applyPlanPatch`)에도 테스트한다. 스펙에는 서버 `SELECT data`만 있다.

### C5. D2 한도 경계와 POST 한도 (R4)

- 서버 하네스에 다음을 더한다.
  - 줄 key 500개 × 최대 길이(129자)의 PATCH가 200이다.
  - 한도 바로 안(128KB)은 200이고, 바로 밖(+1바이트)은 413이다. `readJsonBody`는 `Content-Length`와 누적 바이트가 `> maxBytes`일 때 413이므로 경계는 한도 정확히 = 통과, +1 = 거부다.
  - 다른 PATCH 키(이름·예산)와 함께 보내도 같은 한도가 적용된다.
- `POST /api/interior-plans` + 큰 `lineOrder`와 항목 POST·PUT 16KB 유지가 서버 코드 diff 0과 맞는지 한 줄 테스트로 고정한다.

### C6. 표시 AC를 grep이 아닌 렌더 출력으로 판정한다

`rg "\.vendor\b" src`는 PR 첨부용 점검에는 좋다. 판정은 표면별 렌더 테스트로 한다.

- 현재 `vendor`를 읽는 곳은 소스에서 직접 확인했다: `LineRow.tsx:22,59,63`, `PlanTable.tsx:48`, `buildInteriorPlanTable.ts:43`, `interiorPlanTableToCsvRows.ts:23`, `interiorLineDraft.ts:40`, `interiorLineWrites.ts:45`, `ItemSheet.tsx:252`. 스펙의 표는 이 목록과 일치한다.
- 이 표면마다 V에서 R8·R9를 렌더해 다음을 단언한다.
  - 목록 첫 줄·둘째 줄: 텍스트가 비어 있지 않다. `undefined` 문자열이 없다. 접근 이름이 AC-1 문자열과 `toBe`로 같다.
  - 표·인쇄: 업체 칸은 R8·R9가 "미정", L의 Y(견적 없음)가 빈칸이다.
  - CSV: 11행 전체를 `toStrictEqual`(견적 없음과 미정이 CSV에서도 구분된다).
  - 허브·요약 텍스트.
  - 새 `DragOverlay`·키보드 알림 문구(`nameOf` 재사용 확인).
- "흐린 글자"는 `tbdAmount` 계열 클래스명 단언(예: `className`이 `/tbdAmount/`와 매칭)과 수동 대비 측정(4.5:1)으로 나눈다(R2).
- 업체 이름이 글자 그대로 "미정"인 견적과 업체 키 없음을 표 모델 단위에서 구분하는 단언을 둔다(버그 ⑥의 직접 검출).

### C7. AC-0 읽기-쓰기 0 검증 방법을 구체화한다

- 원문 `===`만으로는 부족하다. 같은 내용을 같은 형식으로 다시 쓰는 경로가 있을 수 있다. 시드를 **들여쓴 JSON**으로 하고(스펙대로) 추가로 `setItem`·`removeItem` 스파이 호출 0회를 단언한다.
- 로그인·가구 모드는 `api.writes()`가 `[]`이다. 로그아웃 모드는 스토리지 스파이 0회이다.
- 이 흐름은 R1(dnd-kit jsdom) 결과에 따라 일부(꾹 눌러 들었다 놓기, 다른 묶음 위에 놓기)가 키보드 경로로만 검증된다. 그 사실을 기록한다.
- 탭 간 `storage` 이벤트(V의 `lineOrder` 포함 원문)는 `corrupt`가 되지 않는지, 이후 목록 순서까지 단언한다.

### C8. 옛 파서 재현 절차를 명시한다 ((g))

영구 테스트는 두지 않되 절차를 고정한다.

1. 새 코드 트리에서 V 원문 JSON과 "P + `lineOrder`" 원문 JSON을 파일로 내보낸다(`JSON.stringify`). 이 JSON이 단일 출처다.
2. `git worktree add <scratch>/old f5ad2b0`(1단계 직전 main). `node_modules`는 심볼릭 링크로 연결한다.
3. 옛 트리에서 임시 테스트 한 개가 `parseInteriorPlans(rawText)`에 두 원문을 넣고 V → `status: "corrupt"`, P+lineOrder → `ok`이며 `lineOrder`만 없음을 단언한다.
4. 옛 `createInteriorPlanStore`로 `lineOrder`가 든 시드에 `addItem` 한 번을 한 뒤 원문에서 `lineOrder`가 사라지는지도 기록한다(스펙의 "예상된 동작"을 데이터로 남긴다).
5. 결과(통과·실패 로그)를 qa 기록에 붙이고 worktree는 지운다. 태스크 2에서는 1단계 커밋으로 같은 절차를 되풀이해 V → `ok`를 확인한다.

### C9. 일부러 넣는 버그 목록 ((h)) 보강

스펙의 ①~⑦ 외에 다음을 더한다. 각각 어떤 테스트가 실패하는지 이름을 기록한다.

- ⑧ `parseLineOrder`가 중복 / 501개 / 정규식(`"a:b:c"`, `":q"`)을 통과시킨다.
- ⑨ 서버 `parsePlanPatchRequest`가 `lineOrder`를 모르는 키로 처리하거나(조용히 무시) `[]`를 통과시킨다.
- ⑩ 서버 PATCH가 `json_patch` 대신 전체 교체로 바뀌어 다른 키 PATCH가 `lineOrder`를 지운다.
- ⑪ `lineOrderAfterMove`가 묶음을 기본 순서로 이어 붙인다(보이는 묶음 순서를 무시한다). C2의 AC-2 마지막 예시 기반 케이스가 잡아야 한다.
- ⑫ 제자리/다른 묶음/Esc에서도 쓰기가 일어난다.
- ⑬ 저장 실패 시 `pendingOrder`가 풀리지 않거나 실패 안내가 안 뜬다. 다음 성공 끌기에서 안내가 안 지워진다.
- ⑭ [확정] 체크 라벨이 끌기 손잡이가 된다(listeners 위치 오류).
- ⑮ `/import` 경로가 `lineOrder`를 버린다.
- ⑯ `parseQuote`가 `vendor: undefined` 키를 남긴다(`Object.hasOwn` 단언).
- ⑰ 목록 `LineRow`가 업체 미정에서 빈 첫 줄이나 빈 접근 이름을 낸다.
- ⑱ 표/CSV가 견적 없음과 업체 미정을 한 문자열로 합친다(⑥의 CSV 쪽).

각 버그는 하나씩 켰다 끄고 실패한 테스트 이름을 기록한다. 실패하지 않으면 그 테스트는 지키는 것이 없다.

### C11. 상태 변화 테스트의 세부

- **끄는 중 재조회**: 키보드로 들고 → `fakePlanApi`로 재조회 결과 변경(R1 삭제, R6 추가) → 끄는 동안 DOM 순서가 든 순간 그대로 → 놓으면 PATCH 본문에서 R1 key는 없고 R6은 맨 끝 자기 묶음. `console.error`·`console.warn`을 스파이해서 중복 key 경고 0을 단언한다.
- **401**: 이 저장소의 로그인 쓰기 실패 하네스에서 401을 내는 방법(기존 홈 세션 만료 테스트)을 재사용한다. 목록 위 `role="alert"`가 없고 세션 만료 안내가 뜬다. 출처 전환 뒤 로컬 계획이 보이는 것까지 확인한다.
- **저장 실패 안내 해제**: 실패 → 다음 성공 끌기 → 안내가 사라진다.
- **저장 지연 중**: 응답을 보류하고 그동안 다른 줄 키보드 들기가 안 되고, 시트 열기와 확정 체크는 된다. 성공하면 순서가 유지된다(깜빡임은 중간 렌더 순서 스냅샷으로 검증: 놓은 순서 → 놓은 순서, 원래 순서 중간 렌더 없음).
- **줄 500개**: `lineOrderAfterMove`와 서버 PATCH는 자동으로, 화면 500줄 렌더+끌기는 시간이 걸리므로 저장 한도(C5)는 서버 하네스, 키보드 끌기는 30줄 정도로 줄이고 500은 순수 함수·서버에서 본다.
