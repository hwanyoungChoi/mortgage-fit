## 1. 가장 위험한데 테스트가 없는 경로 top 5

1. 함께 쓰기 수락·나가기 batch (`server/household/handleHousehold.ts` accept 191-228, leave 256-276)
   - 지키는 것: 수락 시 B 매물 숨김, 나가기 시 숨김 해제, A·B의 예산·순서 복원, 동시 수락·나가기에서 한쪽만 성공.
   - 깨지면: ③의 `householdExists` 가드나 ①의 `used_at`/`accepted_by` 조건이 빠지면 가구 없이 B 매물만 숨겨진 채 사라져 보이거나(수락 실패인데 매물 소실), 나가기에서 `hidden_household_id = NULL` 복원 문장이 빠지면 B 매물이 영구히 보이지 않는다. 나가기 ①의 `inviter_id` 조건이 틀리면 A의 예산·순서가 B 값으로 덮인다. 성공 판정 인덱스(`results[results.length-1]`, `[, , , cleared]`)가 문장 추가로 밀리면 성공을 404/204로 잘못 말한다.
   - 이유: 여러 문장이 서로 가드에 의존하고 순서가 의미를 가진다. 문장 하나를 추가·재배치하면 조용히 깨진다.
2. 매물 범위 SQL과 그 사용처 (`server/household/householdScope.ts` `LISTING_SCOPE_SQL`, `server/listings/handleListings.ts` 전부)
   - 지키는 것: 혼자 쓰는 사용자는 `user_id = ?1`과 결과가 같음(AC-0), 숨긴 행 제외, 500개 상한(INSERT…SELECT 한 문장), import의 id 중복 건너뛰기, PUT이 memo·status를 보존, PATCH가 다른 필드를 되돌리지 않음.
   - 깨지면: `hidden_household_id IS NULL` 누락 시 A와 B의 같은 id 매물이 섞이거나 PUT·DELETE가 숨긴 행에 닿는다. PUT의 `json_patch`/`json_extract` 모양이 바뀌면 가격 수정 때마다 메모·상태가 지워진다(사용자 입력 손실). import의 `IMPORT_OVER_LIMIT_SQL`이 틀리면 500개를 넘겨 들어가거나 정상 재시도가 막힌다.
3. 기기 로컬 → 계정 이전 (`src/hooks/useAccountImport.ts`, 기록 어댑터 `accountImportStorage`·`userIdRecordStorage`)
   - 지키는 것: 로컬 원본은 읽기만 함(AC-0), 성공한 배치의 id만 기록, 지운 매물이 되살아나지 않음, 본문 400KB·100개 분할, 다른 계정 기록이 있으면 1회 확인, 실패 시 재시도.
   - 깨지면: 기록 시점이 요청 전으로 옮겨지면 실패한 매물이 영구 미이전(로컬엔 있으나 계정엔 없음)이다. 기록 누락이면 서버에서 지운 매물이 다음 로그인에 되살아난다. `toBatches`가 틀리면 413으로 큰 메모 매물 이전이 통째로 실패한다. 나아가 결함 후보 D1(아래)이 여기에 있다.
4. 로컬 저장소 읽기·검증 (`listingStorage.parseListings`/`validateListingFields.isListing`, `budgetStorage.parseBudget`, 순서·가리기·글자 크기 어댑터)
   - 지키는 것: 기존 키 원문 불변(AC-0), 하나라도 어긋나면 전체 corrupt(조용한 손실 방지), 손상 목록은 [초기화] 전까지 보존.
   - 현황: `listingStorage.test`가 매물 파싱 경계는 일부 덮는다. 그러나 `validateListingFields`의 메모 5,000자·상태·추가 비용 경계, `parseBudget`, 어댑터들은 직접 테스트가 없다.
   - 깨지면: 검증이 한 칸만 엄격해져도(예: 새 필드를 필수로, 메모 상한 하향, 알 수 없는 상태 값 거부) 사용자의 정상 저장 목록 전체가 corrupt로 판정되어 [초기화] 안내가 나온다. 이미 로그에 "옛 탭에서 500자 초과 메모 목록이 손상으로 보임" 사례가 있다. 다음 사이클(인테리어 플래너)이 매물 데이터에 필드를 더하면 같은 위험이 반복된다.
5. 직접 순서와 클라이언트 쓰기 흐름 (`src/lib/utils/sortListings.ts`, `isListingOrder.ts`, `useListingOrderSource`, `useListingSource`의 쓰기 실패 롤백·404 처리, 서버 `listingOrder` PUT/import COALESCE)
   - 지키는 것: 순서에 없는 새 매물은 맨 위에 보임(함께 쓰기 AC-5), 지워진 id는 무시, 순서 API는 중복·500개 초과·id 규칙 위반을 400, import는 기존 값을 덮지 않음.
   - 깨지면: `sortListings`가 순서에 없는 id를 버리면 새로 저장·상대가 추가한 매물이 목록에서 사라져 보인다(데이터는 있으나 화면에서 소실). `isListingOrder`가 느슨해지면 서버에 깨진 JSON이 저장돼 GET이 500이 된다. 순수 함수이고 입력이 작아 가장 싼 테스트다.

차순위(별도 표시): 카카오 콜백의 state·초대 쿠키 처리(`handleKakaoAuth`), 세션 만료·연장(`session.ts`), 라우터의 405/403/500 분기, 공유 링크 만료(`handleShares`), `parseListingRequests`의 PATCH·import 검증. 모두 서버 하네스가 생기면 같이 덮는다.

## 2. 앞으로의 qa 검증 기록 기준 제안

- 화면 통합은 소수만: "잘못된 값이면 저장 호출이 없다", "로그인 상태 + 함께 쓰는 중이면 기기 매물을 올리지 않는다" 같은 연결 확인.

## 3. 지금 바로 고쳐야 할 결함 (후보)

D1. 함께 쓰는 중인 계정의 다른 기기/재로그인에서 기기 로컬 매물이 가구 목록으로 올라간다 — 담당 fe (결정은 pm/사용자 확인)

- 근거: `src/hooks/useAccountImport.ts`가 `me.household`를 보지 않는다(grep 확인: 이 파일에 household 참조 없음). 서버 `importListings`는 `LISTING_SCOPE_SQL` 범위로 넣으므로 가구 구성원이 이전하면 행이 `user_id`=본인, `hidden_household_id`=NULL로 들어가 상대에게도 보인다.
- 반면 `src/containers/Mortgage/Invite/markDeviceImportsDone.ts`의 주석은 "함께 쓰는 목록에는 초대한 사람의 매물·예산·순서만 있어야 한다(ADR-028 개정)"이고, 그 보장은 수락한 바로 그 기기에서만 한다. 재현: B가 수락 → B가 로그아웃 상태에서 같은 기기에 새 매물 저장(또는 B의 다른 기기에서 로컬 매물이 있는 채 로그인) → 로그인 → 이전 실행 → A 화면에 B의 로컬 매물이 나타난다. 예산·순서 import는 `COALESCE`라 가구 값이 있어 덮지 않으나, 매물은 막는 장치가 없다.
- 사용자 영향: 사적인 로컬 메모·매물이 의도 없이 상대에게 공개된다(되돌리려면 삭제).
- 제안: 가구에 있는 동안은 이전을 건너뛰고(기록하지 않음) 나간 뒤 이전한다, 또는 이전 전에 확인창을 둔다. 둘 중 무엇이 의도인지 스펙(shared-list)에 규칙이 없으므로 pm이 정해야 한다. 자동 테스트로 `importLocalListings`를 `household !== null`에서 호출하지 않는 것을 고정한다.

D2. (낮음, 알려진 한계) 서버가 돌려주는 `id` 규칙 불일치 위험 — 담당 be/fe 확인

- `server/listings/parseListingRequests.ts`의 import는 한 항목이라도 `isListingId`(1~64자 `[A-Za-z0-9_-]`) 위반이면 요청 전체를 400으로 거부한다. 클라이언트는 400을 "limit"(500개 상한)으로 해석한다(`useAccountImport.toFailureReason`). 로컬 id가 규칙 밖인 매물(ADR-010 이전 형식이 있다면)이 하나만 있어도 같은 배치의 정상 매물이 함께 이전되지 않고 "500개 초과"라는 잘못된 안내가 나온다. ADR-010 이후 id가 hex라면 발생하지 않는다. 현재 사용자 운영 데이터에서는 발생 증거 없음 — 확인 필요 정도로 둔다.

D3. (참고) 이미 기록된 위험 중 qa 관점에서 계속 열려 있는 것

- 배포 후 새로고침하지 않은 옛 탭이 새 형식 데이터를 손상으로 판정해 [초기화]를 보이는 문제(로그 "놓침(위험)"). 코드로 막을 수 없고 "버전 확인 장치"가 후보로만 남아 있다. 인테리어 플래너가 저장 형식을 바꾸면 재발한다. 새 필드는 반드시 선택 필드(키 없음 = 기본)로 하고 `isListing`을 더 엄격하게 만들지 않는 것을 플래너 스펙의 AC로 요구하는 것을 제안한다.
- 나가기 후 B의 매물이 500개를 넘을 수 있는 경계는 의도적으로 둔 것이며 데이터 손실은 없다(로그). 다만 이 상태에서 `importListings`의 상한 검사는 이미 500을 넘은 범위에서 새 id를 모두 막는다. 하네스가 생기면 이 경계를 고정 테스트로 남긴다.

그 외 확인한 점(결함 아님)

- 수락 batch의 성공 판정, 동시 수락 처리(`used_at`/`accepted_by` 가드 + 가구 id 한정), 나가기의 가구 id 한정, 라우터의 Origin 검사(Origin 없으면 403), 세션 쿠키 속성은 코드상 설계 의도와 일치한다. 다만 이 판단은 코드 읽기이며 실행으로 확인하지 못했다(테스트 없음).
