# 우리 집 공정별 업체 견적 목록(단순화) 스펙 — be 검토

날짜: 2026-10-27 · 대상: `.cony/specs/interior-simple.md` · 검토만 함(스펙·코드 변경 없음, 시크릿 미열람, 코드 실행 없음)

- **D2 태스크 1 a(제자리): 찬성.**
- **D2 태스크 2 b(처음 쓸 때 떼어 내기): 조건부 찬성.** 조건 4~8을 스펙에 넣는다면. 손실 없는 순서(추가 → 빼기)는 맞다.
- **D2 c(열 때 일괄 쪼개기): 반대.** 읽기 경로의 쓰기라 AC-0(d)를 깨고, 로그인 상태에서 계획을 열기만 해도 PUT이 N번 나가며, 가구 구성원 둘이 동시에 열면 같은 쪼개기가 두 번 일어나 항목이 중복된다(추론).
- 전체: **조건부 찬성** (조건 1~3은 태스크 1 필수, 4~8은 태스크 2 필수, 9는 권고).

## 근거 (최대 3개)

1. **A에서 새로 만드는 "견적 1개 항목"은 지금 검증을 그대로 통과한다 (확인).** `validateInteriorItemFields`(src/lib/utils/validateInteriorPlan.ts)의 필수는 `spaceId`(`isInteriorId`, 형식만 보고 플랜 공간에 있는지는 안 봄)·`status`(5종 중 하나)·`trade`(trim 후 1~30자)뿐이다. 견적은 `id`(16바이트 hex가 `^[A-Za-z0-9_-]{1,64}$`에 맞음)·`vendor` 1~30자·`amount` 1~999,999,999 정수, `memo` ≤200자, `confirmedQuoteId`는 같은 항목 `quotes` 안 id여야 한다. 스펙의 새 항목 `{ spaceId: spaces[0].id, trade, quotes:[{id,vendor,amount,memo?}], confirmedQuoteId?, status:"planned", memo? }`는 모두 이 규칙 안이다. 서버는 `parseItemRequest`가 같은 함수를 부르고(server/interiorPlans/parseInteriorPlanRequests.ts), 로컬은 `addItem`/`updateItem`이 같은 함수를 거친다(interiorPlanStorage.ts). 본문은 `WRITE_MAX_BYTES` 16KB인데 견적 1개 항목은 1KB 미만이다.
2. **항목 상한은 "항목 수 100"이지 줄 수가 아니다 (확인).** 서버 POST는 `COUNT(*) < INTERIOR_ITEM_MAX_COUNT` 조건부 INSERT(handleInteriorPlans.ts `createInteriorItem`), 로컬 `addItem`은 `plan.items.length >= 100`이면 `limit`. PUT·DELETE는 개수를 보지 않는다. 그래서 (a) 줄 추가는 항목 100에서 막히고 400(서버)/`limit`(로컬)이 나오며 스펙의 "[줄 추가] 비활성 + 기존 상한 문구"와 맞다. (b) 옛 항목이 견적 5개씩이면 보이는 줄은 100을 넘을 수 있어도 막히지 않는다(스펙 문구와 일치). (c) **D2 b는 쪼갤 때마다 항목이 +1이라 항목 100개 계획에서는 단계 ①이 실패한다** (조건 5).
3. **PUT은 항목 전체 교체라 확정 토글이 숨은 값을 보존할지는 전적으로 클라이언트 입력에 달려 있다 (확인).** `replaceInteriorItem`은 `SET data = ?4`로 본문을 통째로 쓰고, `validateInteriorItemFields`는 알려진 키만 복사한다. 서버는 빠진 `payments`·`startDate`·`budget`·`contact`를 되살려 주지 않는다. 스펙의 방어("쓰기 입력 = 원래 항목 + 바꾼 칸" 단위 테스트, 입력 = `validateInteriorItemFields(input)` deep equal)는 올바른 위치다. 다만 아래 조건 2처럼 테스트 항목이 더 필요하다.

## D1 B·C를 반대하는 이유 (스펙 본문에 동의, 보강)

- B: 옛 번들은 `parseInteriorPlans`가 모르는 키를 버린 뒤 어떤 쓰기든 `{ plans }` 전체를 다시 쓴다(interiorPlanStorage.ts `commit`). 새 필드 값이 모든 계획에서 한꺼번에 사라진다. 서버도 옛 클라이언트가 PUT하면 새 필드를 버린다. 테스트로 막을 수 없다. 반대.
- C: 같은 데이터에 두 번째 저장 경로, 가구 범위·숨김·나가기 batch(ADR-029 조건 1·4·5)를 새 테이블에 다시 만들어야 한다. 반대.

## 확인 요청 항목별 답

- **새 항목이 서버·로컬 검증을 통과하나**: 예(근거 1). 서버에서 이 항목을 만드는 데 새로 필요한 에러 경로도 없다.
- **줄 수가 늘 때 항목 상한**: 위 근거 2. 100 항목이면 줄 추가는 서버 400 `계획 하나에 항목은 100개까지…`/로컬 `limit`. 스펙의 비활성 처리는 클라이언트 선검사일 뿐이라, 다른 기기가 먼저 100개를 채운 경쟁에서는 서버 응답이 최종 판단이고 `planWriteFailureMessage`가 받아야 한다(이미 있는 경로).
- **확정 토글 PUT의 숨은 값 보존**: 서버 쪽 문제 없음(전체 교체이므로 입력이 곧 결과). 클라이언트가 캐시의 항목에서 `id`·`createdAt`·`updatedAt`만 떼고 `confirmedQuoteId`만 바꾸면 보존된다. 단 캐시가 폴링(약 30초) 주기만큼 낡을 수 있어, 그 사이 다른 기기가 지급 체크를 바꿨다면 토글 PUT이 되돌린다. 이는 ADR-029 조건 8·스펙 A7이 이미 받아들인 "항목 단위 마지막 저장 우선"이다. 옛 화면은 배포 뒤 사라지므로 실제 빈도는 낮다(추론). 스펙 A5의 "그 시점 목록 값을 돌려보내므로 보존된다"는 "목록이 최신일 때"로 문구를 좁히는 것이 정확하다.
- **D2 b의 ① 추가 → ② 빼기 순서의 실패·동시 편집**: 아래 "D2 b 상세".
- **함께 쓰기**: 구성원 둘 다 같은 `PLAN_SCOPE_SQL`/`PLAN_ITEM_SCOPE_SQL`로 항목을 읽고 쓰며 POST 항목은 플랜 소유자 행(`plan_user_id`)으로 들어간다. 줄 추가·토글·삭제가 모두 기존 엔드포인트 한 번이라 가구 batch(수락·나가기)와 새 상호작용은 없다. 숨긴 플랜은 두 요청 모두 404라 D2 b 중간에 가구를 나가면 ①이 먼저 404로 끝나 일부만 저장될 일은 없다(①에서 막힘). 단 ① 성공 뒤 ② 사이에 나가면 ②만 404 → 중복 줄이 남은 채 플랜이 숨는다(나가는 사람 쪽은 자기 플랜이 아니면 어차피 못 봄).
- **로그인 이전·import**: 새 화면이 쓰는 값은 전부 옛 검증을 통과하는 같은 형식이라 `parsePlanImportRequest`(항목 ≤100, 항목 id 유일, `parseInteriorItem`)가 그대로 받는다. 이전은 항목 id·견적 id·`createdAt`을 그대로 보내므로 줄 순서도 보존된다. 함께 쓰는 중 import는 서버가 409 `inHousehold`로 막는 기존 규칙 그대로. D2 b가 부분 실패로 만든 "같은 견적 id가 두 항목에 있는" 상태도 검증은 항목 안 유일성만 보므로 import가 통과한다(확인: `hasUniqueIds`는 `quotes` 배열 단위).
- **AC-0 데이터 보존**: (a)의 `git diff` 빈 출력 요건은 달성 가능하다. 다만 `src/lib/constants/interiorPlan.ts`는 AC-0(a)에 없는데, **worker 타입 검사(tsconfig.worker.json)가 이 파일과 `types/interiorPlan.ts`를 전이 의존으로 가져온다** (`validateInteriorPlan.ts`가 상수를 import, 상수가 `InteriorProcessSource` 타입을 import). 삭제 대상 상수는 server/ 에서 쓰이지 않음을 grep으로 확인했다(`server`·`worker`에 `INTERIOR_TRADES`·`INTERIOR_PROCESS_*`·`INTERIOR_ITEM_STATUS_LABELS`·`INTERIOR_PAYMENT_LABEL_PRESETS` 참조 없음). 삭제 후 `pnpm build`(`tsc -b`)가 worker 프로젝트까지 통과해야 한다(조건 3).

## D2 b 상세 (태스크 2)

- ① `addItem(N)` → ② `updateItem(X, q2 제외)` 순서는 맞다. ①이 실패하면 아무것도 안 바뀌고, ②가 실패하면 q2가 X와 N에 둘 다 남는 **중복뿐 손실 없음**이다 (확인: 서버에 두 요청을 묶는 트랜잭션 API는 없고, 만들면 계약 변경이라 이번 범위 밖).
- 서버가 항목 id를 발급하므로(`createRandomId`) ①에는 멱등키가 없다. 응답 유실 후 재시도하면 N이 둘 생길 수 있다. 중복이지 손실은 아니다.
- 동시 편집 경쟁: (i) 다른 기기가 같은 시점에 같은 견적을 쪼개면 N1·N2가 둘 다 생기고, 둘 다 확정이면 지출 예정이 이중 계산된다(체크된 줄이 둘로 보이므로 사용자가 지울 수 있음, 낮은 확률). (ii) 옛 탭이 X를 q2 포함 상태로 다시 쓰면 q2가 되살아나 중복(스펙에 적힌 대로). (iii) ② PUT은 캐시의 X로 전체 교체하므로 낡은 캐시면 그 사이 X의 숨은 값(지급 등) 변경을 되돌린다(조건 8).
- 새 항목에 복사하는 필드를 AC-7이 `spaceId·trade·quotes[q2]·confirmedQuoteId·status·memo`로 정했다. 항목 `budget`·`payments`·`startDate`·`endDate`를 N에 **복사하지 않고 X에 남긴다**는 점은 맞다(복사하면 지급이 이중으로 잡힘). 이 선택을 스펙에 명시한다(조건 6).

## 리스크

1. 숨은 값 PUT 누락(클라이언트 버그): 서버가 막아 주지 않는다. 검증 통과 = 정상 저장이라 누락은 조용히 지급·날짜 손실이 된다.
2. D2 b가 항목 수를 늘려 100 상한에 막힐 수 있다. 그 순간 사용자는 확정을 바꿀 수 없다.
3. 줄 삭제(견적 0~1개 항목)가 보이지 않는 지급·날짜까지 지운다(A6). 스펙은 사용자 의도로 보지만, 화면에 없는 값이라 "지급 n건도 함께 지워집니다"를 모를 수 있다. AC-0의 "하나도 잃지 않는다"와 충돌하는 지점이다.
4. 로컬 모드의 ① ②는 각각 `commit`(전체 `{plans}` 재쓰기)이라 두 번째 쓰기만 실패(용량)할 수 있다. 확률은 낮고 결과는 서버와 같은 중복이다.
5. 항목 순서: 로컬 `addItem`의 `createdAt`은 `now()` 한 시각이고 서버 정렬은 `created_at, id`다. 같은 ms에 두 항목이 생기면 로컬 배열 순서와 서버 순서가 다를 수 있다. 사람 조작에서는 일어나지 않는다(추론).

## 스펙에 넣을 조건

태스크 1 (필수)

1. **D1 A의 "서버 무변경" 검증 범위를 넓힌다**: AC-0(a) `git diff` 경로에 `src/lib/constants/interiorPlan.ts`의 _검증 상수_(`INTERIOR_ITEM_STATUSES`, 모든 `*_MAX_*`)를 지정한다. 상수 파일은 "삭제만, 남는 상수 값 diff 0"으로 적는다 (worker가 전이 의존으로 쓰므로).
2. **숨은 값 보존 단위 테스트를 표로 확정**: 줄 수정(견적 1개), 줄 수정(견적 n≥2의 q1, **`contact`가 있는 견적**), 0개 항목 채우기, 확정 켜기·끄기, n≥2 견적 삭제 각각에 대해 "입력 = 원래 항목(id·createdAt·updatedAt 제외) + 바꾼 칸만", `payments`·`startDate`·`endDate`·`budget`·`status`·`spaceId`·`quote.contact` 유지, `validateInteriorItemFields(input)`과 deep equal. 비운 선택 칸(세부내용·비고)은 빈 문자열이 아니라 키 삭제로 쓴다(검증은 빈 문자열도 받지만 돌려줄 때 키를 빼므로 deep equal이 깨짐). n≥2에서 견적 삭제 후 `quotes`가 비면 안 되며(n≥2라 불가) 견적 0개가 되는 경로는 `removeItem`뿐임을 명시. 로컬(`createInteriorPlanStore`)과 서버(d1 하네스) 양쪽에서 한 번씩 왕복(PUT 후 GET 값 === 입력) 테스트.
3. 삭제할 상수·타입·유틸을 지운 뒤 `pnpm build`(`tsc -b`, worker 포함)와 `server/**` 테스트가 diff 0으로 통과해야 한다고 AC-0(e)에 적는다.

태스크 2 (D2 b 채택 시 필수) 4. **쪼개기가 필요한 경우를 한 문장으로 정의**: 쪼개는 이유는 "제자리 쓰기가 형제 줄의 모습을 바꾸는 경우"뿐이다 — (가) 확정을 _켜는데_ 같은 항목의 다른 견적이 확정돼 있을 때, (나) 구분·비고를 바꿀 때. 확정을 _끄는_ 쓰기와, 다른 견적이 확정되지 않은 항목에서 켜는 쓰기는 제자리 PUT 1번으로 끝낸다(다른 줄에 영향 없음). 스펙 2-1의 "확정·구분·비고 변경 = 쪼갬"보다 쓰기 수와 항목 증가가 줄어 더 단순하다. 채택하지 않아도 되지만 둘 중 하나로 AC-7에 정확히 적는다. 5. **항목 100개 상한**: ①이 `limit`/400이면 아무것도 쓰지 않고 상한 문구를 보이며, 이때 폴백(제자리 수정)은 만들지 않는다(CLAUDE.md "폴백 금지"). 사전 검사는 UI 편의일 뿐 서버/로컬 쓰기 결과를 최종으로 본다. AC-7에 "항목 100개 + 견적 2개 항목에서 쪼개기 → 쓰기 0건, 문구, 값 불변" 추가. 6. **복사 규칙 명시**: N = `{ spaceId, trade, quotes:[그 견적(contact 포함, 같은 id)], confirmedQuoteId?, status, memo }`. `budget`·`payments`·`startDate`·`endDate`는 X에 남고 N에 복사하지 않는다. X는 그 견적과, 그 견적이 확정이었으면 `confirmedQuoteId`만 뺀다(확정 유지 필요 없는 경우 포함 규칙을 한 곳에). 줄 key는 `(item.id, quote.id)`로 해 같은 견적 id가 두 항목에 있어도 React key가 충돌하지 않게 한다. 7. **부분 실패 처리**: ① 성공 뒤 ②가 어떤 이유(네트워크·404·500·로컬 unavailable)로 실패해도 목록 쿼리를 무효화해 두 줄이 보이게 하고 안내 문구를 띄운다. ②가 404(원래 항목이 다른 기기에서 삭제됨)면 N만 남는 것이 정상이다. ①이 응답 유실로 모호하면(타임아웃) 재시도하지 말고 무효화 후 현재 목록을 보인다(멱등키 없음). AC-7의 ② 실패 주입 테스트를 서버(500)·로컬(setItem 예외) 둘 다 둔다. 8. **② PUT의 입력은 ① 직전이 아니라 ② 직전 캐시/저장소의 X**로 만든다(그 사이 폴링으로 X가 바뀌었을 수 있음). 로컬 스토어는 `writeItem`이 저장소를 다시 읽으므로 입력만 최신 X에서 만들면 된다. 서버는 조건부 PUT이 없으므로 항목 단위 마지막 저장 우선을 스펙에 한 줄 명시.

권고 9. A6의 줄 삭제 확인 문구: 그 항목에 지급·날짜(숨은 값)가 있으면 "지급 n건·날짜도 함께 지워집니다"를 확인 대화에 한 줄 보인다(읽기 전용, 저장 형식 무변경). 비용이 작고 "하나도 잃지 않는다"와의 마찰을 줄인다.
