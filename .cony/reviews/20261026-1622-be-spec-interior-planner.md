# 인테리어 플래너 스펙 — be 검토

날짜: 2026-10-26 · 대상: `.cony/specs/interior-planner.md` · 검토만 함(코드·스펙 변경 없음, 시크릿 미열람, 코드 실행 없음)

## 판정: 조건부 찬성

D1 C 모델은 기존 매물 패턴(행마다 JSON, 한 문장 쓰기, 범위 SQL)과 같아 구현 가능하다. 0007은 추가만이다. 다만 아래 "필수 조건" 1~5가 스펙에 없거나 모호해서, 그대로 구현하면 재시도 시 삭제한 항목이 되살아나거나 가구 수락·나가기가 조용히 어긋날 수 있다. 조건을 스펙에 반영하면 찬성이다.

표기: 확인 = 코드·문서를 읽어 확인한 사실, 추론 = 읽은 근거로 한 판단. SQLite/D1 동작은 실행해 보지 않았다(하네스 없음).

## 근거 (최대 3개)

1. 0007은 추가만이다 (확인). `migrations/0007` 스펙 SQL은 새 테이블 2개와 부분 인덱스 1개뿐이고 `users`·`listings`·`households`에 `ALTER`가 없다. 기존 0005·0006이 쓰던 `ALTER TABLE ADD COLUMN`도 쓰지 않는다. 복합 FK `(plan_user_id, plan_id) → interior_plans(user_id, id)`는 부모 PK 순서와 같고, 자식 PK가 FK 컬럼으로 시작해 CASCADE 조회가 인덱스를 탄다 (추론: 표준 SQLite 동작, D1은 FK를 기본 강제. 스펙대로 `--local`·하네스로 먼저 확인). 기존 코드는 `users` 삭제 경로가 없어(grep: `DELETE FROM users` 없음) 새 `ON DELETE CASCADE`가 실제로 도는 경우는 없다.
2. D1 2MB·674KB 계산은 저장 한도가 아니다 (확인). D1의 2,000,000바이트는 행·문자열 단위인데, C 모델은 행이 항목 ~7KB·플랜 ~4KB다. 실제로 걸리는 곳은 (a) import 본문을 통째로 바인딩하는 1MB(2MB 안), (b) GET 응답 최대 ~2MB(Worker 응답엔 문제 없음, 보통 수십 KB)다. 따라서 "플랜 3개 2.0MB"는 D1 한도 계산이 아니라 응답 크기 계산이라고 스펙 문구를 바로잡는 것이 좋다.
3. 건드리는 기존 파일이 정확히 3개다 (확인): `server/household/handleHousehold.ts`(수락·나가기 batch), `householdScope.ts`(상수 추가), `worker/index.ts`(경로 추가). `LISTING_SCOPE_SQL`·`handleListings.ts`·`parseListingRequests.ts`·`validateListingFields.ts`는 건드리지 않는다. 즉 "기존 매물 경로 무변경"은 지켜지나, **가구 수락·나가기는 기존 경로를 수정한다**(스펙 AC-0 문구는 이를 "문장 추가"로만 적어 가볍게 보인다). 위험이 집중되는 곳이 여기다.

## 필수 조건 (스펙에 반영 요청)

### 1. import·POST(items 포함)의 항목 넣기 가드 — 재시도 시 되살아남 (가장 중요)

- 스펙: "항목 INSERT…SELECT FROM json_each WHERE **방금 넣은 플랜 존재**". 이 조건은 재시도에서도 참이다(플랜은 첫 시도 때 이미 있음). 첫 import 성공 후 사용자가 항목을 지웠거나, 응답 유실로 클라이언트가 기록을 못 남겨 재시도하면 `ON CONFLICT DO NOTHING`은 PK만 막으므로 **지운 항목이 다시 들어간다**. "재시도 안전"(`imported: 0`)이 플랜 행만 안전하다.
- 조건: 항목 문장은 "직전 플랜 INSERT가 1행 넣었을 때만"이어야 한다. 예: `WHERE (SELECT changes()) = 1` 같은 직전 문장 결과 가드(D1 batch는 같은 연결이라 가능하다고 추정, 하네스로 확인) 또는 플랜 INSERT가 만든 표식(서버가 정한 `updated_at` 값 일치 등). 어느 쪽이든 "플랜이 이미 있으면 항목 0행"을 하네스 테스트로 고정(변이: 가드 삭제 시 실패).
- 같은 가드가 POST `{…, items?}`(만들 때 가져오기)에도 필요하다. 이 경로는 플랜이 새 id라 재시도 문제는 없으나 "플랜 3개 초과로 플랜이 0행이면 항목도 0행"이 필요하다.
- 상한 검사 문장: import에서 플랜이 범위에 **이미 있으면** 상한(3)에 걸려도 400이 아니라 `imported: 0`이어야 한다. `importListings`의 `IMPORT_OVER_LIMIT_SQL`처럼 "없는 id일 때만 개수 비교"로 식을 쓸 것(스펙 문구 "개수 < 3"만으로는 재시도가 플랜 3개 상태에서 400이 될 수 있음).

### 2. 검증을 "알려진 키만 복사 + 유일성"으로

- 서버는 검증 뒤 **알려진 키만 새 객체로 복사**해서 저장한다(`parseListingRequests`의 "알려진 키만 남김"과 같음). 그래야 6.7KB 최악 계산이 성립한다. 알 수 없는 키를 통과시키면 항목이 본문 한도 16KB까지 커질 수 있고(100개 × 16KB = 1.6MB, 플랜 3개 4.8MB) 크기 계산이 깨진다.
- 유일성을 검증에 명시: `spaces[].id`, 한 항목의 `quotes[].id`·`payments[].id`, import의 `items[].id`. import에서 항목 id가 겹치면 PK 충돌로 batch 전체가 500이 된다(`ON CONFLICT`를 쓰지 않는다면) — 검증이 400으로 막아야 한다.
- 시각은 `new Date().toISOString()`과 같은 고정 형식(`YYYY-MM-DDTHH:mm:ss.sssZ`)만 허용. 정렬(`ORDER BY created_at, id`)이 문자열 비교라 `+09:00` 같은 형식이 섞이면 순서가 틀어진다. 날짜 `YYYY-MM-DD`는 실제 달력 날짜 검사(`2026-13-01` 거부는 AC-5에 이미 있음), `Number.isSafeInteger`·범위 1~999,999,999를 견적·지급·예산 모두에 적용(지급 금액 범위가 스펙에 없음).
- 크기 재계산: 연락처가 "자유 문자열 30자"(A7)라 한글이면 90바이트다(스펙은 30으로 계산). 견적 5 × ~880 = 4.4KB로 항목 최악은 **~7.0KB**(6.7이 아님). 짝 없는 서로게이트 2배 14KB도 항목 쓰기 한도 16KB 안이라 결론은 같다. import 본문 최악(플랜 ~700KB, 2배 1.4MB)이 1MB를 넘는 것은 스펙이 이미 인지하고 "이전 실패 안내"로 처리한다 — 동의.

### 3. API 계약 빈칸 (구현자가 추측하게 됨)

- 응답 봉투: 매물은 요청·응답 모두 `{ listing }`로 감싼다. 플래너는 POST 201 "플랜(+items)", PUT 200 "항목"이 감쌌는지 불명확하다. `{ plan }`·`{ item }`으로 정하고 요청도 같은 규칙(또는 매물과 다름을 명시)으로 고정할 것.
- 경로의 id 형식이 틀리면 매물은 400 `invalidParams`, 스펙은 404만 적었다 → 400으로 명시.
- 경로 순서: `/api/interior-plans/import`는 `/api/interior-plans/:id`보다 앞(라우터는 첫 일치). 그렇지 않으면 POST import가 405가 된다. 또 `^[A-Za-z0-9_-]{1,64}$`는 `import`도 통과하므로 id `import`는 PATCH·DELETE가 import 경로에 가려진다 — 실제 id는 hex라 실무 위험은 없지만 검증에서 `import`를 거부하는 한 줄을 권장(listings도 같은 허점, 이번엔 새 경로라 막을 수 있음).
- POST 항목 `items?`: id를 서버가 만드는가 클라이언트가 주는가, 상한이 100인가? 본문 한도 16KB와 충돌한다(항목 100개는 쉽게 16KB 초과). 만들 때 가져오기는 추가 비용 인테리어 줄(≤30) + 공간 10개 정도라 11KB 안 → "items ≤ 30, id는 서버 발급"으로 줄이는 것을 권장.
- 404 vs 400 구분(항목 POST): 한 문장 INSERT가 0행일 때 "플랜 없음"인지 "100개"인지 가르는 후속 조회가 필요하다. `importListings`처럼 같은 batch의 두 번째 문장으로 하거나, 항목 POST 실패 시 플랜 범위 존재를 한 번 더 읽는다(경합은 무해). 방식을 스펙에 한 줄.
- 항목 `spaceId`가 플랜 `spaces`에 있는지는 서버가 검사하지 않음(A6의 "공간 없음" 그룹으로 수용). 이 결정은 괜찮으나 "서버는 spaceId 형식만 검증"이라고 명시해 qa가 테스트하게 할 것.
- GET은 플랜·항목 2쿼리를 **한 `db.batch`**로(한 스냅샷). 따로 보내면 그 사이 삭제된 플랜의 항목이 섞이거나 새 항목이 빠진다. 항목 조회는 반드시 "플랜 범위 서브쿼리"를 통과(`(plan_user_id, plan_id) IN (SELECT user_id, id FROM interior_plans WHERE ${PLAN_SCOPE_SQL})`). 항목 행에는 숨김 컬럼이 없어 **범위 통과를 빠뜨린 쿼리 하나가 숨긴 플랜의 항목을 노출**한다. 이 서브쿼리를 상수 한 곳(`householdScope.ts` 또는 `server/interiorPlans`)에 두고 항목 GET·POST·PUT·DELETE가 모두 같은 조각을 쓰게 할 것(스펙의 "같은 판단은 한 곳").
- SQL 열 이름 주의: 항목 테이블에도 `id`·`created_at`이 있어, `PLAN_SCOPE_SQL`(비한정 `user_id`/`id`)을 항목 문장의 서브쿼리에 넣을 때 바깥 테이블 열로 잘못 해석되지 않는지 하네스로 확인(숨긴 플랜·타인 플랜 id로 PUT/DELETE → 404).
- 인증·Origin·413·no-store: `routeApi`가 비-GET Origin을 먼저(403) 검사하고, 그 뒤 `withSession` 401, `readJsonBody`가 413, `errorResponse`·`noContentResponse`가 no-store를 붙인다(확인). 새 핸들러가 이 공통 부품만 쓰면 스펙의 "기존 그대로"가 성립한다. 성공 응답에 `NO_STORE`를 빠뜨리지 않도록 테스트 1건.

### 4. 가구 수락·나가기 batch 문장 추가 (원자성·가드)

- 수락: 성공 판정은 `results[results.length - 1]`이라 문장을 **마지막 앞**에 끼워도 안전하다(확인). 새 문장은 listings 숨기기와 같은 형태(`WHERE user_id = ?1 AND hidden_household_id IS NULL AND ${householdExists}`), `householdExists`(?3)가 이 요청이 만든 가구일 때만 참이라 ①이 실패하면 0행 — 가드가 listings와 같은 강도로 유지된다. 바인딩 3개를 listings 문장과 똑같이 넘길 것(?2 미사용이어도 기존 문장이 그렇게 동작).
- 나가기: 기존 코드가 `const [, , , cleared] = await db.batch([...])`로 **인덱스 3**을 읽는다(확인). 스펙이 "listings 숨김 해제" 옆에 끼우면 `cleared`가 `UPDATE users` 아닌 다른 문장이 되어 항상 성공/실패로 오판한다. 스펙은 "이름 있는 변수로 바꿈"이라 적었으나 구체적으로: 새 문장을 **배열 맨 끝(`DELETE FROM households` 뒤)**에 두면 인덱스가 안 밀리고, `hidden_household_id`는 FK가 없어(0006 주석) 순서 제약도 없다. 그래도 인덱스 의존은 없애고 `users` UPDATE 결과를 이름으로 찾도록 바꿀 것. 이 변경은 qa 0-4 테스트(수정 전 동작 고정)가 먼저 머지된 뒤에 한다(스펙의 의존 관계에 이미 있음, 동의).
- **배포 순서 위험(확인)**: 새 Worker가 먼저 나가고 0007이 아직 없으면 수락·나가기 batch가 `no such table`로 실패해 **함께 쓰기 나가기가 막힌다**(트랜잭션 롤백). 스펙의 "원격 마이그레이션 먼저"가 정확히 이 때문이므로, 4-1이 4-2보다 먼저라는 순서를 Auto-merge 전에 반드시 지킨다(CI 워크플로엔 migrations apply가 없음, 확인: `.github/workflows/ci.yml`). 반대(옛 Worker + 새 스키마)는 안전하다 — 새 테이블을 쓰지 않는다.
- 동시성: 두 사람이 동시에 나가도 새 문장이 `hidden_household_id = ?1`(읽어 둔 가구 id)로 한정돼 뒤의 요청은 0행이라 404가 유지된다(listings와 같은 구조).
- 의미 확인(스펙 AC-9에 이미 일부): 함께 쓰는 동안 B가 만든 플랜 PC에 A가 넣은 항목은 B가 나갈 때 **B와 함께 간다**(PA의 B 항목이 A에 남는 것의 대칭). 매물 메모와 같은 규칙이라 일관되지만 사용자에게 의외일 수 있으니 문구(안내)를 결정 사항으로 남길 것. 또 나가기 뒤 B는 숨겼던 PB + PC 등으로 3개를 넘을 수 있다(매물 500 초과와 같은 의도된 경계) — 이 상태에서 POST는 막히고 GET은 정상이라 데이터 손실은 없다. 하네스 경계 테스트에 포함.

### 5. 서버에서 함께 쓰는 중 import 차단(제안, 결정 필요 아님)

- 태스크 0은 클라이언트만 고친다. 그러나 이미 열려 있는 옛 번들 탭은 계속 import를 보낸다(qa D3 유형, 확인: 서버 `importListings`는 가구 구성원도 범위에 그대로 넣음). **새 엔드포인트 `/api/interior-plans/import`는 옛 클라이언트가 없으므로** 처음부터 `users.household_id IS NOT NULL`이면 넣지 않는 한 줄 가드(409)를 넣는 것이 싸다. 다만 스펙은 "같은 판단을 한 곳"에 두려 하므로(클라이언트 `me.household`) 이중 판단이 된다. 리드가 정할 항목: 넣으면 계약에 409 `inHousehold` 추가. 안 넣으면 현행 스펙 그대로 두고 옛 탭 위험을 로그에 기록.

## 항목별 검토

### AC-0 / 0007 추가만 여부

- 확인: SQL상 기존 행·스키마를 읽거나 쓰지 않는다. 마이그레이션 적용 자체는 기존 데이터에 영향 없음. AC-0(a)의 덤프 쿼리는 기존 6개 테이블만 비교하므로 새 테이블 생성 검증은 "행 수 0" 한 줄 추가를 권장(`interior_plans`·`interior_plan_items` 0행).
- 빈틈: AC-0(a)에 `sessions`는 행 수만 있고 내용 비교는 없음 — 쓰지 않으므로 무방.
- (e) 옛 Worker + 새 스키마: 안전(위 4).
- FK `ON DELETE CASCADE` 복합키가 D1에서 동작하는지 확인하라는 스펙 계획에 동의. 대체안(FK 제거 + DELETE batch)은 그때 선택, 지금 결정 불필요.

### 동시 편집

- 항목 PUT은 `UPDATE … SET data = ?` 한 문장(읽고 쓰기 없음)이라 서로 다른 항목은 안전하다 — 동의(확인: `replaceListing`과 같은 패턴).
- 같은 항목 동시 저장은 마지막 저장이 이긴다(A2). 가장 값비싼 필드는 지급 `isPaid`·확정 견적이라 한쪽 저장이 다른 쪽 변경을 되돌릴 수 있다. 이번 사이클은 수용 가능(스펙이 "다음 단계: 항목 필드별 PATCH"를 이미 둠). 저비용 완화책은 PUT 본문에 클라이언트가 본 `updatedAt`을 담고 `WHERE updated_at = ?`가 어긋나면 409로 재조회시키는 것 — 지금은 넣지 않는 쪽을 권장(복잡도 대비 빈도 낮음).
- 플랜 PATCH는 `json_patch` 한 문장이라 이름·예산·연결은 필드 단위로 안전. **`spaces`는 배열이라 통째 교체**: 둘이 동시에 공간을 고치면 한쪽 추가가 사라진다. 그 공간을 가리키던 새 항목은 "공간 없음" 그룹(A6)으로 보이고 데이터는 안 사라진다 → 수용.
- `json_patch`에서 `budget: null`은 키 삭제(RFC 7396)이므로 "null=지움"과 맞다. PATCH 검증은 필드 단위 부분 검증 함수가 별도로 필요(`isInteriorPlan`은 전체용) — 같은 파일 안 순수 함수로.

### 매물 연결 `listingId` 무결성

- FK 없음·형식만 검증이 맞다. 로컬 import 때 매물이 아직 계정에 없을 수 있고 숨긴 매물도 있어 존재 검증은 불가능·불필요(존재 검증을 넣으면 오히려 이전 순서 의존이 생김).
- 매물 삭제 시 플랜은 남고 화면이 "삭제되었습니다"로 처리(A8)하는 설계에 동의. 서버 쪽 정리 코드 불필요(매물 삭제 경로 무변경 유지).
- 누락된 경우 하나: 함께 쓰던 B가 A의 매물에 연결한 플랜 PC를 가지고 나가면 B에게 연결 매물이 없다. A8의 "숨겨진·삭제된"에 "나간 뒤 다른 사람 목록의 매물"도 같은 표시라고 한 줄 추가.
- 한 매물에 플랜 둘이 연결되는 것을 서버가 막지 않는다(막을 근거 없음). 카드의 [인테리어 계획]은 "첫 번째 연결 플랜"이라고 클라이언트 규칙에 명시할 것.

### 크기 상한과 비용

- 확인: 매물 본문 한도 512KB와 같은 방식(`readJsonBody` 스트림 카운트)이라 새 한도(16KB·1MB)도 부품 재사용으로 충분.
- 추론: 가구 폴링 시 GET 한 번에 읽는 행 ≤ 3 + 300. 30초 폴링이면 사용자당 하루 최대 ~30만 행 읽기(열린 탭 24시간 기준). 매물 500행 목록과 같은 자릿수라 이번엔 문제 없으나, 항목 쿼리가 PK 접두어를 타는지 확인(`EXPLAIN QUERY PLAN`) 한 번.

### 공용 검증 파일 배치

- `src/lib/utils/validateInteriorPlan.ts`(서버 import 가능, `@/` 별칭·DOM 없음)는 `validateListingFields.ts`와 같은 패턴이고 `tsconfig.worker.json` 포함 범위에서 컴파일되는지 1-1 단계에서 `pnpm build`로 확인. 서버 전용 파싱(`{ plan }` 봉투, PATCH 부분 검증, import 항목 유일성)은 `server/interiorPlans/parseInteriorPlanRequests.ts`로 분리해 공용 파일에는 도메인 규칙만 둔다(매물의 `parseListingRequests` 분리와 같음).
- `PLAN_SCOPE_SQL`은 `householdScope.ts`에 추가하는 계획에 동의(listings 상수와 한 파일에서 나란히 보임).

### 기존 매물·가구 경로

- 매물 경로: 무변경 (확인, 위 근거 3).
- 가구 경로: 수락·나가기 batch 수정 (위 4). 이 수정이 이번 사이클에서 **기존 사용자에게 영향을 줄 수 있는 유일한 서버 변경**이다. 0-4 테스트로 수정 전 동작을 고정한 뒤 진행하는 의존 순서가 필수.

## 리스크 요약

1. (높음) import·POST 항목 넣기 가드 누락 → 재시도로 지운 항목 부활. 하네스 변이 테스트 필수.
2. (높음) 나가기 batch 인덱스 의존·배포 순서 → 함께 쓰기 해체 실패(되돌리기 어려움).
3. (중) 항목 조회가 플랜 범위를 빠뜨리면 숨긴 플랜 항목 노출 — 범위 조각 단일화.
4. (중) 알려진 키 복사 없으면 크기 상한 무력화.
5. (낮음) 같은 항목 동시 저장 마지막 이김(수용), 나간 B와 함께 가는 항목(안내 필요), 나간 뒤 플랜 3개 초과(의도된 경계).

## 미검증 (확인하지 못한 것)

- 복합 FK CASCADE가 D1(local/remote)에서 도는지, `changes()`가 D1 batch 안에서 직전 문장 결과를 돌려주는지: 실행하지 않음. 2-1에서 `--local`·하네스로 먼저 확인할 것.
- `tsconfig.worker.json`이 `src/lib/utils/validateInteriorPlan.ts`를 포함해 빌드되는지: 1-1에서 확인.
