# hub-account 스펙 — qa 검토

날짜: 2026-10-27 · 대상: `.cony/specs/hub-account.md` · 관점: 테스트 가능성(코드·테스트는 읽기만 함, 실행 안 함)

## 판정: 조건부 찬성

- 근거 1. AC-1~6은 대부분 판정 가능한 문장이다. be(`Location` 5종)는 현재 서버 테스트가 0개(`server/` 아래 kakao 테스트 없음, `handleKakaoAuth.ts`만 있음)라 새로 쓰는 값이 곧 계약이 된다. parseRoute는 표로 닫혀 있다.
- 근거 2. 지키려는 대상이 분명하다. 14개 키 원문 `===`와 쓰기 종류 단언은 기존 `AppRoutes.storageKeys.hub.test.tsx` 패턴(4모드, 체크포인트, 주입 스파이 + `Storage.prototype` 스파이)을 그대로 확장하면 된다.
- 근거 3. 다만 AC-0의 가리기 대조군 서술이 코드와 어긋나고, 반전되는 기존 테스트 중 가리기 외 항목(홈 계정)에는 감사 규칙이 없고, 401·로그아웃 실패·포커스 같은 경계가 비어 있다. 아래 조건을 반영하면 찬성한다.

## 코드와 대조해서 찾은 사실 오류·구분 불가 서술

1. **AC-0 가리기 대조군의 값과 방향이 틀렸다.** `privacyModeStorage.set`은 켜든 끄든 `setItem(key, JSON.stringify(next))`를 쓴다(`removeItem` 아님). 그리고 시드가 `"true"`이므로 시작이 이미 켜짐이다. 첫 클릭은 끄기다. 따라서 순회 "[가리기] 켜기·끄기"의 실제 쓰기는 `setItem(privacy-mode,"false")` → `setItem(privacy-mode,"true")` 순서의 2회다. 최종 원문이 `"true"`라 `===`는 우연히 통과한다. 고칠 문장: "시드가 켜짐이므로 클릭 2회는 끄기 → 켜기이고, 쓰기는 `"false"`, `"true"` 순서의 setItem 2회, 그 밖의 setItem·removeItem은 0회". 그렇지 않으면 "대조군 하나"라는 허용이 느슨해 우리 집 순회 중 새는 쓰기를 가린다. **더 강한 단언**: 대조군 쓰기는 [매물] 단계에서만 일어나고, [우리 집]·표 보기·홈 단계의 쓰기는 `privacy-mode` 포함 0회다(우리 집이 `privacy-mode`를 다시 건드리는 변이를 잡는다).
2. **AC-0 (a) "removeItem session-hint 1회뿐"의 횟수는 검증 전 단정이다.** 로그아웃 성공 `useLogout.onSuccess → endSession → clear()`에 이어 `/api/me` 재확인이 로그아웃으로 확정될 때 `clear()`가 또 불릴 수 있다(기존 규칙은 "removeItem(session-hint) 1종"이지 횟수가 아니다). 구현 측정 뒤에 횟수를 고정하거나, 종류(키가 모두 session-hint) + 로컬 두 키 원문 `===`로 단언한다. 횟수를 틀리게 적으면 정상 구현이 실패한다.
3. **AC-0 모드 목록.** 스펙은 "로그아웃·로그인 혼자·가구 세 모드"인데 기존 hub 테스트는 확인 중(pending)을 포함한 4모드다. pending(`/api/me` 응답 없음)을 빼면 "확인 전 쓰기 0회"와 "확인 중 자리의 [로그아웃]이 안 눌린다"가 빠진다. 4모드로 유지한다. 또 "[함께 쓰기] 시트 열고 닫기"는 혼자 모드에서만 가능하다(가구 모드에는 [함께 쓰기]가 없다). 가구 모드는 시트 단계를 건너뛰는 것으로 명시한다.
4. **AC-0 (c)** `git diff`는 자동 테스트가 아니라 검증 체크리스트다. 그렇게 표기하고 qa 기록에 명령과 출력을 붙인다. `server/` 변경 범위(`--stat`)도 같다.
5. **AC-5 grep 범위가 좁다.** `MortgageHome`·`Home/components/**`만 보지만 가리기 잔재가 `src/lib/constants/interiorPlanTable.ts:52` (`INTERIOR_PLAN_EXPORT_NOTICES.privacyMode` "가리기를 끄면…")와 그 안내 우선순위 판정 함수, `PlanScreen.module.css`에도 있다. "가리기를 끄면"·`INTERIOR_PLAN_EXPORT_NOTICES.privacyMode`·`isPrivacyMode`를 `src/` 전체에서 grep해 `Listings`·`Hub`(U6 기본값)·테스트를 제외하고 빈 출력을 요구한다. 안 지우면 죽은 상수가 남는다.
6. **AC-7이 가리기만 다룬다.** 반전되는 기존 테스트가 더 있다. `MortgageHub.account.test.tsx`의 "로그아웃 버튼은 홈에 두지 않는다", "계정 확인 실패: 로그인 자리도 상태 줄도 없다"(AC-1이 반대로 바꾼다), `MortgageHub.accountQa`의 "계정 확인 실패(500 + session-hint): 쓰기 0회"와 "로그인: 링크는 카드 3개뿐", `platform-home` AC-7(c)("오류 문구 없음", A6), `AppRoutes` 쪽 `#/?login=failed → #/` 행(AC-2에만 언급). 이 반전 테스트들과 함께 쓰기를 저장 목록에서 Hub로 옮기며 바뀌는 문구(U8) 테스트도 R/T/X와 같은 형식의 감사표에 넣는다. 분류는 반전(I)을 새로 두고, I마다 옛 단언 → 새 단언과 이유를 적는다.

## 누락된 경계·미정의 동작(스펙에 정의를 요청)

- 홈에는 출처가 둘이다(`listingSource`, `planSource`; 계정 자리는 `listingSource.status`만 본다). "홈의 출처가 401"이 어느 쪽인지 정의돼 있지 않다. 계획 출처만 401이거나 매물 출처만 401일 때 안내 한 줄·계정 자리가 어떻게 되는지 각각 정한다(테스트는 둘 다 만든다).
- `POST /api/auth/logout`이 401(이미 끝난 세션)·네트워크 오류일 때. 401은 사실상 로그아웃 성공이다. 실패 줄과 세션 만료 줄 중 무엇인지, 상태가 로그아웃으로 바뀌는지 정한다.
- 안내 줄 규칙. "한 줄씩"이 동시에 몇 줄까지 쌓이는지, 새 동작이 시작되면 옛 결과를 지우는지(나가기 실패 뒤 재시도 성공 시 실패 줄 제거, 로그아웃 성공 시 나가기 결과 제거 등). 지금 서술로는 "로그아웃 실패 줄을 로그아웃 뒤에도 남기기"는 변이로 잡히지만 나머지 조합은 판정 기준이 없다.
- `?login=` 복귀 직후 이미 로그인된 상태로 해석되는 경우의 안내 순서(로그인 결과 + 세션 만료 동시).
- 포커스. [로그아웃]·[나가기]를 누르면 그 버튼이 사라진다. 포커스가 어디로 가는지(계정 자리 또는 안내 줄)와 안내 줄의 `role="status"`/`aria-live` 여부를 정하지 않으면 테스트가 질의할 수단이 없다. 지금 `HeaderNotices`가 쓰는 역할을 그대로 쓴다고 명시한다.
- 중복 클릭. [로그아웃]·[나가기]는 "누르는 동안 비활성"이라 요청 1건 단언이 가능하다. [나가기]에도 같은 문장이 필요하다.
- A3·A4에 대응하는 AC가 없다. 추가: 해시 `#/`(login 없음)에서 안내 없음, 공유받기 화면에서 로그인한 성공 복귀(초대 쿠키 없음)가 `#/`.
- 계정 확인 실패: 세션 힌트 없는 500은 "로그아웃처럼 로그인이 보인다"(기존 accountQa)와 이번 [다시 시도] 줄이 어느 쪽인지(힌트 유무로 갈리는지) 표에 명시. [다시 시도] 재실패·재성공 각각.

### 경계값 표 (테스트 작성 시 쓸 입력)

- parseRoute: `#/?login=failed|cancelled|notConfigured`, `#/?login=`(빈 값), `#/?login=FAILED`(대소문자), `#/?login=failed&a=1`, `#/?login=failed&login=cancelled`(중복), `#/?login=constructor`·`toString`·`__proto__`(`in`/객체 조회로 허용 값을 검사하면 통과해 버리는 입력), `#/calculator?login=failed`·`#/home?login=failed`(홈 아닌 경로는 `login` 불유지), `#/listings?login=failed&x=1`. 왕복(`toRoutePath`)도 확인: `{hub, login}` → `#/?login=…`, `{hub}` → `#/`.
- 서버 `Location`/`Set-Cookie`(현재 테스트가 0개이므로 먼저 **옛 값 그대로 고정하는 특성 테스트**를 쓰고 그 diff로 5개 Location만 바뀐 것을 보인다): 키 둘 다 없음 / 하나만 비어 있음 / 공백만(`trim`) → notConfigured. state 쿠키 없음·null·불일치 → failed(`error=access_denied`가 같이 와도 state가 먼저라 failed). `error=access_denied` → cancelled. `error=server_error` → failed. `code` 없음·빈 문자열 → failed. 토큰 교환 실패 → failed. 성공 + 초대 쿠키 정상 → `#/invite/{token}`. 성공 + 초대 쿠키 모양 불량 → `#/`(초대 아님). 성공 + 쿠키 없음 → `#/`. 포트가 있는 origin. 모든 경우 302, `Cache-Control: no-store`, `Set-Cookie` 목록 순서·내용 완전 일치(`clearStateCookie`, `clearInviteCookie`, 세션).
- 계정 자리 상태 5행 × 로그아웃/실패 응답 (200·401·500·네트워크 오류).

## 감사 규칙 개정(가리기 테스트를 R로 허용)의 위험

- 위험 1. R의 단위가 "파일"이다("R로 지운 파일마다 …바꿔 쓴다"). 한 파일에 우리 집 가리기 테스트(R)와 storage 단언(T)이 섞여 있다. 가리기 언급은 `Home/*.test.tsx` 약 67줄, `AppRoutes.storageKeys.*` 6개 파일에 퍼져 있다. 파일 단위로 R을 허용하면 storage 단언이 같이 지워져도 눈에 안 띈다.
- 위험 2. 허용 범위가 "우리 집·홈 가리기"인데 `MortgageHome.table.test`(내보내기 비활성), `lineOrderQa`, `tbd*`, `wonUnit` 같은 파일의 가리기 `it`는 표 병합·정렬·0원 같은 다른 주제의 단언을 한 `it` 안에 함께 갖고 있을 수 있다. `it` 단위로 쪼개 보지 않으면 비가리기 단언이 사라진다.
- 위험 3. "AC-5·6 단언으로 바꿔 쓴다"가 새 단언을 빼고 R만 남기는 것을 막는 기계적 확인이 없다.
- 개정안(조건):
  1. 분류 단위를 `it`로 한다(파일 단위 아님). 감사표 열: 파일 · 지운 `it` 이름 · 분류(R/T/I) · 대체 테스트 이름.
  2. 지우기 전·후 `it` 개수와 `setItem|removeItem|clear|toBe\(.*(raw|seed)|===` 포함 단언 줄 수를 `git show main:<file>`과 비교해 감소가 감사표의 R 항목과 1:1로 맞는지 스크립트로 확인한다(qa 기록에 출력 첨부).
  3. 반전(I)을 새 분류로 둔다(홈 로그아웃 버튼·계정 확인 실패·`#/?login`·홈 401·함께 쓰기 문구). X(설명 없음)는 0.
  4. 새 "켜져 있어도 보인다" 테스트는 **먼저 현재 코드에서 실패(red)함을 확인**한 뒤 구현으로 통과시킨다. 이것이 변이 검증을 대신하는 가장 싼 방법이다.
  5. 이동(함께 쓰기를 Hub로)은 삭제가 아니라 T(이동)로 분류하고 `git diff -M`에서 유사도 100%(경로만 변경)를 기록한다.
- 이 개정 자체는 좁게 한정돼 있어(이 범위에서만) 받아들일 수 있다.

## 변이 후보 (스펙 목록에 더할 것)

기존 스펙 목록(복귀 주소 `#/listings`, `login` 안 지움, 실패 줄 잔존, 목록에 로그아웃 재삽입, 확인 중 [로그아웃] 포커스, 나가기 취소인데 요청, 재조회 빼기, 포커스 복귀 빼기, 로그아웃 상태 [함께 쓰기], 401 줄 빼기, 목록에 "함께 쓰는 중", 우리 집이 `privacy-mode` 읽기, 내보내기 비활성 부활, 홈 가림 부활, 저장 목록 가림 끄기)에 더한다.

1. parseRoute가 허용 값을 `in`/인덱싱으로 검사(`login=constructor` 통과).
2. `replace` 대신 `push`(AC-2의 `history.length`가 잡는다).
3. 홈이 `login`을 주소에서 지운 뒤에 상태에 저장(안내가 안 뜸) 또는 지우기 전에 두 번 저장(StrictMode에서 두 번 뜸). StrictMode 렌더 1건을 AC-2에 넣는다.
4. 서버: 초대 성공 분기에서 `#/`로 보냄 / 모양 불량 초대 쿠키를 초대 화면으로 보냄 / 실패 분기에서 `clearInviteCookie` 누락 / `Cache-Control` 누락.
5. 나가기 404를 실패로 처리 / 나가기 성공인데 안내 안 보임 / 나가기 성공 뒤 둘째 줄이 그대로 "n명이 함께 쓰는 중".
6. 확인 문구에서 "인테리어 계획" 빼기(`confirm` 문구는 `vi.spyOn(window,"confirm")`로 부분 문자열 단언).
7. 시트 열고 닫기, 나가기, 로그아웃 중 하나가 localStorage에 쓰기(AC-0 순회가 잡는지).
8. 우리 집에서 [가리기]를 숨겼지만 `privacyModeStore` 구독이 남아 표 보기 안내만 "가리기를 끄면…"으로 나옴(AC-5 문구 부재 단언).
9. 저장 목록 `HeaderNotices`가 `login` 결과를 계속 처리(`#/listings?login=failed` 안내 없음 단언).
10. 로그아웃 성공 뒤 계정 자리는 바뀌지만 카드가 서버 값으로 남음(재조회 누락).

## 리스크

- 가장 큰 리스크는 AC-0이다. 대조군 서술 오류(1)와 횟수 단정(2)이 그대로면 정상 구현이 실패하거나, 반대로 허용을 넓혀 새는 쓰기를 통과시킨다.
- 반전 테스트가 많아(홈 계정, 가리기, 문구, 로그인 복귀) 감사표 없이 진행하면 약화 은닉 위험이 크다. 감사 규칙 개정안을 스펙 AC-7에 반영한다.
- 홈 안내가 메모리 상태이고 탭 이동 시 사라지는 설계라, 결과를 놓친 사용자의 복구 경로는 없다(테스트 문제가 아니라 제품 판단. 스펙의 다음 단계 후보 수준으로 충분).
- jsdom의 한계: `inert`, 실제 포커스 이동, 360px 레이아웃, 카카오톡 인앱 브라우저, 실제 카카오 OAuth는 자동 검증 불가.

## 화면에서 직접 확인할 항목(자동화 불가)

1. 360×780에서 계정 자리 두 줄이 줄바꿈 없이 들어가는지, 확인 중 → 확인 뒤 카드가 밀리지 않는지.
2. 시트가 열렸을 때 뒤 화면이 실제로 탭·클릭되지 않는지(`inert` 실동작), 닫을 때 포커스가 [함께 쓰기]로 돌아오는지, 나가기·로그아웃 직후 포커스 위치.
3. 실제 카카오 로그인 성공·취소가 홈으로 돌아오는지(카카오톡 인앱 브라우저 포함), 초대 링크 로그인은 초대 화면인지.
4. 저장 목록 [가리기]를 켠 뒤 우리 집·홈의 값이 보이는지와 그 노출이 의도된 것인지(U6).

## 조건(찬성으로 바꾸는 요건)

1. AC-0 대조군을 "시드가 켜짐이라 끄기 → 켜기, `setItem "false"` → `"true"`"로 고치고, 우리 집·표 보기·홈 단계의 `privacy-mode` 쓰기 0회를 추가한다. (a)의 `removeItem` 횟수는 측정 후 고정하거나 종류로 단언한다. 모드는 pending 포함 4개로 쓴다.
2. AC-7의 분류 단위를 `it`로 바꾸고 반전(I) 분류를 신설하며, 단언 줄 수 감소를 스크립트로 확인한다. 새 "켜져 있어도 보인다"·홈 로그아웃 테스트는 현재 코드에서 먼저 실패함을 확인한 뒤 구현을 통과시킨다.
3. 누락된 경계(홈 401 출처, 로그아웃 401·네트워크 오류, 안내 수명, 포커스·`role`, [나가기] 중복 클릭, A3·A4의 AC)를 스펙에 한 줄씩 정의한다.
4. AC-2 be 테스트는 옛 값 고정 특성 테스트를 먼저 쓰고 5개 Location만 바뀌는 diff로 만든다. 입력 조합은 위 경계 표를 쓴다.
5. AC-5 grep 범위에 `INTERIOR_PLAN_EXPORT_NOTICES.privacyMode`와 "가리기를 끄면"을 포함한다.
6. U6는 사용자 확인 뒤에 AC-6을 확정한다. U4의 문구는 같은 시점에 확인한다.
