# 데이터 조회 로딩: 스켈레톤으로 한 번에 나타나기

> 작성 2026-11-12 · 브랜치 `cony/loading-skeleton` · 상태: 초안(검토 전)
> 관련: 스펙 `platform-home.md`(홈 카드별 상태표 AC-7, 로딩 중 로컬 값 플래시 금지) · ADR-031 조건 2(카드별 독립 상태 — 이 스펙이 "로딩" 부분만 갱신, U1) · 스펙 `ui-refresh.md`(CSS `gradient|blur|uppercase` 금지) · `design-polish.md`(글자 토큰) · `.cony/log.md` 2026-11-07 "vitest는 CSS를 비워 읽음"·"왜 이렇게 오래걸려?"

## 요청(원문)

- "데이터 조회일 때 로딩을 넣어줄 수 있나, 예로 loan.conychoi.dev 접속하면 홈 탭이 기본인데 로딩되는대로 하나씩 표시되는데 이상하다. 각자 로딩을 해주던지 한번에 로딩을 해주던지 아니면 스켈레톤!!!! 으루"

## 목표

서버에서 데이터를 받아 오는 동안 실제 내용과 같은 모양·같은 자리의 회색 막대(스켈레톤)를 보이고, 한 화면의 내용은 **다 받은 뒤 한 번에** 나타나게 한다. 받는 순서대로 하나씩 튀어나오거나 아래 내용이 밀리는 일을 없앤다. 서버·저장 형식·계산은 그대로다.

## 사용자 시나리오

1. (로그인, 처음 열기) loan.conychoi.dev를 열면 홈 제목과 카드 제목은 바로 보이고, 매물·예산 카드의 숫자 자리와 제목 줄 오른쪽 계정 버튼 자리에 회색 막대가 은은하게 깜빡인다. 잠시 뒤 숫자·버튼·함께 쓰기 줄이 **한꺼번에** 나타나고, 그 순간 카드 위치는 움직이지 않는다.
2. (빠른 회선) 응답이 0.3초 안에 오면 회색 막대는 보이지 않고 바로 내용이 나온다.
3. (탭 이동) 매물 탭을 처음 열면 예산 줄·목록 자리에 스켈레톤이 있다가 예산·목록·순서가 한 번에 나온다. 홈으로 돌아왔다 다시 오면 스켈레톤 없이 바로 보인다.
4. (실패) 매물 조회가 실패하면 드러날 때 매물 카드는 "불러오지 못했습니다", 예산 카드는 정상 요약이다(지금과 같음).
5. (동작 줄이기·다크 모드) 기기에서 동작 줄이기를 켜면 막대가 움직이지 않는다. 다크 모드에서도 막대가 면과 구분된다.
6. (스크린리더) 로딩 중 카드는 지금처럼 "불러오는 중"으로 읽히고, 막대 하나하나는 읽히지 않는다.

## 진단: 지금 무엇이 하나씩 튀어나오나

react-query 기본값(`staleTime 0`, 재시도 없음). 캐시가 있으면(탭을 다녀옴) 바로 그려지므로 문제는 **앱을 처음 열 때와 로그인 직후**다. 로그아웃 사용자도 `/api/me` 응답 전에는 출처가 `loading`이다(`selectAccountSourceStatus`).

### 홈(`Hub/MortgageHub.tsx`) — 로그인 사용자 기준 순서

- **첫 그림**: 제목 "홈", 제목 줄 오른쪽 빈 자리, 대출 계산 카드는 draft로 바로 채워짐, 매물·예산 카드는 "불러오는 중" 한 줄 글자(`HubCard` `STATUS_TEXT`), 계정 자리는 보이지 않는 자리 표시(`HubAccount` `placeholder`).
- **① `GET /api/me`**: 제목 줄 오른쪽에 [카카오 로그인] 또는 닉네임·[로그아웃]이 튀어나옴(`HubAccountAction`이 로딩 중 `null`). 계정 자리 등장. 로그아웃이면 여기서 카드도 채워짐.
- **② `GET /api/listings`**: 매물 카드가 한 줄(약 20px) → 라벨+숫자 두 줄(`HubSummaryPair`, 약 50px)로 커지며 아래 예산 카드·계정 자리를 밀어냄.
- **③ `GET /api/interior-plans`**: 예산 카드가 한 줄 → 계획 수 × 두 줄로 커지며 계정 자리를 밀어냄.
- (가끔) 이전 문제·세션 만료: `HubNotices` 줄이 카드 위에 끼어 전체가 밀림.

②와 ③은 병렬이라 순서가 매번 다르다. 사용자가 본 "하나씩"은 ①②③이 따로 오는 것, "이상하다"는 ②③의 밀림이다.

### 같은 문제가 있는 다른 곳

- **매물(`Listings/MortgageListings.tsx`)**: "저장 목록을 불러오는 중" 한 줄 → 목록을 받으면 `BudgetBar`("예산을 불러오는 중") + "직접 정한 순서를 불러오는 중" → 예산(`useAccountBudget`)·순서(`useAccountListingOrder`)가 각각 와서 표가 나타남. 제목 줄 [가리기]·[목록 공유]도 목록과 함께 튀어나옴. 3~4단계 → **범위에 넣는다.**
- **예산(`Home/MortgageHome.tsx`)**: h1 "예산" + "예산 계획을 불러오는 중" → 계획 화면 전체로 바뀜. 계획이 매물에 연결돼 있으면 매물 목록이 늦게 와 "연결된 매물 · 이름" 줄이 제목 아래 끼어들며 밀어냄(`linkedListingOf` → `unknown`이면 `null`). 매물 카드에서 들어온 경우 "매물을 확인하는 중". → **범위에 넣는다.**
- **실거래가 시트(`Calculator/components/TradeResults.tsx`)**: 이미 스켈레톤(줄 높이 44px 회색 막대 3개, 움직임 없음, `role="status"` + `aria-label`). 모양은 맞음 → **공통 부품으로 바꾸기만 한다.**
- 계산 화면 [저장] 버튼 "저장 목록을 불러오는 중입니다"(버튼 비활성 문구, 자리 이동 없음), 시트들의 버튼 `isPending`(쓰기 진행 표시, 조회 아님) → 범위 밖.
- 공유받기·초대(`StatusPanel` "공유받은 매물을 불러오는 중"/"초대를 불러오는 중"): 링크로 한 번 들어오는 화면이고 한 단계라 하나씩 문제는 없음 → 다음 단계 후보.

### 이미 있는 것

- 스켈레톤 라이브러리 없음(`package.json`). 회색 막대 선례는 `TradeResults.module.css` `.skeletonRow`(`--color-raised`) 하나.
- 색은 모두 `light-dark()` 토큰이라 다크 모드가 따라온다. 흰 면 위 채움 `--color-raised`, 바탕 위 채움 `--color-raised-on-bg`.
- `prefers-reduced-motion` 규칙이 이미 여러 곳(`index.css`, `Sheet`, `TabNav`)에 있다.
- 숨김 글자(보조기기 전용) 클래스는 모듈마다 따로(`HubAccountAction`·`MortgageListings` `.visuallyHidden`).

## 참고한 사례

- **React `Suspense` 문서**: 한 경계 안의 것들은 "다 준비되면 한꺼번에" 나타나고, 경계는 "사용자에게 보여 주고 싶은 로딩 순서보다 잘게 나누지 말라". React는 드러내기를 최소 300ms 간격으로 묶는다. → 한 화면을 한 경계처럼 다룬다(U1). 300ms는 지연 기본값의 근거(U3). https://react.dev/reference/react/Suspense
- **GitHub Primer 로딩 패턴**: 작은 영역이 붙어 있으면 항목마다 표시하지 말고 하나로. 1초 안에 끝나는 로딩은 표시하지 않는 편이 낫다(깜빡임이 더 느리게 느껴짐). 내용이 들어올 때 레이아웃 이동을 피한다. 스켈레톤 묶음에는 알림 하나, 갱신 중인 영역에 `aria-busy`. (Primer는 줄어든 움직임에서도 은은한 움직임을 끄지 말라고 하지만, 이 앱은 이미 모든 움직임을 끄는 규칙이라 그것을 따른다.) → 홈 카드 세 줄은 붙은 작은 영역이라 하나로(U1), `aria-busy` + 기존 문구 하나(AC-6). https://primer.style/product/ui-patterns/loading/
- **NN/g Skeleton Screens 101**: 스켈레톤은 화면 전체 로딩용이고 최종 구조를 그대로 흉내 낸다(제목은 굵은 막대, 설명은 얇은 막대). 1초 안이면 아무것도 보이지 않아도 된다. 움직이는 스켈레톤은 산만하거나 접근성 문제가 될 수 있다. 머리·바닥만 그리는 "틀 스켈레톤"은 피한다. → 실제 줄 모양을 따른 막대, 은은한 움직임 + 줄어든 움직임에서 끔(U2). https://www.nngroup.com/articles/skeleton-screens/
- **토스 TDS Skeleton(React Native)**: `width`·`height`·`borderRadius`만 받는 회색 블록을 실제 목록 줄 모양으로 조합해 쓴다. 움직임·지연 규칙은 문서에 없다. → 우리 부품도 크기·모서리만 받는 막대 하나로 단순하게. https://tossmini-docs.toss.im/tds-react-native/components/skeleton/
- **토스·뱅크샐러드·Linear 앱 홈의 실제 동작**: 공개 문서로 **확인하지 못했다**(지어내지 않음).
- **react-loading-skeleton**: 반짝임이 `::after`의 `linear-gradient`가 옆으로 흐르는 방식이고 줄어든 움직임이면 끈다. → 이 앱은 CSS `gradient`를 금지(ui-refresh)하므로 반짝임 대신 밝기 맥박(opacity)을 쓴다(D1). https://github.com/dvtng/react-loading-skeleton
- **지연 표시**: "200~300ms 지나도 로딩이면 그때 보이기"가 흔한 관례로 블로그·훅 라이브러리에 반복되지만 표준 문서는 찾지 못했다. React의 300ms 묶음과 맞춰 300ms를 제안한다(U3).
- **우리 선례**: `TradeResults` 스켈레톤(줄 높이 그대로 회색 막대), `HubAccount`의 "확인 뒤 들어갈 내용을 보이지 않게 그려 자리 지키기", 홈 로딩 중 로컬 값 플래시 금지(platform-home AC-7(b)).

## 화면

### 규칙 하나: "한 화면은 한 번에"

화면마다 **첫 화면에 보일 조회가 모두 끝났는지**(성공·실패·손상·빈 상태 무엇이든 "로딩이 아님") 하나의 값으로 정한다. 끝나기 전에는 데이터 자리 전부가 스켈레톤이고, 끝나면 **같은 렌더에서** 모두 실제 내용으로 바뀐다. 기존 상태 유니온(`status: "loading"`, `HubCardSummary.kind`) 위에서 파생한다(D2 A).

- 처음부터 아는 것(제목, 카드 제목, 정적 문구, 로컬 draft)은 첫 그림부터 그대로 보인다. 첫 그림에 있던 것은 "튀어나옴"이 아니다.
- 실패·손상·저장소 없음·빈 상태는 스켈레톤이 아니다. 드러낸 뒤 지금과 같은 문구·버튼이 나온다(카드별·영역별로 따로, ADR-031 조건 2의 실패 독립성은 그대로).
- 캐시가 있어 처음부터 끝난 상태면 스켈레톤은 한 번도 그려지지 않는다. 뒤에서 다시 받는 중(`isFetching`)은 로딩이 아니다.

### 스켈레톤 막대(공통 부품, D1 A)

- 위치: `src/components/Skeleton.tsx` + `Skeleton.module.css`(홈·매물·예산·계산 네 container가 쓴다. 태스크 1만 따로 배포하더라도 같은 PR의 태스크 2가 곧 쓴다).
- 모양: 크기(가로·세로)와 모서리만 받는 회색 막대. 글자 자리는 **바꿀 글자와 같은 글자 크기·줄 높이 상자 안에** 높이 1em 안팎의 막대를 놓아, 줄 상자 높이가 실제 글자와 같게 한다(자리 이동 없음의 핵심). 버튼 자리는 버튼 높이(36px)·모서리(`--radius-small`)로.
- 색: 흰 면 위 `--color-raised`, 바탕 위 `--color-raised-on-bg`. 새 색 없음, `light-dark()` 토큰이라 다크 모드가 따라온다.
- 움직임(U2): 밝기 맥박(`opacity` 1 → 약 0.5 → 1, 약 1.6초, 무한). `gradient` 없음. `prefers-reduced-motion: reduce`면 움직이지 않는 회색 막대.
- 지연(U3): 자리는 첫 그림부터 차지하되 막대는 **300ms 동안 투명**했다가 보인다(CSS `animation-delay`, JS 타이머 없음). 300ms 안에 끝나면 회색은 한 번도 안 보이고 바로 내용이 나온다. 줄어든 움직임이어도 지연은 그대로(움직임이 아니라 나타나는 시점).
- 보조기기: 막대는 `aria-hidden="true"`. 로딩 영역은 `aria-busy="true"`이고 **지금 쓰는 로딩 문구를 숨김 글자로 그대로** 둔다(예: "불러오는 중", "저장 목록을 불러오는 중"). 그래서 스크린리더가 읽는 것과 기존 테스트가 찾는 글자가 바뀌지 않는다. 막대마다 알리지 않고 영역마다 문구 하나(Primer). 드러낸 뒤 `aria-busy`는 없다.
- 가리기 모드와 무관(막대에는 값이 없다).

### 홈

- 한 번에 묶는 것: 매물 카드 요약 줄, 예산 카드 요약 줄, 제목 줄 계정 버튼 자리(`HubAccountAction`), 계정 자리(`HubAccount`). 조건 = 출처 상태가 `loading`이 아니고 두 카드 요약이 모두 `loading`이 아님.
- 대출 계산 카드: draft는 로컬이라 첫 그림부터 내용 그대로(기다리지 않음).
- 카드 요약 줄 스켈레톤: `HubSummaryPair` 두 줄 모양 — 첫 줄 라벨 막대(본문 글자 상자, 약 6em), 둘째 줄 숫자 막대(`--fs-figure` 상자, 약 5em). 예산 카드는 계획 한 개 모양(두 줄). 지금의 "불러오는 중" 한 줄 글자는 숨김 글자로 남아 카드 링크 설명(`aria-describedby`)이 지금처럼 "불러오는 중"이다.
- 제목 줄 계정 버튼 자리: 바탕 위 36px 알약 막대(로그인 버튼 정도 폭). 드러낼 때 버튼으로 바뀐다(가로만 달라지고 세로 이동 없음).
- 계정 자리: 지금처럼 보이지 않는 자리 표시(이미 정확한 높이를 지킨다)를 쓰되, `me`가 아니라 위 "한 번에" 조건으로 드러낸다.
- 받은 결과가 소개 문구(데이터 0개)나 계획 2개 이상이면 드러낼 때 카드 높이가 한 번 바뀐다. 모두 같은 렌더라 "하나씩"은 아니다(마지막 모양 기억은 다음 단계 후보).
- 로그아웃 사용자: `/api/me` 하나만 기다리면 로컬 값으로 한 번에 드러난다. 로그인 직후(`#/?login=`) 이전 중이면 이전이 끝날 때까지 스켈레톤.

### 매물

- 한 번에 묶는 것: 목록(`list`), 예산(`budgetSource.state`), 직접 정한 순서(`orderSource.state`) — 셋 다 `loading`이 아니어야 드러낸다. 제목 줄 [가리기]·[목록 공유]도 이때 함께.
- 본문 스켈레톤 하나: 예산 줄 모양(흰 면, 라벨 막대 + 금액 막대 + 버튼 막대) → 표 머리("이름 / 필요한 자기자금", 정적이라 글자 그대로) → 줄 3개(`--row-min-height`, 이름 막대 + 금액 막대).
- 이전 중(`accountImport` running): "이 기기의 매물을 계정으로 옮기는 중"은 **보이는 한 줄**로 스켈레톤 위에 남긴다(가정 A3).
- 드러낸 뒤 예산·순서 실패는 지금처럼 그 자리 문구와 [다시 시도]. 중간 상태 "예산을 불러오는 중"·"직접 정한 순서를 불러오는 중"은 첫 진입에서 보이지 않는다(그 컴포넌트의 로딩 분기는 재시도 등으로 다시 로딩될 때를 위해 남겨도 된다 — fe 판단).

### 예산

- 한 번에 묶는 것: 계획 목록. 열 계획이 정해졌고(`currentPlan`) 그 계획에 `listingId`가 있으면 매물 목록까지(연결 매물 줄이 늦게 끼어들지 않게).
- 본문 스켈레톤: 요약 카드 모양(흰 면, 라벨 막대 + 큰 숫자 막대 + 두 줄) → 묶음 2개(제목 막대 + 줄 3개). h1 "예산"은 지금처럼 로딩 중에 보이고, 드러낼 때 계획 화면 머리글로 바뀐다(같은 렌더).
- 매물에 연결된 계획은 계획 목록이 오기 전에는 연결 여부를 알 수 없어, 연결 매물 줄 높이(약 20px)만큼 한 번 바뀔 수 있다(계획이 먼저 오면 스켈레톤 중간, 매물 목록이 먼저거나 함께 오면 드러날 때). 홈과 같이 허용하고 마지막 모양 기억은 다음 단계 후보.
- "이 기기의 예산 계획을 계정으로 옮기는 중"은 매물과 같이 보이는 한 줄로 남긴다. "매물을 확인하는 중"도 같은 스켈레톤 + 숨김 문구.

### 실거래가 시트

- `TradeResults`의 `.skeletonRow` 3개를 공통 막대로 바꾼다(높이 44px·간격 그대로, 맥박·지연·줄어든 움직임 규칙을 따름). `role="status"` + `aria-label="실거래가를 불러오는 중"`은 그대로.

### 반복 사용 불편 점검

- 탭을 오가면 캐시가 있어 스켈레톤이 다시 뜨지 않아야 한다(AC-1 마지막 항목). 매번 회색이 깜빡이면 오히려 나빠진다.
- 빠른 회선(300ms 안)에서는 회색이 아예 안 보여 지금보다 깜빡임이 줄어야 한다.
- 스켈레톤 중에도 카드 링크·탭은 누를 수 있다(지금처럼).

## 가정

- A1: 사용자가 말한 "로딩되는대로 하나씩"은 처음 열 때(캐시 없음)의 홈이다. 탭을 오갈 때는 캐시로 바로 그려져 이번 변경 대상이 아니다.
- A2: "스켈레톤"은 실제 내용 모양의 회색 막대를 뜻하고, "각자/한번에"는 스켈레톤이 걷히는 시점의 선택으로 읽는다(U1).
- A3: 계정 이전 중 안내("…계정으로 옮기는 중")는 로그인 직후 한 번, 평소보다 오래 걸리는 이유라 스켈레톤으로 가리지 않고 보이는 한 줄로 남긴다(NN/g: 길어지는 대기는 이유를 알린다).
- A4: 홈 "한 번에"는 ADR-031 조건 2 "카드별 독립 상태"를 **로딩에 한해서만** 바꾼다. 실패·손상·빈 상태는 여전히 카드별이다. 채택되면 리드가 ADR-031에 개정 한 줄을 단다.
- A5: 기존 테스트는 로딩 문구를 글자·`aria-busy`로 찾으므로 문구를 숨김 글자로 남기면 대부분 고치지 않고 통과한다(`toHaveAccessibleDescription("불러오는 중")`은 `aria-hidden` 막대를 빼고 숨김 글자를 읽는다). fe가 1-2 첫 단계에서 `grep`으로 확인한다.

- **D2 "한 번에" 구현**: A 화면마다 기존 상태 유니온에서 "다 끝남" 값 하나를 파생 / B React `Suspense` + `useSuspenseQuery`로 옮기기 — 추천 **A**. 이유: B가 React 관례에 더 가깝지만 출처 훅(`useListingSource`·`useInteriorPlanListSource`)과 이전·세션 만료·로컬 플래시 금지 규칙, 수십 개 테스트를 다시 짜야 한다. A는 각 container에서 몇 줄이고 상태 유니온과 테스트 방식을 그대로 쓴다. 화면이 더 늘어 같은 조건식이 세 곳 넘게 복붙되면 B를 다시 본다.

## 사용자 확인 필요

제품 기본값(쓰는 느낌)이다. 답이 오기 전에는 **굵은 제안값**으로 진행한다. 모두 되돌리기 쉽다(조건식·CSS 몇 줄).

- **U1 한 번에 vs 각자**: **화면마다 한 번에.** 홈은 매물·예산 카드·계정 버튼이 다 올 때까지 스켈레톤이고 같이 나타난다(대출 계산 카드는 기기 값이라 처음부터 보임). 매물·예산 탭도 같다. 대가: 가장 느린 요청만큼 기다린다(병렬이라 보통 차이는 작다).
  - 대안: 카드별로 각자 스켈레톤 → 각자 채워짐(자리를 지키므로 밀림은 없지만 하나씩 나타나는 것은 남는다).
- **U2 움직임**: **은은한 밝기 맥박**(약 1.6초 주기), 기기에서 "동작 줄이기"를 켜면 멈춘 회색.
  - 대안: 움직임 없는 회색(지금 실거래가 시트처럼) / 옆으로 흐르는 반짝임(ui-refresh의 그라데이션 금지를 풀어야 함).
- **U3 짧은 로딩은 안 보이기**: **300ms 안에 끝나면 회색을 보이지 않는다**(자리는 처음부터 지킴).
  - 대안: 바로 보이기(빠른 회선에서 회색이 번쩍일 수 있음).
