# ADR-029 인테리어 플래너의 저장 모델·진입·매물 연결·함께 쓰기 범위

- 상태: 채택
- 맥락: 계약한 집의 인테리어를 턴키 없이 공간·공종별로 따로 맡기며 예산·견적·지급·일정을 관리하고 싶다(사용자 요청). 기존 기능은 그대로 두고 계산기가 첫 화면이어야 한다. 저장 모델, 화면 진입, 매물과의 관계, 함께 쓰는 목록과의 범위를 정해야 했다. 스펙: [interior-planner](../specs/interior-planner.md)
- 선택지:
  - D1 A 플랜 한 행에 전체 JSON / B 정규화 테이블(견적·지급 행) / C 플랜 행 + 항목 행(항목 안에 견적·지급 JSON)
  - D2 A 세 번째 탭 [우리 집] + 매물 카드 진입 / B 매물 카드 안에서만 / C 별도 앱
  - D3 A 플랜에 선택적 `listingId` 참조 + 매물의 인테리어 추가 비용 줄을 한 번 복사 / B 매물 안에 플랜 포함 / C 연결 없음
  - D4 A 매물과 같은 가구 범위·숨김·복귀 / B 개인 전용
  - D5 A 만원 정수 / B 원 단위
- 의견: pm(전부 추천안) / be(D1·D4 조건부, D2·D3·D5 찬성) / fe(D1·D2 조건부, D3·D4·D5 찬성) / qa(조건부 찬성: AC 값 대부분 맞음, "앞으로 낼 돈" 정의 미구분, 하네스는 `@cloudflare/vitest-plugin`)
- 검토 원문: [be](../reviews/20261026-1622-be-spec-interior-planner.md) · [fe](../reviews/20261026-1622-fe-spec-interior-planner.md) · [qa](../reviews/20261026-1622-qa-spec-interior-planner.md)
- 결정: D1 C, D2 A, D3 A, D4 A, D5 A. 아래 조건을 구현 필수로:
  1. **항목 넣기 가드(be 1)**: import·POST의 항목 INSERT는 같은 batch의 직전 플랜 INSERT가 1행을 넣었을 때만 돈다. 플랜이 이미 있으면 상한에 걸려도 400이 아니라 `imported: 0`. 하네스 변이 테스트로 고정(가드 삭제 시 실패).
  2. **검증(be 2)**: 알려진 키만 새 객체로 복사해 저장. `spaces[].id`·`quotes[].id`·`payments[].id`·import `items[].id` 유일성. 시각은 `toISOString` 형식만, 금액은 견적·지급·예산 모두 `Number.isSafeInteger` 1~999,999,999.
  3. **계약(be 3)**: 응답·요청 봉투 `{ plan }`·`{ item }`. 경로 id 형식 오류 400 `invalidParams`, id `import` 거부. `/import`를 `:id`보다 먼저 라우팅. POST `items?`는 30개 이하·id 서버 발급. 항목 POST 0행은 같은 batch 두 번째 문장으로 404/400을 가른다. GET은 플랜·항목을 한 `db.batch`로. 항목 쿼리는 모두 `householdScope.ts`의 한 플랜 범위 조각을 쓴다. 성공 응답 no-store.
  4. **가구 batch(be 4)**: 수락은 새 문장을 마지막 문장 앞에. 나가기는 새 문장을 맨 끝에 두고 `[, , , cleared]` 인덱스 의존을 이름으로 바꾼다. 0-4 테스트가 먼저 머지된다. 배포는 원격 0007 적용 → PR 머지 순서(새 Worker + 옛 스키마면 나가기가 막힘).
  5. **함께 쓰는 중 import 서버 차단(be 5 채택)**: `/api/interior-plans/import`는 요청자가 가구 구성원이면 409 `inHousehold`. 새 엔드포인트라 옛 클라이언트가 없고, 클라이언트 `me.household`가 낡았을 때도 서버가 최종 판단한다. 기존 매물 import에는 넣지 않는다(동작 무변경, 태스크 0 클라이언트 수정으로 막음).
  6. **태스크 0 재실행(fe 1·2)**: 이전 상태에 `skipped`(사유 household)를 두고 `skipped && household === null`이면 다시 실행. 예산·순서는 skipped여도 계정 조회를 켠다. 플랜 이전 기록은 `Record<userId, planId[]>`. 수락 시 미리 완료 표시하지 않는다. "household가 null로 바뀌면 send 1회" 테스트 포함.
  7. **클라이언트 경계(fe 3·5)**: `useLeaveHousehold`·`useAcceptHouseholdInvite`의 무효화에 `interiorPlanListQueryKey()` 추가(파일 소유에 포함). 카드는 플랜 GET을 부르지 않고 `#/home?listing={id}`로 보내며, Home이 연결 플랜을 찾으면 `#/home/{planId}`로 replace. 연결 플랜이 여럿이면 첫 번째.
  8. **같은 항목 동시 편집(fe 6, 클라이언트만)**: 시트를 연 시점의 `updatedAt`과 저장 직전 캐시의 `updatedAt`이 다르면 "다른 사람이 고쳤습니다"를 띄우고 다시 불러오게 한다. 서버 409(조건부 PUT)는 이번엔 넣지 않는다(be도 빈도 대비 복잡도로 비추천).
  9. **계산 정의(fe·qa)**: "앞으로 낼 돈"은 확정 항목별 `max(확정 금액 − 그 항목 지급함, 0)`의 합(qa 정의 다). 확정 안 된 항목의 지급 줄은 더하지 않고, 과지급 항목은 0. AC-4에 정의를 가르는 기대값을 넣는다: P에서 D만 확정하면 1,150, 샷시 잔금까지 지급하고 D 확정이면 250. 할 일 "견적 받기"는 견적 0개·미확정, "확정하기"는 견적 1개 이상·미확정.
  10. **구조(fe·qa)**: `MaskedValue`를 `src/components/`로 승격. 공정 순서 단계와 공종 프리셋은 한 상수(14개, 타일 → 욕실 순)에서 파생하고 직접 입력 공종은 맨 뒤 입력순. `TAB_ORDER`는 `TABS`에서 파생. `[공간별|공종별]`은 `?view=` 쿼리. 공간 기본값·공종 정렬·합계·상태 전이·추가 비용 변환은 `src/lib/utils` 순수 함수.
  11. **금액·이름(qa)**: 소수 입력은 기존 `validateAmount`처럼 거부(반올림 안 함), 표시는 기존 `formatManwon`. 공종·항목 이름 상한은 추가 비용 줄과 같은 30자로 맞춰 변환에 자르기가 없다. 확정한 견적을 지우면 확정도 풀린다.
  12. **하네스(qa)**: `@cloudflare/vitest-plugin`(pool-workers는 vitest 5 미지원). `test.projects`로 기존 jsdom 테스트와 분리, 전환 전후 699 통과 + 1 todo 동일. `rm -rf dist && pnpm test` 통과가 0-3 수락 조건. 0-4에 qa 보완 범위(골든 응답 0001~0006/0007 두 번, 수락 실패 분기, 동시 나가기 Proxy 재현, 변이 확인)를 포함.
  13. **AC 문구(qa)**: AC-9 개수는 가구 id 조건으로, AC-10은 "이 기기에서 수락한 경우 기록이 이미 있음" 전제를 명시하고 세 훅 모두 테스트. localStorage는 "기존 12개 키" 허용 목록 방식(새 키 2개 외 쓰기 0회) + 원문 `===` 비교.
- 이유: C는 매물과 같은 "행마다 JSON·한 문장 쓰기·범위 SQL" 패턴이라 새 구조를 발명하지 않고, 서로 다른 항목의 동시 편집이 안전하다(D1). 계산기를 첫 탭으로 두면서 계약 뒤 매일 쓰는 화면이 필요하다(D2). 매물 형식을 건드리지 않아 옛 번들 손상 위험이 없다(D3, AC-0). 함께 쓰기와 같은 규칙이라 사용자가 새 규칙을 배울 필요가 없다(D4). 기존 금액 단위와 같다(D5).
- 뒤집을 조건: 같은 항목 동시 편집 충돌이 실제로 잦으면 조건부 PUT(409) 또는 필드별 PATCH. 플랜이 3개로 모자라면 상한 상수만 올린다.
- 롤백: 0007은 추가만이라 옛 Worker + 새 스키마는 안전. 가구 수락·나가기 batch가 새 테이블을 건드리므로 플랜이 있는 가구가 생긴 뒤 옛 Worker로 되돌리면 나간 사람의 플랜이 숨긴 채 남는다.
- 제품 기본값(사용자 확인 전): 스펙 U1~U10, 매물 카드의 [인테리어 계획]을 버튼 줄 아래 전체 폭 한 줄로 두는 배치, B가 만든 플랜에 A가 넣은 항목은 B가 나갈 때 B와 함께 간다는 안내.
