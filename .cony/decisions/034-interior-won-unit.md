# ADR-034 [우리 집] 견적·총 예산을 원 단위로: 새 키 `amountWon`·`budgetWon` + ADR-033 게이트 재사용

- 상태: 채택
- 맥락: 사용자가 [우리 집] 금액을 "입력·표시 모두 원"으로 원했다(예: 견적 1,234,500원). 지금은 만원 정수(ADR-002, ADR-029 D5)라 원 단위 값을 담을 수 없다. 저장 형식이 늘어나므로 옛 번들 문제(ADR-033)가 같고, 1단계(065a94b) 번들은 새 키를 모른 채 쓰면 조용히 지운다(qa가 옛 파서로 재현: db36b56 → corrupt, 065a94b → ok지만 `amountWon`·`budgetWon` 버림). ADR-002를 [우리 집] 견적·총 예산에 한해 뒤집고, ADR-033 조건 3("서버 diff 0")을 개정한다.
- 선택지: A 견적 `quote.amountWon?`·총 예산 `plan.budgetWon?` 새 키, 옛 키는 읽을 때 ×10,000 / A-1 견적만 원 / B 플랜 단위 표시 `amountUnit` / C `amount`에 소수 4자리
- 의견: be(A 추천) / fe(A 조건부, A-1·B·C 반대) / qa(A 조건부, A-1 중립, B·C 반대 — C는 `1.005×10000 = 10049.999…` 재현)
- 검토 원문: [be 제안](../reviews/20261027-2000-be-proposal-won-unit.md) · [fe](../reviews/20261027-1937-fe-won-unit.md) · [qa](../reviews/20261027-1937-qa-won-unit.md)
- 결정: A. 반대 없음, 반론 라운드 생략. 조건:
  1. **배포 순서(be R1)**: 새 키 읽기·보존을 **1단계에 넣은 뒤** 1단계를 배포한다. 원 입력은 ADR-033 2단계(같은 게이트) 화면에서 연다.
  2. **읽기 한 곳(be 조건 2, fe 1·2, qa Q3)**: 옛 키(`amount`·`budget`·항목 `budget`)는 `interiorPlanRows` 계층의 `quoteWonOf`·`planBudgetWonOf`(+ 항목 예산 원 변환)에서만 읽는다. 소비처는 원만 본다. 합계 필드 이름에 `Won`(`plannedTotalWon` 등). `toWon`·`formatWon` 중복은 하나로. `rg "\.(amount|budget)\b" src` 허용 목록을 PR에 첨부. 파서는 저장 형태를 바꾸지 않는다(`amount`를 `amountWon`으로 정규화하지 않음, `toStrictEqual`로 확인).
  3. **검증(qa Q2)**: `amountWon` 0~`MAX_WON`(= 9,999,999,999,999, 13자리) 안전 정수, `budgetWon` 1~`MAX_WON`. 한 견적·한 플랜에 옛 키와 새 키가 함께 있으면 거부. `amount`·`budget` 규칙은 현행 그대로이고 8e30cdd의 `amount: 0` 허용은 유지(qa Q1 b, `quoteWonOf`가 두 0을 같게 읽음 — truthy 판정 금지).
  4. **쓰기 규칙 두 곳(be 조건 3, qa Q6·Q8)**: 견적은 `editedQuote`(1단계 `amount` 쓰고 `amountWon` 제거, 2단계 반대, 비우면 둘 다 없음), 총 예산은 공용 순수 함수 `budgetMergePatch`(한 키를 쓰면 다른 키 `null`, `{budget:n, budgetWon:null}`·`{budgetWon:n, budget:null}` 허용, 두 키 모두 숫자는 400)를 서버 `parsePlanPatchRequest`와 로컬 `applyPlanPatch`가 같이 쓴다. 서버 알려진 키 목록에 `budgetWon` 추가. 모든 쓰기 경로(POST·PUT·import·PATCH·로컬)가 두 키를 동시에 만들 수 없다는 테스트. D1에서 `SELECT data`로 지운 키가 아예 없음을 확인.
  5. **설정 시트(fe 4)**: `PlanSettingsSheet`는 바뀐 칸만 보낸다(이름만 고치면 예산 키를 보내지 않음).
  6. **1단계 시트 채우기(be, fe 5, qa Q9)**: 원 단위 값이 10,000으로 나누어떨어지고 0보다 크면 만원으로 채우고, 아니면(1,234,500·0 등) 빈칸으로 열며 "원 단위로 저장된 금액이라 이 화면에서는 만원으로 다시 입력해야 해요" 같은 안내 한 줄. 이 안내는 2단계에서 삭제.
  7. **보존 테스트(qa Q7)**: 로컬에서 계획 X에 새 키가 있을 때 계획 Y의 모든 쓰기 뒤 X `toStrictEqual`, 형제 견적 편집 뒤 `amountWon` 유지, D1 항목 PUT·`/import` 왕복. 구현 뒤 복사·제거 코드를 임시로 지워 실패 확인.
  8. **예시 M(qa Q4·Q5)**: 확정 `{amount:800}`·`{amountWon:1234500}`·`{amountWon:1235000}` + 미확정 `{amountWon:999}` + 확정 미정 1건 → 지출 예정 10,469,500원, 총 예산 1000만원이면 예산 초과 469,500원·미정 1건, `{budgetWon:12000000}`이면 남은 1,530,500원. 상한 합계 정확성.
  9. **표시(제품 기본값)**: 목록·요약·허브·표·CSV 모두 "1,234,500원"(표·CSV는 지금과 같음). 입력 칸 힌트만 억·만 형식(`formatWonKorean`). 원 입력에서 1만원 미만이면 "원 단위입니다" 안내(저장은 막지 않음). 허브에서 계산기 카드(만원)와 우리 집 줄(원)이 나란한 것은 허용.
  10. **작업 순서(fe 6)**: fe 1-3(뒤로 가기·비고·시트 순서·플로팅 버튼)이 커밋된 뒤 시작하고, 계산·표시 전환과 입력 전환을 별도 커밋으로.
- 이유: 원화는 정수로 저장하는 관례(C 기각), 단위 키는 모르는 번들이 10,000배로 오독(B 기각), A-1은 요구를 못 채움. A는 새 키 두 개와 변환 함수 두 개로 끝나고 AC-0을 지킨다.
- 뒤집을 조건: 옛 키 데이터가 모두 원 키로 다시 쓰여 옛 키 분기가 쓰이지 않게 되면 변환 분기 삭제 검토(일괄 재작성은 하지 않는다).
- 롤백: ADR-033 조건 2와 같다(1단계 이전으로 되돌리지 않는다).
- 검토 권장: 없음.
- 제품 기본값(사용자 확인 전): 조건 9의 표시 형식.
